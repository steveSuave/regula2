## Phase 121 — Old kernel deletion + convention unification

- [x] ~~Revisit the detour orientation convention~~ — **settled in Phase 120c**: drags take a constant half-plane and a round trip carries honest monodromy (PLAN §"A round trip is honest"). Was deferred from 117 on a user decision of 2026-08-14 and reopened by the user on 2026-08-17
- [x] Unify the last convention non-uniformity it left: **locus** runs used `detourOrientation1D` (odd in the drive direction) while drags used the constant. Unified onto one `detourHalfPlane` (renamed from `dragDetourOrientation`, which is no longer drag-only; `detourOrientation1D` deleted), and the fixture diffs are **nil, bitwise** — measured on all four locus documents, of which only `apatitos-topos.rgl` detours at all, twice, both on forward legs, which is exactly where the two rules disagreed. The reason generalizes and is now recorded (PLAN, same section): an arc encircles its one estimated singularity by a half-turn whichever side it passes, and a half-turn either way exchanges the two sheets of a simple branch point — so the half-plane can only matter when an arc encloses more than one collision, or one of higher order, where the arc is mis-planned and neither rule is right. New coverage pins that the Phase 117b rig *detours* (two arcs, no folds), so the sheet assertions over it are known to exercise one
- [x] `construction.dart` carried a **literal NUL byte** in a composite map key (`'${curve1.id}\x00${curve2.id}'`, the Phase 120c per-pair adoption group), which made `file(1)` call it `data` and `grep`/`rg` skip the whole file as binary — silently, so a search for anything in the largest domain file came back empty. Escaped; same string value, and the file is text again
- [x] `locus.dart`'s index-flip consistency guard assumed two candidates (`old.length != 2 || now.length != 2 → skip`), so a conic∩conic pair inside a locus chain silently lost that check rather than crashing. **Widened**, and moved to `trace_acceptance.dart` as `relabelIsBenign` where it is directly testable: a flip is a benign canonical relabel exactly when every root the slot did *not* follow pairs with a distinct other root across the flip within the same motion allowance. Nearest-match is exact rather than greedy here because the cap is at most half the set's minimum pairwise separation, so no pairing is ambiguous; at two candidates the general form reduces to the old `1 - index` arithmetic exactly. Unequal candidate counts still impose nothing — a root has entered or left the real set and the walk's other rules own that
- [x] Delete `lib/domain/math/intersections.dart` — **moved** to `test/v1_oracle/intersections.dart` rather than deleted, and with it the three other V1 modules that turned out to be in the same state (`angle_bisector`, `circle_relations`, `harmonic`, `tangents`: no `lib/` importer since Phase 110 superseded each with a projective kernel). Deleting them would have deleted the *evidence* that the projective kernels still agree with V1 on real transverse cases, which is the contract `branchIndex` addresses and is permanent because v1 documents are. Six test files consume them as oracles. Living under `test/` turns the standing rule from a grep gate into the directory layout, and `layer_rule_test.dart` gained a gate that no shipped file reaches into `test/`
- [x] Demote `LineEq`/`CircleEq` to view structs (remove throwing construction paths from domain flows) — already true in code and now stated where it is read: nothing constructs either outside `lib/domain/`, and inside it only through `toLineEq`/`toCircleEq` or behind a guard, so the throwing factories are a programmer-error contract rather than a path a recompute can fall down. The one exception was `InscribedCircle`, which passed `inradius(...)!` straight into `CircleEq` on the strength of two helpers sharing a collinearity test; it now checks. Recorded in both type headers and CLAUDE.md, whose "legacy affine math (frozen; shrinking)" row was no longer true of what is left in `lib/domain/math/`
- [x] One degeneracy convention everywhere: projective value total; projection nullable — audited across all 44 kinds and found already uniform (`null` only when a parent's projective value is null, or when the computed homogeneous value is the **zero triple**, which is not a projective object). Stated at the declaration site in `geo_object.dart` with its three sanctioned exceptions named (`IntersectionPoint`'s realness gate, `PointOnObject` without a chart, the Phase 112 consumer kinds), and given a gate: collapsing every free point in the two kitchen-sink corpora onto one position produces all 44 degeneracies at once, and every surviving affine view must still have an agreeing projective value (29 do — a degeneracy is mostly a value, not an absence)
- [x] Remove lift-default dead code where every kind now overrides — `GeoPoint.projPoint`, `GeoLine.projLine` and `GeoCircle.conic` are **abstract**. All 44 kinds already implemented them (eight only through a migrated intermediate base — `TriangleCenterPoint`, `RelativeLine`, `TriangleCircle` — which is why a per-file grep undercounts), as did every test stub: the change is analyze-clean and suite-green with nothing else touched. The defaults were right during the migration and are a trap after it, because a kind that forgot to store homogeneous state would silently inherit a lift of its affine value instead of failing to compile. The `lift` constructors themselves stay: they are the chart → homogeneous kernel API, not scaffolding
- [x] `point_coincidence.dart` re-pointed at projected positions — **it needed no code change, which is the finding**: the probe only reads `GeoPoint.position` and writes `FreePoint` positions and `PointOnObject` parameters, all of which are projections and chart parameters now, so the perturbation still perturbs exactly the mutable roots and the restore is still bit-exact (a `FreePoint` stores the lift of its position, `w` exactly 1). Two consequences are deliberate and now stated in the file and pinned by a test: an off-chart point (at infinity, or complex) has no position and is never merged — two pairs of parallels meeting at the *same* projective point stay two points, the conservative branch this function takes everywhere — and the tolerance stays in world units, because it screens "one dot or two", a question about the chart and not a projective invariant
- [x] Grep gates recorded in CLAUDE.md; PLAN's migration-contract section replaced by the final architecture description. ## Phase 122 — Performance hardening + compile-target finalization

- [x] **Measure the hot loop before rewriting it — it is not the tracing slot** (PLAN §"The hot loop was not where the phase said it was"). On a traced `IntersectionPoint.recompute`, `TracedBranch.follow` is 43 ns of 3044 — **1.4%** — with `checkpoint` at 11 ns and `restore` at 6. The remaining ~98% is `intersectionCandidates`. So the SoA item below is re-pointed: it can only ever have been worth a percent and a half of a drag frame, and the phase's budget belongs where the time is
- [x] **Two circles need no cubic.** `intersectionCandidates` on two circles cost 8× line∩conic, because it ran the general four-root pencil (balance → cubic → clustering → member scoring → adjugate split) and then discarded I and J — which it had just recovered numerically and which are known. A conic is a circle exactly when `xy = 0`, `xx = yy`, and for two of those `b.xx·A − a.xx·B` kills the quadratic block, leaving `w·(2Dx + 2Ey + Fw)`: the degenerate member in closed form, ℓ∞ together with the radical axis. Steps 2–4 collapse to two subtractions; the Newton polish goes with them (it cleans up a member found at an inexact root, and there is none). The centroid balance **stays** — free for circles, and measured load-bearing at 1e6 offset (2e-5 unbalanced vs 1.3e-10). Measured on `locus-miss-2.json`: 5.85 → 3.47 µs/solve VM, 8.53 → 3.77 AOT, 8.28 → 4.37 dart2js, 8.65 → 3.98 dart2wasm, with **identical solve counts** and `apatitos-topos.rgl` (line∩circle) unchanged as the control
- [x] Tests: the circular points come back at exactly `w = 0` — the discriminator that says the short route was *taken*, the general one leaving them at `|w| ~ 1e-33`; both routes answered index for index over 400 random pairs, the general one reached by nudging a conic 1e-30 off the circle shape, with both the real and the conjugate regimes covered (they order by different rules); the centroid balance load-bearing at 1e6; complex carriers — what a detour hands it — incident on both conics; concentric circles meeting only at I and J, doubled. The pre-existing V1-agreement and complex-rescaling properties now run over the short route, which is what pins the branch orderings
- [x] **Canonical ordering was half of what was left, mostly a tie-break nobody reached.** With the cubic gone, `_canonicalOrder` cost 505 ns of the surviving 1080 — not in recovering the two centres (handing those in, free for a circle, is worth 56 ns) but in building four `_OrderKey`s eagerly, each with its lexicographic tie-break list and a `normalized` behind it. A circle pair gives two real points and then I and J, where tier and primary always decide, so all four were built and discarded every solve. Lazy now; same rule, same comparisons. `intersectConicConic` on two circles: 2676 → 947 ns
- [x] `benchmark/chain_solve_bench.dart` + `run_chain_solve.sh` — the breakdown itself, kept so the split is re-measurable on every target rather than re-derived
- [x] **SoA re-measured against the new profile and closed as not worth doing** (PLAN, same section) — a measurement, not a reversal. Phase 101's numbers stand: unboxed SoA beats boxed `Complex` by 1.30–1.78× *on the arithmetic*. Applied to a tracing slot that is **3–6%** of a traced recompute (VM 4.1%, AOT 5.7%, dart2js 6.1%, dart2wasm 3.0%), the ceiling is 1–2.5% of a drag frame — under the noise of the gate it would be measured on. The prior was sound when formed; what it could not know was how small the arithmetic-heavy slot would be next to the graph recompute. Phase 101's real dividend, the storage shape for `TracedBranch`, is already in place. Unboxing the *kernel* (the 85–97%) is a different and much larger question, deliberately not opened: nothing is currently bottlenecked, and the algorithmic route already beat what representation promised, at a fraction of the risk
- [x] Benchmark suite runnable in CI (informational job) — `benchmark/run_ci.sh` (VM-only, dependency-free, ~1 min) behind `.github/workflows/benchmarks.yml`, on every push to main plus manual dispatch. Deliberately non-failing: a shared runner's absolute timings are not what the 8 ms budget is about, so it reports and the per-target scripts decide. Its value is catching an order-of-magnitude move and putting the trend in the log
- [x] **Final dart2js-vs-dart2wasm decision executed: wasm, Pages deploy switched** (PLAN, same section). dart2wasm wins raw complex arithmetic by 1.4–1.7× and is a wash on the whole engine (it takes `locus-miss-2` 3.69 vs 3.92 µs/solve and the drag gate 0.128 vs 0.140 ms, and *loses* `intersectionCandidates` on two circles, 2345 vs 2060 ns). What settles it is the payload: `--wasm` emits both, so a WasmGC browser fetches 2.4 MB of wasm instead of 2.8 MB of js and anything older falls back to exactly what it gets today. Not yet smoke-tested in a browser — the repo has no remote, so the workflow has never run; that check belongs with the first deploy
- [x] **Drag budget re-measured and recorded as the standing gate.** `tracing_bench.dart` now *throws* when a frame exceeds `dragFrameBudgetMs`, so a job can enforce it without parsing text (thrown, not `exit`ed: `dart:io` would cost the file its js and wasm targets, and an uncaught error is a non-zero exit on all four). Standing measurement across VM/AOT/dart2js/dart2wasm: **1–2%** of the 8 ms budget plain, **7–11%** carrying the 128-sample locus, checksums identical

## Phase 126 — M-CK3: the mode as a UI

The first phase of the milestone the user can *see*. Three phases of kernel work were reachable only from tests; this one opens the door, in the order the door has to open — **the tool layer first, the codec's refusal last**, because the refusal was standing in for the threading that was missing.

- [x] **The kernel carried into the tool layer**, per the note left at `nearestIntersectionBranch` in Phase 125. `ToolInput.absolute`, filled by the canvas from `Construction.kernel`, threaded through `resolvePoint`, `IntersectionTool`, `MidpointTool`, `MultiPointTool` and the macro tools; the `IntersectionPoint` factory takes it for the canonical remap alone, both orders' candidate lists being filtered against the absolute. Done *before* the codec change, not after: `branchIndex` addresses the filtered list, so a tool on the default in a hyperbolic document writes an address into the file naming a different crossing on reload
- [x] Two findings from that threading. **`coincidentExistingPoint` is worse than answering wrongly** — it perturbs every mutable root and recomputes the *whole construction*, so a defaulted absolute leaves the entire document computed Euclidean, silently, until the next mutation happens to recompute it. And **three `recompute()` calls in `locus.dart`** were still on the default (the static settle after a sweep, and both drive steps inside `_TracedSweep`, which had the absolute in hand throughout)
- [x] **The premise checked rather than asserted.** Two `FivePointConic`s through Euclidean-concyclic points that *miss* give two candidates under Euclidean and four under hyperbolic — and I and J sort *around* the complex pair, so address 0 is a crossing in one geometry and a circular point in the other. A five-point conic is tier 1, so the conics are bit-identical in both and the crossings do not move at all: only the numbering does
- [x] **`Construction.kernel` stops being `final` and does not become a setter.** The only route is `switchKernel`, which switches, recomputes, re-points by chordal match and returns the report — so no call switches without re-addressing (PLAN §"The switch is an operation, not a setting"). The general rule is worth keeping: when a mutation has an obligation attached, make the obligation the only route rather than a rule the caller must remember
- [x] `SetGeometryCommand` records what the switch decided and replays those addresses verbatim on undo and redo, because nearest-match is not invertible — running it backwards can land a point where it never was, and a point with no position at the switch was never matched in either direction. What cannot be matched is **reported**, not repaired: there is no evidence of what the user meant
- [x] **The codec's refusal turned into support.** `_decodeKernel` drops the second guard and keeps the first — an *unknown* metric name is still refused. Round-trip tests per metric, and the geometry comes back with the document (the CK midpoint, not the affine one). The version rule is untouched; a non-default kernel was already v2 and `test/fixtures/` stays v1
- [x] **Disc-boundary rendering.** `absoluteDisc` gives the hyperbolic unit circle with the region outside it washed, because that region is not part of the plane. Elliptic and Euclidean draw nothing, for two *different* reasons that are facts about the geometries rather than gaps — elliptic has no real absolute and no edge at all; Euclidean's is the line at infinity, real but in no chart. Centre and radius come from the viewport, exact under rotation because a circle stays a circle
- [x] **The mode as UI**: a geometry menu beside "Axes & grid", the switch routed through the command stack so it undoes like the edit it is, and the re-addressing report surfaced in a snack bar
- [x] **The mini-tutorial**, asked for directly and written where a user finds it (the menu's own guide): four things to build that look different in each geometry, plus the note that nothing in the toolbar changes — what changes is which theorems are true
- [x] **And the guide's first claim is a test rather than a promise.** A triangle's angle sum is exactly π in Euclidean, less in hyperbolic, more in elliptic; the hyperbolic defect grows with the triangle and vanishes in the small limit. Gauss–Bonnet from three independent `VertexAngle`s — a global fact that no angle measure wrong by a scale, a sign, a supplement or a chart artefact survives. The first payment on the debt Phase 125 recorded: its coverage gate showed each kind *responds* to the absolute, never that the response was right
- [ ] Still owed from the same debt: per-kind correctness beyond angle, and `RotatedPoint`, which is a gap rather than a refusal (a rotation about the disc centre *is* the Euclidean matrix)
- [x] The load-time report for `repairedIntersections` — the decoder computes it and **nothing displays it**. Done in Phase 126e below, and it turned out to be two reports rather than one

## Phase 126b — M-CK3 follow-up: the presentation boundary

Reported by the user after 126 shipped: a triangle in the hyperbolic plane measured exactly 180°, no circles appeared, and elliptic looked identical to Euclidean. **All three were real, and all three sat outside what `ck_kind_coverage_test` can see** — that gate asks whether a kind's *value* responds to the absolute, and every one of these was a correct value that never reached the screen. The coverage debt Phase 125 recorded was about per-kind correctness; this is a second and separate gap, at the domain→presentation boundary, and it is the one that decided whether the milestone appeared to work at all.

- [x] **The angle label read the marker, not the measure.** `labelText` took `angle.measure` — the chart sweep of the drawn arc — where it meant `GeoAngle.measure`. The same trap `GeoAngle.measure` itself fell into mid-Phase-125, one layer out. Labels now read 152° / 180° / 202° for one triangle across the three geometries, which is also what made elliptic look inert
- [x] **Every CK circle was invisible.** `GeoCircle.isDefined` was `circle != null`, which asks whether the conic is a *Euclidean* circle; a CK circle is bitangent to the absolute, so `toCircleEq` answers null and the painter skipped it before reaching the conic arm that draws it correctly. Now falls back to `ConicShape.isParameterized` — a curve, **narrowly**, where `isDrawable` would also admit line pairs, which is what keeps Euclidean bit-identical (a collinear `ThreePointCircle` is a real line pair and must stay undefined)
- [x] **The plane was two pixels across.** The absolute is the unit circle in *world* units and the default scale is one pixel per world unit, so the whole hyperbolic plane was a dot at the origin while the figure sat hundreds of units outside it — outside the plane, where angles collapse to zero. `fittedToAbsolute` frames the disc on switching; Euclidean and elliptic leave the view alone, neither having a privileged region to frame
- [x] **One constant was answering two questions.** Framing the disc needed `maxScale` above 50, which moved six goldens — and the move was the finding. "How far may the user zoom" is about the view and a hyperbolic document needs a great deal of it; "how far may a fit blow a tiny figure up" is about taste and its right answer did not change. Split into `maxScale` (2000) and `maxFitScale` (50, the old value)
- [x] **The wash was correct and invisible** (Phase 126c). One alpha of 0.09 on the absolute's colour measures a 5 % luminance step over the light canvas — reported as "the same background colour". Replaced by a per-theme colour with its alpha baked in, because the two canvases start from opposite ends and one alpha cannot serve both; light and dark now measure 0.14 and 0.10. Pinned by **rasterizing and measuring**, the only kind of test that separates "drawn in the right shape" from "visible" — the painter test that checks the path's shape was green the whole time
- [x] **The wash left no hole at all on the web renderer** (Phase 126d) — the user's actual report, which I misread twice before the screenshots settled it. With the disc entirely inside the canvas the whole surface was washed and only the rim showed; with any part of the boundary off an edge it rendered correctly. `Path.combine(PathOperation.difference, rect, oval)` returns the outer rect unbroken on web when the inner shape is fully contained, and the annulus on the VM. Both uses are even-odd fills now — same region, no boolean op, nothing left to differ — and the second use, the region-pick scrim, had the identical defect unreported and one grep away
- [x] **`test/web/` and a CI browser gate.** Web is the compile target, the VM harness is not the renderer, and nothing in the suite had ever run in a browser. `flutter test --platform chrome test/web` is in CI and in CLAUDE.md; scoped to a directory because `--platform chrome` compiles everything it is handed to JS. The file keeps the boolean difference as *evidence*, asserting the broken behaviour, so the day an engine fixes it the test says so
- [ ] `visibleWorldBounds` contributes nothing for a CK circle — it reads centre and radius, which a bitangent conic has not got — so fit-to-construction under-frames a hyperbolic document. Harmless while `fittedToAbsolute` frames the plane instead, and worth a conic bounding box eventually
- [ ] **The absolute's radius is fixed at 1 world unit, and that is a usability decision worth revisiting.** It is the canonical normalization and every kernel test assumes it, but it means an existing Euclidean construction — drawn at world coordinates of tens or hundreds — is entirely outside the plane the moment it is switched, and cannot be brought in without moving every point. A per-document absolute radius (`diag(1, 1, −1/R²)`, additive to the kernel block, still v2) would make switching an existing figure meaningful. Not built: it is a schema decision, not a bug fix

## Phase 126e — the two silent re-addressings, said out loud

The debt Phase 126 left, and it was larger than the checklist line. An intersection point's **address** can change without the user touching it in exactly two ways: opening a document the reader had to repair, and switching the document's geometry, where `branchIndex` names a position in the candidate list *as ordered against the absolute*. Both are invisible by construction — a re-pointed crossing looks exactly like the one the user tapped — and a silent repair is how the Phase 120c document accumulated points nobody could account for in the first place. So the fix is one report, in one place, for both.

- [x] **The reader was silent about the case it could not fix, which is the case that matters more.** `_separateDuplicateBranches` returned the ids it moved; a duplicate whose curve pair has no crossing left to give it fell out of the loop with nothing recorded. A repaired point is a defect the reader *fixed*; an unrepaired one is still there, no drag can separate it, and the only remaining fix is to delete the surplus — which is the user's call, not the decoder's. `DecodedDocument.unrepairedIntersections`, the honest remainder, same shape as `GeometryChange.unmatched` and for the same reason
- [x] `intersection_report.dart` — both messages as plain functions taking no `BuildContext`, because **the sentence is the feature** and should be readable without a widget tree, plus one `showIntersectionReport` so the two read as the same kind of news. The switch's phrasing is unchanged and `GeometryMenu._report` becomes a call to it
- [x] Wired into the open flow in `main.dart`. Checked while there: reading `decoded.kernel` would be a *second* source — the kernel rides on `decoded.construction`, which the codec built with it — so the load path needs no separate apply and does not have one
- [x] **Tested at three levels, which is the Phase 126b lesson applied rather than restated**: the strings themselves; that `showIntersectionReport` actually puts one on screen; and both real flows end to end — Open through the fake picker `file_menu_test` already had, and the switch through the `geometry_switch_test` witness (two tier-1 conics that miss, so nothing moves and only the numbering changes). Every one of the four Phase 126b–d defects was a correct value that no test drove all the way to the screen
- [x] **And the negative on each**, because it is a claim rather than an omission: a well-formed document and an ordinary switch say **nothing at all**. Most of a document is real transverse crossings that keep their indices in every geometry, so the usual report is no report — an unconditional "your points may have moved" is noise and trains the user to dismiss the one time it matters
- [ ] The unrepairable case gets a snack bar that vanishes in six seconds, for a defect the user has to *act* on (delete the surplus point). If anyone ever hits it, that wants a dialog naming the ids, or the object tree flagging them

## Phase 125 — M-CK2: the tier-2/3 substitutions

The bulk of the milestone: 32 kinds. Taken in the audit's order — the verbatim pole/polar generalizations first, then the genuine re-foundings, then the refusals. **Zero Euclidean behaviour change** throughout.

- [x] `euclidean.dart` → **`metric.dart`**, every function taking an `Absolute`. It was never only Euclidean; it was the Euclidean case of a family
- [x] **Midpoint and angle bisector are the same construction, dually** (PLAN §"Two constructions, one algebra"). A midpoint is the pair harmonic to `{P,Q}` and to the absolute's two points on `PQ`; parameterizing `X(t) = P + tQ`, harmonic to `{0,∞}` forces `M₋ = −M₊`, and harmonic to the absolute's roots forces `t² = ⟨P,P⟩/⟨Q,Q⟩` — so `M± = √⟨Q,Q⟩·P ± √⟨P,P⟩·Q`. Under Euclidean `⟨P,P⟩ = w²` and that reads `w_Q·P ± w_P·Q`: **the affine midpoint, plus the point at infinity in direction `P−Q`** — the external midpoint, whose sitting at infinity is why Euclidean seems to have one. The same algebra in the dual gives `B± = √⟨m,m⟩*·ℓ ± √⟨ℓ,ℓ⟩*·m`, which under `diag(1,1,0)` is exactly the √-unitization `twoLineBisectorOf` already had
- [x] Perpendicularity generalizes verbatim — `perpendicularThrough(P,ℓ) = P ∨ absolute.poleOf(ℓ)`, the audit's structural claim, now a test
- [x] `parallelThrough` **refused** under a proper absolute (zero triple), not approximated
- [x] Two cross-cutting fixes the tests found: **conjugacy is perpendicularity** in every CK geometry, so a vanishing pairing between two *non-isotropic* lines is a right angle whatever the self-pairings' signs (a line and its perpendicular can sit on opposite sides of the absolute, making the product under the root negative); and **every measure removes a global phase first**, because the CK constructions take a square root of a form that is negative inside the absolute and hand back real elements scaled by `i`. The normalization divides by the pivot's unit *phase*, not the pivot — it must be exact, since the perpendicularity test is an exact zero and rounding it to 2.7e-17 lost every right angle it touched
- [x] The eleven `metric.dart` consumer kinds wired, with the absolute threaded through the two template methods (`TriangleCenterPoint.computeCenter`, `RelativeLine.carrierFrom`) rather than each override reaching for it
- [x] **Transforms**: `ProjTransform.harmonicHomology` added, and it reproduces the shipped Euclidean reflection matrix **entry for entry** — the audit's claim that reflection *is* the homology about `(axis, its pole)`, checked rather than asserted; point reflection is the homology about `(centre, its polar)`, ℓ∞ under Euclidean, which is why it reads as a homothety of −1
- [x] **Circles** in `ck_circles.dart`, and they split the way distance splits (PLAN §"A circle follows its distance measure"). `d(C,X) = r` squares to `⟨C,X⟩² = k⟨C,C⟩⟨X,X⟩`, i.e. `K = ⟨R,R⟩(ΩC)(ΩC)ᵀ − ⟨C,R⟩²Ω` — the pencil through the absolute and the doubled polar of the centre, hence **bitangent**. Under Euclidean that whole pencil collapses to multiples of ℓ∞, so `circles.dart` is a *companion*, not a special case. A centre on the absolute is a **horocycle**, not a degeneracy. `Arc`/`Sector` refused: the carrier generalizes, the angular extent is a chart parameterization
- [x] The five re-foundings, and **three of them turned out to generalize** because their definitions are constructions rather than formulas: the centroid is the medians' common point (CK midpoints), the incentre the internal bisectors' (CK bisector), the inscribed circle centred there through the foot of a perpendicular. `FixedRadiusCircle` gets `ckCircleWithRadius`. Refused with reasons at the site: homothety and translation (a similarity that is not an isometry does not exist in CK — Wallis), rotation (needs an orthonormal frame in the pencil, whose form changes sign across it), Apollonius and bifocal conics, the radical axis, the focal conic, the circle centre (a generalized eigenproblem for the pencil `{K, Ω}`), segment-ratio points
- [x] `IntersectionPoint`'s circular-point filter made absolute-aware, and threaded **all at once** because `branchIndex` addresses the *filtered* order — a caller left on the default lands its points in a different address space, the Phase 120c failure from a new direction. One caller knowingly stays on the default and says so: the tool layer has no construction to read a kernel from, which is correct only while the codec refuses non-Euclidean documents. **Phase 126 must carry the kernel into the tools before lifting that refusal**

## Phase 124 — M-CK1: measurement, and the half of it that is not a cross-ratio

PLAN §M-CK said the tier-4 kinds are "re-founded on cross-ratio, with Euclidean as the degenerate case that reproduces today's numbers". **Measured first: that is true of angle and false of distance**, which is the classical Cayley–Klein classification arriving as a code constraint — Euclidean has *elliptic angle measure* and *parabolic distance measure*.

- [x] **Angle unifies, at the bilinear-form level rather than through logs.** `cos θ = ⟨ℓ,m⟩*/√(⟨ℓ,ℓ⟩*·⟨m,m⟩*)` against the *dual* absolute is Laguerre's cross-ratio formula with the logs cleared, and under `diag(1,1,0)` it is `(a₁a₂+b₁b₂)/(|n₁||n₂|)` — the textbook Euclidean formula, verbatim. Measured: agrees with the chart route to **7.4e-13** over 20k random line pairs
- [x] **Distance does not unify, and cannot.** A line meets the Euclidean absolute (the *doubled* ℓ∞) in one point twice, and a cross-ratio with a repeated point is identically 1, so the log is identically 0 for every pair of points. Euclidean distance is not a cross-ratio at any constant — recovering it needs the constant to diverge as the absolute degenerates. So distance **dispatches on the measure** where angle substitutes: parabolic (Euclidean, the chart route it already uses), hyperbolic (`cosh d = |⟨P,Q⟩|/√(⟨P,P⟩⟨Q,Q⟩)`), elliptic (the same with `cos`). Verified against `artanh(r)` and against the cross-ratio route to the last digit
- [x] Thread the absolute into `recompute`, per Phase 123's decision — **defaulted to Euclidean while the migration runs**, which is the pattern Phases 106–121 already used for the projective accessors and then removed. Scheduled for removal at the end of Phase 125, when all 38 kinds take it; `Construction` passes `kernel.absolute` from the start, so the default is scaffolding at the declarations and never a live fallback
- [x] `Absolute` gains the bilinear pairings (`pairPoints`, `pairLines`) the quadratic forms of Phase 123 polarize to; `lib/domain/projective/ck_measure.dart` holds the two measures and names the three measure kinds
- [x] `VertexAngle` and `LineAngle`: the CK formula becomes the *definition*, with the exact Euclidean route retained as its specialization — the Phase 122 circle-fast-path rule, for the same reason (it is exact, cheaper, and keeps `expect(angle, 90)` reading exactly 90). Agreement proven by test rather than by routing. The marker's vertex and start direction stay chart quantities, like a measurement's anchor
- [x] `DistanceMeasurement` on the three measures. `LengthMeasurement` and `AreaMeasurement` are **integrals**, not substitutions (hyperbolic circumference is `2π·sinh r`, and a hyperbolic triangle's area is its angular defect) — deliberately **not** implemented here, and undefined rather than wrong under a proper absolute. `SlopeMeasurement` is Euclidean by definition and goes undefined with the others
- [x] Gates: **zero Euclidean behaviour change** — suite **2438** green, analyze clean, **32 goldens byte-identical**, perf gate PASS at 1% / 7% of budget with unchanged checksums. Every non-Euclidean path is reachable only from tests this phase, since the codec still refuses the two other metrics. Also added: `GeoAngle.measure` beside `angle`, because a marker is not a measure — the arc is still drawn between the same two chords while the number is the CK angle

## Phase 123 — M-CK0: the absolute, and the audit that scopes the milestone

Opens the M-CK milestone (PLAN §"M-CK — Cayley–Klein"). The kernel track closed at 122; this is the first milestone phase. **Zero Euclidean behaviour change** is the phase's safety property — suite, 32 goldens and the tracing checksums all untouched — because it is what lets 124–126 be incremental.

- [x] `Absolute` in `lib/domain/projective/absolute.dart` — the fundamental conic as **both** matrices, point conic and dual, given explicitly per instance rather than derived (PLAN §"The absolute is carried as its dual"). The reason sharpened while building it: the Euclidean *dual* {I, J} is rank 2, but the *point conic* is the doubled line at infinity, **rank 1**, and the adjugate of a rank-1 matrix vanishes identically — so the dual cannot be derived, and the derivation fails harder than "not invertible" suggested. `ConicMatrix.applyToLine` added as `polarLine`'s dual-role counterpart (distinct from `poleOf`, which forms the adjugate first — on a dual already in hand that would be taking the dual twice)
- [x] **The audit — the phase's main deliverable** (PLAN §"The audit"). The import census that scoped this phase said 25 and missed two whole routes: `proj_transform.dart` is a **fifth** metric kernel module (five transform kinds import none of the four censused ones), and the six measurement kinds import nothing metric *because they measure in the chart directly* — the Phase 112 boundary working as designed, and invisible to a census

So tier 3 is largely *rewriting formulas as the pole/polar constructions they already are*.
