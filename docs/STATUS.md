## Session 122 (V2 Session 24) — 2026-08-17

**Done**
- **Phase 120 complete** (five-point conic: object + tool) and **Phase 120b complete** (the conics group), merged to `main`. Two defects were found on the way and fixed at the root — both had shipped in earlier phases and only became reachable when a kind could finally *produce* a general conic.
- **`FivePointConic`.** Stores `ConicMatrix.throughFivePoints`; `circle` is the circle projection, so a five-point conic that happens to be a circle takes the painter's and hit-tester's circle arm with nothing special-casing it. `isDefined` is `ConicShape.isDrawable`, so a degenerate five-point set is still defined when it draws (a line pair, a doubled line) and undefined when it does not (an isolated point, an imaginary ellipse). Coincident parents guarded at `projectiveEpsilon`; the other rank deficiencies come back from the kernel as a null.
- **The conics group** (user-directed scope addition, PLAN updated first). `FocalConic` carries the eccentricity as a param — the parabola tool is that kind at `e = 1`, so there is no separate parabola kind to keep in step — and `BifocalConic` carries the sum/difference flag. The Conics toolbar group holds conic-*valued* kinds only: five points (moved out of Circles), parabola, ellipse, hyperbola, and the eccentricity dialog; tangent/polar/radical-axis stay in Lines because they are lines. Shortcuts `G B`, `G ⇧E`, `G ⇧H`, `G ⇧C`, with `G 5` unchanged.
- **Where the metric enters is the whole design** (PLAN §"The conic constructors, and where the metric enters"). `focalConicOf` is metric but still polynomial, and its entire Euclidean content is one coefficient — `a² + b²`, the directrix against the dual of {I, J} — which is M-CK's only substitution there. `bifocalConicOf` genuinely cannot be: a sum of square roots of distances has no polynomial form in homogeneous coordinates, so it reads projections at the Phase 112 metric boundary. One formula covers both bifocal branches; the flag chooses a definition, not a case in the algebra, and both degenerate limits fall out of it. The projective alternative (the confocal family as a dual pencil, "P on C" quadratic in the pencil parameter, its two roots the ellipse and the hyperbola) is recorded and rejected for now.
- **Defect 1 — a parabola could classify as an ellipse, and 0.4% of the time not draw at all.** `ConicShape.of` asked whether the two meets with ℓ∞ were *real* before asking whether they were the *same point*. A parabola's meets are one double root, inherently only ~√(machine eps) accurate, so rounding routinely pushed the pair off the real axis and sent the conic into the ellipse branch — which seeds from a probe through the centre, and a parabola's centre is genuinely at infinity. Surveyed over 3000 random exact focus-directrix parabolas: **1700 parabola, 1287 ellipse, 13 `empty` — not drawable at all**. Coincidence is now asked first (no new tolerance: `doubleRootEpsilon` already decided parabola-versus-hyperbola on the real side), and the seed is taken as the null direction of the quadratic block, real by construction. After: **3000 of 3000**, every one drawing, all 30 goldens byte-identical.
- **Defect 2 — `IntersectionPoint` capped `branchIndex` at 0..1.** Right while every `GeoCircle` was a circle, and it survived Phase 110's four-candidate conic∩conic solver only because nothing could produce a general conic. Tapping the third crossing of two conics threw an `ArgumentError` from the tool, and the codec would have refused to reload any document containing one (the decoder builds through the same constructor). Now `maxBranchCount = 4`; `recompute` already clamped, so nothing else moved.
- **Defect 3 — a fill attribute on a conic crashed the frame.** `_drawFill` unwrapped `object.circle!` for every `GeoCircle`. Phase 119 made the stroke, label-anchor and label-obstacle paths conic-aware but not this one. A conic bounds nothing the painter can close, so the pass skips it and the inspector withholds the row — by *kind*, so an undefined circle keeps its row.
- **`buildKitchenSink()` is now frozen** by `test/fixtures/v1/kitchen-sink-v1.json`: it is what a v1 app wrote, so a kind v1 never knew cannot honestly appear in it. Post-v1 kinds live in a new `buildPostV1Kinds()`, and both "every concrete kind" sweeps (codec round-trip, projective bridge) run over the pair. `geometryOf` falls back to the conic when there is no circle projection, or the round-trip check would have been vacuous for exactly the kinds it was extended for.
- **No version bump.** The three new kinds store ordinary params, and a v1 build meeting one refuses the whole file by its unknown type — which is exactly the protection the stamp buys. Novelty is not misreading. (The Phase 119 STATUS predicted `FivePointConic` would be the first user of the reserved homogeneous-param slot; it needs no stored homogeneous state, so that slot is still unused.)
- **The Conics group's icon is drawn, not a font glyph.** `Icons.egg_outlined` shipped first and read as a filled egg; rendering every plausible Material candidate side by side confirmed there is none that means *conic* — they are all either circle variants (which compete with the Circles group sitting right beside them) or organic. So `ConicIcon`: a wide ellipse on Material's 24-unit grid with a 2-unit stroke, taking its size and colour from the ambient [IconTheme] exactly as `Icon` does. `_ToolGroup.icon` is now a `Widget` and the active tint flows through `IconTheme.merge`, so the group tints a font glyph and a painted one identically without knowing which it has.
- Suite **2363 green**, 32 goldens (four new, all reviewed), analyze clean, `flutter build web` compiles.

**Next**
- Phase 121 — old kernel deletion + convention unification: delete `lib/domain/math/intersections.dart` (test-side only now), demote `LineEq`/`CircleEq` to presentation view structs, one degeneracy convention everywhere, the deferred detour-orientation decision, and grep gates recorded in CLAUDE.md.

**Gotchas**
- **`ConicShape.kind` is a label, not a code path** — the sweep, the break parameters and `closed` all come from geometry, never from the enum. That is what made defect 1 survive Phase 119's goldens, and it is why the parabola's *label* is exempt from the five-point reconstruction property (its double root is only √eps accurate, so a reconstructed parabola reads as whichever open class the rounding lands on). Don't add a `switch (kind)` in the render path without re-reading this.

## Session 121 (V2 Session 23) — 2026-08-16

**Done**
- **Phase 119 (conic rendering + hit-testing) complete** on `phase-119-conic-rendering`, merged. Six commits, math before pixels deliberately: the whole phase is thin arms over one domain file, so the file was built and tested against the geometry before anything drew.
- **`lib/domain/projective/conic_shape.dart`.** The class is **how the conic meets the line at infinity** — two real meets a hyperbola, one doubled a parabola, a conjugate pair an ellipse (real or imaginary, settled by a line through the centre). That is the classical definition and also the projective one, so it needs no world-space tolerance and the same test hands back the real point the sweep is seeded from. A hyperbola's two branches and a parabola's arm are then not cases in the code: they are the arcs between the parameters where the curve passes through infinity. Rank ≤ 2 splits into components (`splitDegenerateConic` published out of the pencil solver, with its own tests): two real lines, a conjugate pair whose real meet is the conic's only real point, or one line doubled.
- **The sweep is stereographic**, per PLAN §Parameterization: `X(Q) = (QᵀAQ)·P₀ − 2·(P₀ᵀAQ)·Q`, quadratic in Q, so `pointAt` is polynomial in homogeneous coordinates and total. Q runs as `e_i·cos φ + e_j·sin φ`, walking the pencil's RP¹ cyclically over `[0, π)` — the Phase 117 density profile — instead of putting the rational parameter's blow-up on one point of the curve; `X` comes out exactly π-periodic.
- **The viewport clip is exact, not sampled.** A conic can only cross the box on one of the four edge *lines* and only escape on ℓ∞, so those five cuts make every arc wholly visible or wholly hidden; one interior sample classifies each, adjacent visible ones merge (a curve tangent to an edge from inside is cut where it never leaves and must not draw a seam), survivors are walked to a flatness tolerance under a shared bisection budget. This is why the painter does *not* over-extend and let the canvas clip, the way infinite lines do — a hyperbola runs off in two directions and there is no "far enough".
- **A real kernel bug, found by the first golden-sized circle.** `ConicMatrix.rank` compared `|det|` against `eps·‖A‖³`, which asks `σ₃ > eps·σ₁²/σ₂` — far stricter than the conditioning question it meant to ask, whenever the matrix is stretched. A circle lifted at centre (300, −120) with radius 45 has `ww ≈ 1e5` against a quadratic block of 1 and came back a **line pair**; the renderer would have drawn a straight stroke through it. Now `|det| > eps·‖A‖·‖adj‖`, with σ₂ asked before σ₃ so a double line's vanishing adjugate cannot let `det`'s noise read as rank 3. Past |centre| ≈ 1/√eps the wall is representational rather than a cutoff — **both sides are pinned**, because the second is what makes `ConicShape`'s balanced classification frame necessary rather than decorative (centre to the origin, blocks commensurate; only the answers come back, so the sweep and the clip still run on the caller's matrix).
- **Painter**: a second `GeoCircle` arm, taken only when the carrier has no centre and radius. The circle branch is untouched and all 26 pre-existing goldens are byte-identical. Flatness is half a screen pixel in world units, so the polyline is a screen-space budget — zooming out makes a conic cheaper, never denser. `CanvasViewport.visibleWorldBox` (new) is the clip bound: the four corners' world images, hence a superset under rotation, which is the right side to err on. `label_anchor` and `label_obstacles` came along — the two other `circle!` unwraps painting reaches — so a conic's label hangs from a deterministic point of its curve and a hyperbola contributes **two** obstacle chains, leaving the gap between its branches available to a label.
- **Hit-tester**: `ConicShape.distanceTo`. Degenerate conics answer exactly from their components; a curve is answered by a coarse sweep whose *every* local minimum is refined — the stationarity condition is quartic, so ≤ 4 stationary points and a scan an order finer cannot miss a basin, but its single best sample can sit in the wrong one where the parameter is stretched. Refinement is **golden-section, not the Newton step the checklist planned**: the bracket is already in hand, a bracketed search cannot leave it, and a tap has no performance pressure. Band selection gets `extremesAlong` (projective — the polar line of a direction's point at infinity), so only an ellipse can be contained and a rotated band measures it along its own axes.
- **Driving it a phase early.** Phase 120's `FivePointConic` is the first thing that will produce a non-circle conic, so tests drive both arms through a new `StubProjectiveConic` — a `GeoCircle` whose `isDefined` is `ConicShape.isDrawable` rather than "projects to a circle". Writing that shape down now is what makes Phase 120's object a drop-in.
- New goldens: a conics scene, light + dark, with one of every drawable class plus a circle-shaped conic that must still take the circle arm; both reviewed. Suite **2272 green**, 28 goldens, analyze clean, `flutter build web` compiles. Decisions pinned in PLAN §"A conic is drawn by its own parameterization, and clipped exactly".

**Next**
- Phase 120 — five-point conic: the `FivePointConic` object (`ConicMatrix.throughFivePoints` already exists), `ConicTool` as a 5-slot `MultiPointTool`, and the full shell checklist (toolbar row, shortcut, inspector, object-tree label, codec entries). It is also the first user of Phase 118's reserved homogeneous-param slot, so `requiredFormatVersion` must learn about it or documents carrying one get stamped v1 and misread.

**Gotchas**
- **Do not run `dart format` over a directory here.** The formatter in the current Flutter SDK is newer than whatever the repo was formatted with, and reformatted ~200 unrelated lines across eight canvas files. All of it was reverted and only the intended edits re-applied — but the CI gate is `analyze && test`, and neither notices, so the churn would have landed silently.
- `ConicMatrix.rank` is deliberately a property of *the matrix as written*, not of the conic. A caller with a geometric question balances first, as `ConicShape.of` does. Don't "fix" the wall at |centre| ≈ 1/√eps inside `rank` — there is genuinely no radius left in the representation there, and the test that pins rank 1 at (10⁶, 10⁶) says so.
- `ConicShape.isDrawable` is false for an `isolatedPoint` (two conjugate complex lines, e.g. `x² + y² = 0`). It has a real point but no curve, and a conic's ink is its curve — the painter and hit-tester both rely on that, and a conic kind's `isDefined` should be `isDrawable`, not "has a real point".
- Conic-valued kinds live under `GeoCircle` until Phase 121's convention unification renames it. `GeoCircle.isDefined` stays "projects to a circle" as the *default*, so no existing circle kind changes meaning; a conic kind overrides. Adding a `GeoConic` abstract kind now would have broken eleven exhaustive switches for no behaviour.
- `polylines` takes a world box, not a viewport, and the hit-tester never builds one — it measures to the whole curve, not to the visible ink. That is a deliberate divergence from the clipped-line and locus rules ("a tap on the invisible part misses"): an off-screen conic is unreachable anyway because the tap is on-screen, and threading a box through the tester would have bought nothing.
- The rank fix makes `rank` *more* willing to say 3. Only `isDegenerate` and tests consumed it before this phase, so nothing else moved — but `conic_intersection.dart` has its own cutoffs (`degenerateMemberEpsilon` and friends) that are unrelated and were not touched.

## Session 120 (V2 Session 22) — 2026-08-16

**Done**
- **Phase 118 (codec v2 + permanent v1 loader) complete** on `phase-118-codec-v2`, two commits, in that order deliberately: the corpus was pinned *before* the version constant moved, so the "v1 still loads" claim is measured against a baseline nothing had touched yet.
- **The corpus first.** Every document under `test/fixtures/` — the five real user files plus a new `v1/kitchen-sink-v1.json`, frozen from `buildKitchenSink()` through the Phase 117 encoder — must be v1, must load with every written object present and wired to the right parents, and must survive decode → encode → decode with identical geometry object for object (`geometryOf`, so positions, carriers, locus samples and rendered text all by value). The sweep is data-driven: dropping another user document into `test/fixtures/` enrols it with no test edit, and the version assertion is what stops a v2 file being added there and silently ending the coverage. The kitchen-sink file is the one member pinned against something outside itself — the live builder.
- **The stamp is a requirement, not a build number.** The obvious reading of the bump is that the encoder writes 2 on everything from now on — which locks a user's older build out of documents it could read perfectly, for nothing. `encodeDocument` now stamps `requiredFormatVersion(document)`: the lowest version that reads the document back *correctly*. Ordinary documents stay v1, byte-identical to what a v1 build wrote. **What earns a bump is misreading, not novelty** — the codec has added keys three times without one (viewport rotation, the display flags, the locus params) because a reader that skips them lands on exactly the defaults the file meant; a skipped `kernel` block instead draws the document in the wrong geometry. That distinction is the whole content of the version field, and it is now written down in PLAN and in CLAUDE.md's invariant, which previously said only "bump on any breaking schema change".
- **v1 needs no rewriting** — v2 only adds, so the migration *is* the defaults the new readers fall back to. Worth naming because it is the kind of claim that rots: `branchIndex` means the same thing in both files (a canonical-order **seed**, re-derived at every traced pass end since Phase 116 — a v1 file was written by a build that had no other notion), and an absent kernel block is the Euclidean geometry every pre-M-CK document is in. Both documented at the codec sites.
- **Hook 1 — per-file kernel flags (M-CK).** A top-level `kernel` block carrying the fundamental conic; `DocumentKernel` on `DecodedDocument`. `euclidean`/`hyperbolic`/`elliptic` are reserved *names* rather than free-form strings, and the two this build cannot honour are **refused with a message naming them**, not approximated — drawing a hyperbolic document in Euclidean geometry is precisely the failure the version stamp was bought to prevent, and it would be no less wrong for happening inside the build that understands the key. M-CK deletes that guard, not the parser. Omitted from the file while default, which is what keeps ordinary documents at v1.
- **Hook 2 — homogeneous params (Phase 120).** One settled wire shape for a `ProjPoint`, a `ProjLine`, or a conic's six independent entries: `{"h": [[re,im], …]}`, each component written as a pair even when the value is real, so nothing downstream ever has to guess whether a bare number was real. The map wrapper is what makes such a param self-identifying — to the version rule, and to a human reading the file. `encodeHomogeneousParam` / `homogeneousParam`, `FormatException` (never `TypeError`) on every malformed shape, tested at 3 and 6 components.
- `version > 2` still throws naming the newest understood; `version < 1` now throws too (the accepted range is explicit rather than one-sided).
- Suite **2177 green**, analyze clean, `flutter build web` compiles. One existing test changed premise — `encodeDocument stamps the current format version` became `stamps the lowest version that can read the document back`.

**Next**
- Merge `phase-118-codec-v2`; then Phase 119 — conic rendering + hit-testing (classify the conic, viewport-clipped parametric sampling reusing the locus polyline machinery, seeded-Newton conic distance, one golden per conic class × light/dark with circles pinned as regressions).

**Gotchas**
- **Don't "fix" the encoder to always stamp `constructionFormatVersion`.** It looks like an oversight and is the phase's main decision; the reason is in PLAN §"The version field is a requirement, not a build number" and in CLAUDE.md. The corollary is that adding a v2-only feature to a kind means teaching `requiredFormatVersion` about it, or documents carrying it will be stamped v1 and misread by v1 builds.
- The version rule keys off the *encoded* document, not the construction — `requiredFormatVersion` sniffs for the `kernel` key and for `{"h": …}` params. That is why the homogeneous shape is a wrapped map and not a bare list; a bare list would be indistinguishable from any other list-valued param.
- Nothing constructs a non-default `DocumentKernel` yet, so `saveConstructionFile` was deliberately left without a `kernel` parameter — there is no path by which a non-Euclidean document could be opened (decode refuses it) and then re-saved with its kernel dropped. M-CK threads it through file_io at the same time it makes the metric settable.
- `FundamentalConic.name` is a stored token, separate from the Dart identifier, so renaming the enum value cannot silently change the file format. The "every reserved metric name is distinct and stable" test is what holds that.
- The corpus test decodes and re-decodes documents carrying loci, so it pays two full traced sweeps per such fixture. Cheap today (the whole file is well under a second); if it ever isn't, split the round-trip check off rather than dropping fixtures.

## Session 119 (V2 Session 21) — 2026-08-15

**Done**
- **Phase 117c — field instrumentation**, on `phase-117c-trace-diagnostics`. The user re-tested after 117b: the locus *shape* is fixed, but both documents still "move very slowly and then hang" in Chrome — `locus-miss-2.json` after moving C, `apatitos-topos.rgl` after moving D. They asked for logs they could share.
- **The two triggers land where session 118's fuzz never looked.** In apat, **D is the locus driver** (a `PointOnObject`), so the gesture is a *slide* through `recomputeAlongParameterPath` — 118 dragged free points. In lm2, the only `IntersectionPoint` sits *inside* the locus chain, so it is excluded from drag seeding and the whole per-frame cost is the locus sweep. Re-probed both on those paths: apat sliding D a full turn in 720 frames is **0.5 ms mean / 8 ms worst, zero bails**; lm2 dragging C over a 41×41 grid of destinations (and measuring the frame *after* each move, which is the reported symptom) peaks at **13 ms**. Neither reproduces on the VM.
- So the phase is not a fix for a defect we can see — it is the instrument that says where the cost is on the reporter's machine. `TraceDiagnostics`: per-frame wall time, the locus sweep's share, and counters for trials, detours, folds, probes and **chain solves** (one recompute of the affected subgraph — the unit a slow frame is actually made of; trials are not the currency). Frames nest by depth, so `Locus.recompute` opens its own when nothing else has, and a sweep from a load, a command or an undo is recorded too.
- **The part that survives the symptom**: both walks call `checkpoint` from their inner loops, so a frame that overruns prints where it is and how far along, every second, *while it is still running*. A frame that never returns never ends, so nothing that only reports at frame end would ever have been seen.
- Armed in debug **and profile**. On the web those are different compilers — `flutter run -d chrome` is DDC, profile is optimized dart2js — and the perf gate puts optimized js at ~1.5× the VM on the very locus scenario in question. So "kernel or debug compiler?" is settled by running the same reproduction in both and diffing the numbers, which instrumentation confined to debug could not have asked.
- Surfaced two ways: the ⇧O trace overlay grew a cost line (ms · locus ms · chain solves · STALLED), and **Ctrl/⌘⇧O** opens a copyable report — totals, ten slowest frames, last forty — mirrored to the console.
- **Real waste found by the instrument, and removed.** The first armed run showed apat spending **410 of every frame's 742 chain solves inside collision measurement**: `locateSeparationMinimum` refined every confirmed collision to the floating-point floor, ~205 probes per crossing, twice a frame, forever. That precision exists to keep a tight *near-miss* from reading as a collision — but once a probe has been below `doubleRootEpsilon` the verdict is closed for good, and the parameter's only remaining job is centring an arc whose radius is a fraction of the same distance. The stopping rule now relaxes at that moment (`_collisionResolution`, 1e-4 relative): **742 → 442 solves/frame, 0.93 → 0.60 ms**, goldens bit-identical. A near-miss still pays the floor, since that is the case it was bought for.
- Suite **2103 green**, 26 goldens unchanged, analyze clean, `flutter build web` OK, perf gate PASS on all four targets.

- **The reporter's numbers came back the same session, and they close the question.** `locus-miss-2.json` dragging C in `flutter run -d chrome`: 138 frames, **median 106.7 ms, worst 178.3 ms, locus share 100%** — ~870 chain solves per frame at **~200 µs each**, entirely inside `Locus.recompute`, no painting in the frame at all. The VM does that same solve in **5.6 µs** and `dart2js -O4` in **8.3** (`benchmark/run_locus_docs.sh`, which inlines both documents and sweeps them on VM/AOT/js/wasm). **DDC is ~25× optimized dart2js on the kernel's complex arithmetic**, and that is the whole of this bug report: a 4 ms sweep rendered as a 178 ms frame, two per pointer event, which crawls and then wedges with nothing looping.
- Added so it cannot happen again: the benchmark above; a one-line startup notice in debug web builds naming `--profile`; and the finding pinned in PLAN.
- **Checked and rejected**: a coarse locus preview during drags. `locus-miss-2.json` is 504 solves at 128 samples and still **349 at 16** — the walk's step is adaptive and its folds belong to the curve, so the scan is only ~15% of a sweep. Would have traded real fidelity for ~30%. Measure before optimizing this.

- **Reporter confirmed in profile, and asked the right follow-up**: "how do we make this fixed under all circumstances?" Profile numbers: `locus-miss-2.json` dragging C is median **4.9 ms**, p90 7.6, worst 16.6 (predicted 4.2 from 8.3 µs × 504 solves); `apatitos-topos.rgl` sliding D is median **1.3 ms**. Nothing sticks. But nothing was *fixed* either — the compiler changed, the workload did not.
- **Phase 117d, the structural answer**: `LocusRefresh`. A locus is the only leaf whose recompute has no bounded cost, and it is a DAG leaf, so nothing anywhere can read a stale sample. During a drag preview it now re-sweeps on a duty cycle of its own measured cost (default: sit out one sweep's duration between sweeps). No wall-clock constant in the rule, so it self-tunes across machines, documents and compilers. The gesture's command runs *outside* the preview scope, so committed/undone/saved state is never stale — staleness lives and dies inside the gesture.
- Measured on `locus-miss-2.json`: at 60 Hz with a healthy sweep **299 of 300 frames still sweep** — no behaviour change for anyone whose document fits the budget. With frames arriving as fast as they are served (what a 25× slower environment looks like), mean frame cost goes **2.09 ms → 0.01 ms** and the locus coalesces instead of the gesture dying.

**Next** Then merge `phase-117b-tracing-degeneracy` and `phase-117c-trace-diagnostics`; then Phase 118 — codec v2 + permanent v1 loader.
- Open, not urgent: even at 8.3 µs/solve a heavy frame is ~7 ms of the 8 ms budget. 117d means that no longer takes the gesture down, but the headroom is still thin, and the honest lever is per-solve cost (allocation in the complex kernel), not the sweep's shape. Natural fit for Phase 122's performance hardening.
- Watch for: a locus can now be up to one sweep-duration stale if the user drags fast and then holds still, since no further frame arrives to catch it up. Invisible at profile speeds; if it ever shows, the fix is a catch-up sweep on pointer-idle, not a smaller duty cycle.

**Gotchas**
- **Neither document reproduces headlessly, and now we know why**: nothing was wrong with them. Two sessions went into hunting a defect that the build mode had manufactured. The lesson is procedural — when a report says "slow in Chrome", establish the build mode *before* forming a hypothesis, because `flutter run -d chrome` is DDC and no benchmark in this repo measures DDC (`run_tracing.sh` uses `dart2js -O4`).

- Diagnostics counters are recorded only inside a frame; `frameBegin`/`frameEnd` must stay paired in a `finally`. `checkpoint` outside a frame is a deliberate no-op, and `detail` closures are not built unless the frame has actually overrun — so the instrumentation costs a bool read and a counter bump on a normal frame.
- The relaxed collision-refinement rule means `SeparationMinimum.t` is now only accurate to ~1e-4 of the distance travelled *for confirmed collisions*. That is a documented contract with a test on it; anything that wants the old precision must ask for a near-miss-grade search, not assume it.

## Session 118 (V2 Session 20) — 2026-08-15

**Done**
- **Phase 117b complete** on `phase-117b-tracing-degeneracy`, opened from two user documents: dragging a free point in `apatitos-topos.rgl` froze the app in Chrome, and its locus drew the wrong sheet over a third of the sweep. `locus-miss-2.json` was reported alongside but does not reproduce a freeze here — see gotchas.
- **The freeze, root-caused**: `G = TangentLine ∩ the circle it touches` is a double root *by construction* — measured chordal separation 9.4e-17.
