# Dynamic Geometry App in Flutter

## Context

Build a cross-platform (web, Android, iOS) dynamic geometry application from scratch in an empty repo. The app is a constructive geometry tool: the user drops free points and builds derived objects (lines, circles, intersections, midpoints, triangle centers, …) on top of them. Dragging a free point must propagate updates to every dependent object correctly and instantly. The project will live in `$HOME/Code/var/regula/`.

Decisions confirmed up front:

- **State management:** Riverpod.
- **Persistence:** Local JSON files only (via `file_picker` — works on web via download/upload, on mobile via the native picker).
- **Undo/redo:** Full Command-pattern undo/redo.
- **Testing:** Unit + property-based + widget + golden tests.

The fundamental abstraction is a **construction graph**: a DAG of geometric objects where every derived object is a pure function of its parents. Free points are the only mutable roots. The same graph powers rendering, hit testing, undo/redo, and save/load.

## Architecture

### Layer separation

```
lib/
├── domain/          # Pure Dart, no Flutter imports — fully unit-testable
│   ├── math/        # Vec2, line/circle primitives, intersections, predicates
│   ├── construction/# GeoObject hierarchy + Construction (the DAG)
│   ├── tools/       # Tool state machines
│   └── commands/    # Undo/redo command interface + concrete commands
├── application/     # Riverpod providers, controllers, persistence I/O
│   ├── providers/
│   └── persistence/
├── presentation/    # Flutter widgets, painters, theme
│   ├── canvas/
│   ├── panels/      # toolbar, tool palette, attributes inspector, object tree
│   └── theme/
└── main.dart
```

The `domain/` layer must not import `package:flutter/*`. This is the boundary that makes the math testable without a widget tester and reusable across platforms.

### Construction graph (`domain/construction/`)

- `sealed class GeoObject` with `id`, `parents`, `attributes: ObjectAttributes`, and `void recompute()`. Sealing is at the *kind* level: `GeoPoint` / `GeoLine` / `GeoCircle` / `GeoAngle` are the sealed branches, concrete objects extend an open kind — Dart requires a sealed class's direct subtypes in the same library, which one-file-per-object rules out on the root. Kind switches are exhaustive; concrete-type switches are not.
- Kinds are *value shapes*, not visual shapes. A kind's geometry accessor is what intersection math and hit testing consume: `GeoPoint.position`, `GeoLine.line` (carrier `LineEq` — segments and rays reuse line∩x math through it, with extent clamps at the painter/hit-tester), `GeoCircle.circle` (carrier `CircleEq` — arcs and sectors reuse circle∩x math the same way, with *angular* extent clamps), `GeoAngle.angle` (an `AngleGeometry`: vertex, unit start direction, CCW sweep in [0, 2π) — angles are decorations plus a measure; nothing intersects them). Phases 37–39 add three more kinds that likewise take part in no intersection math: `GeoPolygon.polygonVertices` (the filled region's vertex loop), `GeoMeasurement.value`/`anchor` (a live number displayed as canvas text), and `GeoLocus.samples` (a sampled trace polyline; null entries mark gaps where the traced point was undefined). Phase 58 adds an eighth kind, `GeoText.renderedText`/`anchor` — user text at a fixed world position whose `{…}` slots evaluate live (see **Texts** below). Every new kind must add its case to the exhaustive kind switches: painter `_drawObject`/`_drawFill`, hit tester (priority / band containment / distance), `label_anchor`, `labelText` (label_layout), declutter scene builder (label_obstacles), `fit_viewport`, `object_naming`, tree grouping, `object_kind_label`, codec.
- `parents` is a getter derived from typed parent fields (e.g. `Midpoint` holds `GeoPoint point1, point2`), so ill-typed constructions are unrepresentable rather than runtime errors.
- Derived objects support an *undefined* state (degenerate parent configuration — coincident points defining a line, curves that stopped intersecting mid-drag). Undefined objects stay in the graph, are skipped by painter/hit-tester, and recover when the degeneracy passes.
- Subclasses (one file each, grouped by kind):
  - **Points:** `FreePoint`, `PointOnObject` (constrained to a curve), `IntersectionPoint`, `Midpoint`, `Centroid`, `Orthocenter`, `Incenter`, `Circumcenter`, `SegmentRatioPoint`, and the four transformations (Phase 15): `ReflectedPoint` (about a line), `CentralReflectionPoint` (about a point), `RotatedPoint` (about a center by a fixed angle in radians, CCW), `TranslatedPoint` (by the live vector between two points) — ordinary derived points, so recompute, persistence and hit testing work unchanged. Phase 65 adds three more: `ProjectionPoint` (point + line parents; the foot of the perpendicular via `LineEq.project`; undefined while a parent is; tool = `PointAndLineTool` with a `buildProjectionPoint` tear-off on `G F` — the one `PointAndLineTool` that builds a point, so the toolbar's Points/Lines group highlight splits on the builder), `HomotheticPoint` (point + center parents, scalar finite `ratio` baked at creation like `RotatedPoint.angle`, constructor-rejected otherwise; not an isometry, so excluded from `TransformKind` curve mode v1; ratio input settled as the numeric dialog — the segment-ratio precedent: dialog-first closure over `TwoPointTool`, tap order point then center per the transformee-first convention, `G H`; Phase 68 promotes it into the Transform group as the dilate transform's image-point kind and retires that Points-flyout wiring — see the Phase 68 bullet), and `HarmonicConjugatePoint` (three collinear point parents A, B, C → the fourth harmonic with cross-ratio (A,B;C,D) = −1; undefined while non-collinear, the base pair coincident, or C the midpoint of AB). Its `HarmonicConjugateTool` (`G 4`) is a dedicated `MultiPointTool` whose dedupe is **structural** (an existing conjugate over identical parent instances, either base-pair order — the conjugate is symmetric in A and B) rather than numeric: `dedupedDerivedPoint`'s random probes can never confirm this object, because perturbed parents stop being collinear and the candidate goes undefined — `MultiPointTool.constructionObjects` exposes the search space for such structural dedupes.
  - **Lines:** `LineThroughTwoPoints`, `Segment`, `Ray`, `PerpendicularLine`, `ParallelLine`, `AngleBisectorLine`, `TwoLineBisectorLine` *(Phase 29b: two `GeoLine` parents plus a `branch` param 0/1 — two lines have two bisectors, a perpendicular pair through their intersection; the branch is baked at creation from the two tap positions, picking the bisector of the tapped wedge — direction `d̂1 + s·d̂2` with `s = +1` for branch 0, `−1` for branch 1; undefined while the carriers are parallel or a parent is undefined, recovers)*, plus (Phase 33): `PerpendicularBisectorLine` (two point parents; carrier through their midpoint, perpendicular to the join — a dedicated kind on the `AngleBisectorLine` precedent rather than a hidden Midpoint + PerpendicularLine macro, single-valued and continuous; undefined while the points coincide) and `TangentLine` (point + circle parents plus a `branch` param 0/1; both branches go undefined together while the point is strictly inside the circle and recover with sides preserved — the branch order is left/right of the center→point line, see `tangents.dart`; on the circle both branches collapse to the tangent at the point; the carrier is built point-direction through the tangent point perpendicular to the radius, which stays well-conditioned near the rim where a through-points form would degenerate). Phase 67 adds `RadicalAxisLine` (two `GeoCircle` parents; the locus of equal power to both circles; undefined while the circles are concentric). Its `RadicalAxisTool` (`G X`) is the first "click two circles" tool — `PointAndLineTool`'s slot collection with `IntersectionTool`'s curve-tap rules (hit-only, everything but a circle ignored), plus a structural dedupe: an existing axis over the identical circle instances, either order (the axis is symmetric), refuses the completing tap. Kept a dedicated class rather than a builder-parameterized base until a second two-circle consumer exists. Phase 71 adds `PolarLine` (point + circle parents; the polar of the pole P — the line `(P − c)·(X − c) = r²`, perpendicular to the center→pole join at the inverse point; through the pole's tangent points when P is outside, the tangent at P when P is on the circle, and still defined inside; undefined only while P sits on the center, where every direction is equally 'perpendicular'). Its `PolarLineTool` (`G ⇧ P` — `G P` stays reflect-about-point) rides `TangentTool`'s two-slot collection (point + circle in either order, circle-flavored taps consumed before the point ladder) but commits a single line, with `RadicalAxisTool`'s structural dedupe: an existing polar over the identical point + circle instances refuses the completing tap. The Lines flyout row sits directly below Tangents and above Radical axis, keeping the two point-and-circle tools adjacent ahead of the two-circle tool.
  - **Circles & arcs:** `CircleCenterPoint`, `ThreePointCircle`, `CompassCircle` (two points defining radius + center), `Arc` (through three points: endpoints first and last, the arc is the carrier branch containing the middle point; undefined while collinear), `Sector` (center + rim point fixing radius and start angle + a third point fixing only the end angle; sweep is CCW from start to end), and (Phase 34) `FixedRadiusCircle` (center parent + a numeric `radius` param; constructor rejects non-positive/non-finite — serves the circle-by-radius tool directly and doubles as the segment-by-length macro's hidden circle). Phase 66 adds two triangle circles on the `ThreePointCircle` model (three `GeoPoint` parents, undefined while collinear/coincident): `NinePointCircle` (center = midpoint of circumcenter & orthocenter, radius = circumradius/2) and `InscribedCircle` (center = incenter, radius = its distance to a side). Phase 67 adds `ApolloniusCircle` (parents A, B + a third point C supplying the ratio `|CA|/|CB|` — click-only, the circle passes through C; undefined while C is equidistant from A and B or points coincide). It rides `ThreePointTool` via a `buildApolloniusCircle` tear-off (`G ⇧ A` — `G A` stays the arc), and, having all-`GeoPoint` parents, joins the Phase 24 transform whitelists like the Phase 66 circles: distance *ratios* survive any similarity, so the rebuilt image is the transformed circle. Phase 70 adds `DiameterCircle` (two `GeoPoint` parents — the endpoints of a diameter: center at their midpoint, radius half their distance; the Thales circle over the two points, and the enabler of the classic semicircle constructions — right angle on the diameter, geometric mean via the altitude). Coincident endpoints give a zero-radius circle like `CircleCenterPoint`, so it survives a drag through the degeneracy. It rides `TwoPointTool` via a `buildDiameterCircle` tear-off (`G 2` — pairs with `G 3`'s three-point circle) and joins the transform whitelists per the all-`GeoPoint`-parents rule (a diameter maps to a diameter under any similarity).
  - **Angles:** `VertexAngle` (arm–vertex–arm points; sweep is CCW from the first arm's ray to the second's, so the two tap orders give the two complementary markers) and `LineAngle` (between two lines; vertex at the intersection, undefined while parallel). `LineAngle` originally always folded to the acute/right angle in (0, π/2]; from Phase 31 the marked wedge **follows the taps**: each tap picks the half of its line nearer the tap, giving half-directions d1′/d2′, and the wedge between rays(d1′, d2′) has sweep in (0, π) (start = whichever direction makes the CCW sweep < π) — so tapping with the obtuse pair between the taps yields the obtuse marker, and the right-angle square lands in the chosen quadrant instead of under the lines. The choice persists as two **sign flips relative to the canonical carrier directions** (baked at creation from the tap positions, so the wedge follows drags continuously; codec `params`, additive, no version bump). **Absent params = legacy always-acute mode**, so old saves decode and render byte-identically.
  - **Polygons (Phase 37):** `Polygon` — the first variable-arity object: `final List<GeoPoint> vertices` (≥ 3, constructor-enforced; the list is fixed for the object's lifetime, and `parents => vertices` keeps the typed-parents rule intact). Undefined when any vertex is; collinear/self-intersecting stays *defined* (it's a drawable outline — area math handles it in Phase 38). Draws its own closed outline and fill, deliberately emitting **no Segment edges**: the shape *macros* stay segment-based editable compositions, while `Polygon` is a single first-class region — which avoids N redundant objects per polygon and makes Phase 38's area target unambiguous. Migrating the macros onto `GeoPolygon` is explicitly out of scope. The tool bakes `fillAlpha: 0.25` into the created object (the attribute *default* stays null, so nothing else changes).
  - **Measurements (Phase 38):** `DistanceMeasurement` (two point parents; value = their distance, anchor = the midpoint; point–line distance deferred v1) and `AreaMeasurement` (a single `GeoObject subject` parent, constructor-enforced `GeoPolygon` or `GeoCircle` — the `PointOnObject.curve` precedent, so ill-typed saves normalize to `FormatException`; value = |shoelace signed area| or πr², anchor = vertex average / circle center). Measurements render as text only, riding the label machinery (see Canvas), so text dragging, `labelFontSize` presets and color styling come free. Phase 73 adds `SlopeMeasurement` (GeoGebra's Slope; one `GeoLine` parent of any concrete kind — the carrier abstraction makes segments, rays and derived lines measurable alike): value = the carrier's rise/run (`direction.y / direction.x`), undefined for vertical lines like every other degenerate measurement; anchor derived from the subject's `parameterExtent` (segment midpoint, ray origin, closest-to-origin carrier point for infinite lines — the `labelAnchor` conventions, computed in the domain so the object stays presentation-free). Slope is dimensionless, so it formats through the generic measurement arm (2 decimals default, `valueDecimals` overridable). Intended for quickly checking parallelism at a glance.
  - **Loci (Phase 39):** `Locus` — parents `PointOnObject driver` + `GeoPoint traced` (the constructor validates by a pure parent-graph walk that `traced` transitively depends on `driver`); params `sampleCount` (default 128) plus, for line hosts, `center`/`halfSpan`. **Recompute is sweep-and-restore** over a `_chain` computed once at construction (the transitive ancestors of `traced` that themselves depend on `driver`, plus both endpoints, topologically ordered by post-order DFS over parent links): save `driver.parameter`, for each sample set it, recompute the chain in order, record `traced.position`; then restore the saved parameter and recompute the chain once. This is safe against every invariant: `GeoObject.recompute` never notifies (`Construction`'s single notification fires after the whole topological pass the locus runs inside), the restore is bit-exact because chain members are pure functions of parents + parameter, the locus sits after its ancestors in topological order so the chain has already settled before being perturbed, and a chain can never contain another locus (`PointOnObject` rejects non-line/circle hosts). A pleasing consequence: *sliding the driver does not change the locus* — the sweep domain is fixed. Sampling domain: circle host = one full closed turn; line host = `[center − halfSpan, center + halfSpan]` **baked at creation** (center = the driver's parameter, halfSpan = the visible world width via the additive `ToolInput.viewExtent`, fallback 100) — the locus sibling of `PointOnObject`'s analytic-parameter caveat. 128 uniform samples, no adaptivity v1; undefined samples become nulls → gaps in the polyline. Perf note: a drag frame costs sampleCount × chain-length recomputes — fine for realistic chains, revisit if manual testing disagrees. *(Phase 39b, user feedback on 39 — "manual testing disagreed" in two documents:)* the uniform sweep is now post-processed into **components**. (1) *Circle-host runs are cyclic*: defined runs are grouped after rotating the sample array to start at a gap, so a run straddling the 0/2π wrap is one stroke, not two split at an invisible seam (the reported "small hole"). (2) *Boundary refinement*: each defined↔undefined transition is located by parameter bisection and the run gets extra samples geometrically clustered toward the boundary — near a tangency the traced point moves like √ε per parameter step, so uniform sampling visibly truncated the curve (~1 uniform step of parameter ≈ a large arc of trace). (3) *Linkage continuation*, the Cinderella-inspired part done with real arithmetic and scoped strictly to the sweep: when the undefined boundary is caused by a chain `IntersectionPoint` whose two candidates coalesce (candidate count 2 → 0, i.e. a tangency), the sweep *reverses direction and flips that intersection's branch* — the physical linkage swinging through its aligned position — and keeps walking until the branch assignment returns to the original at the starting end (→ closed component, first sample repeated to close the polyline) or an open end / non-flip boundary / sample budget stops it (→ open component). This buys the full figure-eight-style loci *without* path-dependent semantics leaking anywhere: dragging keeps the deterministic persisted branch, saves are unchanged, and the restore contract extends to branch indices — `IntersectionPoint.branchIndex` is mutable now, with the same "mutated only inside a sweep, always restored before recompute returns" contract as `driver.parameter` (safe for loci sharing chain members: each locus restores before the next recomputes). Non-generic cases (a mid-walk undefined sample under a flipped assignment, walks that keep flipping) truncate to an open component after a fixed segment budget — never wrong ink, at worst shorter than ideal. *(Phase 39c, user feedback on 39b:)* flipped sheets are kept **only when the walk closes** — returns to the original branch assignment at its starting end with matching geometry — because a closed continuation is a genuine closed curve of the mechanism (the figure-eight, the full circle), while an *open* walk that ends still-flipped dangles into positions the app's deterministic-branch dragging can never reach, which reads as phantom curves (the doc-1 report: mirror strokes plus dives through a degenerate limit point). A non-closing walk trims back to the last sample taken under the original assignment, so such a locus is exactly the branch-fixed trace with refined boundaries. Closure is checked **geometrically as well as combinatorially** (parity back to original *and* the trace's end within a small fraction of its extent from its start): flipping the culprit can in principle swap a *downstream* intersection's deterministic candidate ordering (doc 1's mirrored bisector reverses the along-line order), and a closed-parity walk whose downstream members landed on the wrong sheet misses the join — the guard demotes it to open, which trims it to the branch-fixed trace. Never wrong ink; continuity-tracking downstream members to *keep* such walks closed is deliberately deferred until a real construction needs it. *(Phase 39d, user feedback on 39c — doc 1 still grew diagonal spikes:)* at a tangency boundary the parameter refined toward is the edge of the culprit's **two-candidate region** (the true discriminant-zero point), not the defined↔undefined edge the plain bisection finds. Between the two lies the intersection math's epsilon-*tolerance* zone, where a fabricated tangent position stands in for two roots that have already gone complex; on the coalescing point itself the stand-in is the coalescence limit (harmless — the figure-eight's crossing), but a *downstream* member can amplify it arbitrarily — doc 1's bisector degenerates there (its vertex ray F−D shrinks to zero) and threw the traced point onto A/B, drawn as a long phantom diagonal off each stroke's end. The true limit is finite and the refined ladder now converges to it (in doc 1 the bisector's limit direction is 45° to AB, G → A + (AD̂ ± perp)·|AB|/2 — verified analytically and by probe). The two user documents live verbatim in `test/fixtures/` with a codec-to-samples regression test (`locus_fixture_regression_test.dart`); `tool/locus_render.dart` renders any document's locus to SVG for eyeballing. *(Phase 39e, user feedback on 39d — doc 1's strokes stop visibly short of the line through A ⊥ AB:)* the trace has a **finite limit at driver-infinity** (as D → ±∞ the Thales circle over AD converges to the perpendicular through A, so G → A ± perp·|AB|/2 like 1/t), and Cinderella's projective driver draws the stroke touching it — a finite sweep window cannot (at doc 1's window the gap is |AB|²/(4·t_edge) ≈ 11 world units). Fix: a line-host run ending at the **window edge** (an open end, not a boundary) gains an **infinity tail** — parameters at geometrically doubling distances from the edge (starting at 2·halfSpan so the driver's distance-from-figure roughly doubles every rung, capped at 10⁹ world units), kept **all-or-nothing**: accepted only if the traced point stays defined the whole way *and* every position increment decays (each ≤ 0.95 × the previous — algebraic convergence like t^−p gives ratio 2^−p, while divergence, even logarithmic, gives ratio ≥ 1). Any rejection keeps today's exact window cut: no ink ever leaks past the window for diverging traces (the midpoint chevrons), nor into a defined region just beyond the edge (the U-curve). The ladder stops early — converged, tail accepted — once an increment falls below 10⁻⁶ of the trace's extent (the remaining gap to the limit is the same order, far subpixel). The stop is also a correctness matter, pinned by the scaled unit fixture before the fix: deep in the ladder the traced position's double-precision noise (~parameter × ε) overtakes the shrinking true increments — at figure scale ~3 the position visibly quantizes near t ≈ 10⁸ — and one noise uptick flaps the decay test, rejecting a genuinely converging tail; convergence is reached long before that regime. The doubling ladder makes chord faceting decay with the increments; if a real document ever shows a visibly curved tail, densify to ×√2 rungs (decay threshold still separates: 1/t → 0.71, log-divergence → 1). Fully-defined line-host sweeps now also route through the run walk so their two open ends get tails (the uniform-list early return stays circle-host-only — the goldens' byte-exactness contract); a no-tail line sweep emits the identical uniform list, at one extra sweep of eval cost. *(Phase 39f, user feedback on 39e — a parabola locus, `locus3.json`, "also stops early before infinity":)* the trace *diverges* at driver-infinity, so no finite tail can complete it — the defect is the bounded window itself, the third report against it. Line hosts now sweep **projectively**, Cinderella's driver semantics: the uniform grid maps through `t = center + halfSpan·tan(φ)`, φ cell-centered uniform over (−π/2, π/2) — strictly monotone, symmetric, covering the *entire carrier* (outermost samples ≈ ±halfSpan·(2n/π) ≈ 80 view-widths out at n = 128). `center`/`halfSpan` keep their persisted values and meaning but become the sweep's **focus** rather than a cut: half the samples land within |t − center| ≤ halfSpan (⇔ |φ| ≤ π/4), density falling hyperbolically toward infinity. Diverging arms (the parabola) thus run out far past any reasonable zoom, and converging ends land within ~focus/80 of their limit before the 39e infinity tail closes the rest (its rung ladder now starts at max(2·halfSpan, |edge − center|) so the driver's distance from the focus doubles per rung — starting at 2·halfSpan from an ≈80·halfSpan edge would make early increments *grow* and spuriously trip the decay rejection). No codec change: params reinterpreted, old documents just stop truncating. Window-*cut* semantics are gone — a sweep boundary no longer ends a run mid-geometry (the 39c cut-window U-curve fixture now closes into the full circle and is re-pinned as the projective-coverage pin; open-walk trimming stays pinned by the doc-1-shaped fixture, whose walks end at the infinity edges). Because line-host `samples` can now reach astronomically far positions, `GeoLocus` gains **`coreSamples`** — the defined uniform positions traced from the focus window, default (and circle hosts) = all defined samples — consumed by viewport **fit** and **label anchoring** (fit on the parabola document stays at figure scale instead of 10³× out; the label anchors near the creation view; `tool/locus_render.dart` frames on core bounds too). Band selection deliberately keeps whole-`samples` containment: a diverging locus is line-like, and like lines it never band-selects. In-focus uniform density is ~0.64× the old window density (tan′ spreads the grid); boundary ladders unchanged — bump the default `sampleCount` only if a real document shows faceting. Consequences: `samples` is no longer aligned to the uniform parameter grid and its length varies (nothing consumed the grid; `sampleCount` is the uniform resolution), and a fully-defined full-turn circle-host locus still emits exactly the old uniform gapless list, so the painter's close-the-loop rule and existing goldens are untouched.
  - **Texts (Phase 58):** `ExpressionText` — the combined text & calculation object: user `content` placed at a fixed world `anchor` (the placing tap; serialized as `x`/`y` params), where `{…}` slots hold live expressions over the construction (`perimeter = {dist(A,B)+dist(B,C)+dist(C,A)} cm`). Parents are the referenced objects, bound **by name once at creation** (dialog-OK) and re-bound on load by zipping the template's `referenceNames` (unique, first-occurrence order — deterministic) with the decoded parent ids — so renames never break evaluation; the stored source string does go stale after a rename (accepted v1 — the edit dialog shows the old name and re-resolves on OK). `recompute()` renders the template: each slot substitutes `formatComputedValue` (domain-side — the string is built in recompute, where presentation's `measure_format.dart` is unreachable; fixed 2 dp until Phase 72, now the text's `valueDecimals` with 2 as the null default, re-rendered by the `setAttributes` carve-out) or `?` when its expression is undefined; the text object itself **stays defined** whatever its references do (user-authored content must not vanish; `isDefined` is false only in unreachable states). Texts render as text only, riding the label machinery like measurements. Texts are **not referenceable** from other texts v1 (the binder rejects `GeoText` targets), which keeps two things trivially true: nothing ever depends on a text, so *editing* is `MacroCommand([DeleteObjectsCommand([old]), AddObjectCommand(replacement, same id + attributes)])` — no re-parent primitive exists, and delete + re-add with existing tested commands is exactly "replace with rewired dependents" in one undo step — and cascades from a text's deletion are always just the text. Body dragging moves the text's own **anchor** (`_TextAnchorDragSession` → one `MoveTextAnchorCommand` per gesture, via `Construction.moveTextAnchor` — free placement, no radial clamp, no grid snap: a text is annotation, not geometry) and never the referenced free points, which a rigid translate would have dragged along (*follow-up in-session, user feedback: the initial label-drag-only repositioning felt broken — its 40 px caption clamp is wrong for an object whose body is its label; the canvas label-drag loop now routes GeoText grabs to the body drag*). `labelDx`/`labelDy` still exist but are baked to 0 at creation and no longer user-draggable on texts.
- `class Construction` owns the DAG: insertion-ordered map of objects (insertion order doubles as topological order), topological recompute on dirty propagation, dependents lookup for cascading delete. It is pure Dart with a minimal hand-rolled listener API — *not* a Flutter `ChangeNotifier` (the domain layer must not import Flutter, and `ChangeNotifierProvider` is the legacy path in Riverpod 3 anyway). The application layer wraps it in a `@riverpod` `Notifier` that re-exposes state after each command. If that notifier ends up being the only listener by Phase 4, drop the listener API.
- `class ObjectAttributes`: `name`, `colorArgb` (raw ARGB int, `null` = theme default — the domain layer can't use Flutter's `Color`; presentation maps it), `visible`, `labelVisible`, `labelDx`/`labelDy` (label offset from the object's anchor in *screen* logical px so zoom never flings labels; defaults 6/−18 match the pre-Phase-17 hardcoded offset), `strokeWidth`, `dashPeriod` (0 = solid, > 0 = dashed with that period in logical px, dash = gap = period/2), `angleMarkerRadius` *(Phase 22 — angle-marker radius in screen px, default 20 = the pre-22 painter constant)*, `labelFontSize` *(Phase 28 — label size in logical px, default 12 = the pre-28 `label_layout.dart` constant; read by both `_drawLabel` and the shared `labelScreenRect` so paint and hit rect can't drift)*, `showValue` *(Phase 35 — default false; a segment appends its length and an angle its degree measure to its label; independent of `labelVisible`, which gates only the name part — composition rules under Canvas)*, `lineClip` *(Phase 44 — Cinderella-style line display extent, int-coded: 0 = infinite (default); 1 = clipped to the segment between the two defining points (`LineThroughTwoPoints` only — the one kind whose defining points both lie on the carrier); 2 = clipped to the span of the **points incident to the line** — the outermost of its on-carrier defining points, `PointOnObject`s hosted on it, and `IntersectionPoint`s having it as a parent — so a later-created point beyond the defining pair extends the drawn extent, and the mode works for `PerpendicularLine`/`ParallelLine`/`AngleBisectorLine`/`TwoLineBisectorLine` too, whose defining points aren't (all) on the carrier. Mode 2 also applies to `Ray`: the origin end stays fixed and the far end clamps at the outermost incident point ahead of the origin (incident points behind the origin are ignored; none ahead → drawn unclipped). Incidence is *structural* (construction ties, not epsilon tests) and counts **visible** points only, so hidden macro scaffolding never stretches the clip; fewer than 2 distinct incident points on a line → drawn infinite until enough exist. *(Phase 44b, user feedback on 44:)* structural incidence also includes **derived incidences** — points provably on the carrier by a construction theorem over parent ties, still zero epsilon: the `IntersectionPoint` of exactly a `TwoLineBisectorLine`'s two parent lines (either parent order; every bisector branch passes through the crossing) and the `Midpoint` of exactly a `PerpendicularBisectorLine`'s two parent points. The list is deliberately short v1 — other true theorems (`SegmentRatioPoint`/`Midpoint` of a `LineThroughTwoPoints`' defining pair, `Incenter` on an `AngleBisectorLine` over the same triple) can join when a real construction wants them. A point merely *coinciding* with a carrier by theorem-of-the-figure (e.g. a tangent that provably overlaps another line, as in the provoleas fixture) is **not** incident — that is exactly the epsilon test this design rejects; create the tangency point (intersect the tangent with its circle) to clip such a line. **Display + hit-test only**: the carrier stays infinite for construction semantics — intersections, perpendiculars and `PointOnObject` parameters are unaffected; clipping is style, not geometry. `Segment` is untouched — it is already its own clip)*, `valueDecimals` *(Phase 72 — decimal digits (0–5) for the label's value part; `null` (default) = kind default: 2 for lengths/areas, 1 for angles)*, plus per-type extras (point size, fill alpha — `fillAlpha` applies to sectors *and*, from Phase 22, to angle-marker wedges). Built with `freezed` for immutability + `copyWith`. All attribute fields are additive with defaults, so new ones need no save-format version bump.
- **Automatic naming (Phase 23).** New objects get an auto-name at creation: points `A…Z, A1…`; lines *and circles* share one lowercase pool `a…z, a1…`; angles `α…ω, α1…`. The allocator is a pure domain function (`domain/construction/object_naming.dart`, `nextAutoName(usedNames, object)`) doing a first-free scan over the names already in the construction — so deleted names are reused, File > Open just works (the scan sees whatever the file brought), and nothing keys off ids (uuid.v4 has no order). It runs in a single interceptor in `ToolNotifier.handleInput` — the one funnel every `AddObjectCommand` passes through — recursing into `MacroCommand.commands` and naming only objects with an empty name **and** `visible: true` (macro scaffolding is invisible, so it burns no letters). Because `AddObjectCommand` holds the object instance and redo re-adds it, a name baked in before the first apply is undo/redo-stable with no extra command state. Display convention: points and angles keep `labelVisible: true` (canvases show A, B, C by default); lines and circles are named but get `labelVisible: false` at assignment — the name shows in the tree/inspector, not on the canvas, until the user reveals it. Manual renames stay free-form; the allocator just skips whatever exists — except clashes (Phase 27): renaming to a taken name evicts the old holder to a numbered variant (pure helper beside `nextAutoName`), both renames in one multi-id `ChangeAttributesCommand` (the command already batches ids — no `MacroCommand` needed), so names stay unique without ever rejecting the user's chosen name. Phases 37–39: polygons, measurements and loci join the lowercase line/circle pool; polygons and loci get `labelVisible: false` at assignment like the other curves, while **measurements keep `labelVisible: true`** — their whole point is the on-canvas text, which reads best as `a = 3.42`. Phase 58: texts join the same lowercase pool but get `labelVisible: false` at assignment — a text's rendered *content* is its whole on-canvas presence, and `labelText` never composes `name = content` for texts (user prose can itself contain `=`, so the prefix would read as a bogus equation chain); a text's name lives in the tree and inspector only, and the inspector hides the show-label toggle (plus the stroke-width/line-style rows — pure label text, like measurements) on text selections.

### Pure math (`domain/math/`)

- `Vec2` with the usual ops, `dot`, `cross`, `norm`, `distanceTo`.
- `LineEq` / `CircleEq` value types for analytic forms. *(Phase 67 adds circle-relation helpers in `circle_relations.dart`, the `harmonic.dart`/`tangents.dart` precedent:)* `radicalAxis(CircleEq, CircleEq) → LineEq?` (null for concentric) and `apolloniusCircle(a, b, ratio) → CircleEq?` (null at ratio 1, where the locus degenerates to the perpendicular bisector; also null for non-positive or non-finite ratios) — property-tested (equal power on the axis; the distance ratio on the circle).
- `intersections.dart`: line∩line, line∩circle, circle∩circle returning `List<Vec2>` (0/1/2). Each intersection object carries an `index` so the user's chosen branch is stable across drags.
- Caveat: the index is *deterministic*, not *continuous*. Line∩circle branches are ordered along the line's direction, so dragging a defining point past the other reverses the direction and the two branches visibly swap. Known wart, not a bug. If it bothers in Phase 5/6 manual testing, layer a runtime continuity heuristic (prefer the candidate nearest the previous position) on top — but the *persisted* branch stays the index; continuity is path-dependent and must never leak into the save format.
- `triangle_centers.dart`: closed-form centroid, orthocenter, incenter, circumcenter. *(Phase 66 adds)* `circumradius` and the inradius (distance from the incenter to a side) — the nine-point circle is then midpoint(circumcenter, orthocenter) with radius `circumradius / 2`.
- `angle_geometry.dart`: `AngleGeometry` value type (vertex, unit start direction, CCW sweep) plus angle helpers — `ccwSweep(from, to)` in [0, 2π), and the arc-branch pick `sweepThrough(start, via, end)` (signed sweep from start to end passing via; feeds `Arc`).
- `tangents.dart` *(Phase 33)*: `tangentPointsToCircle(external, circle)` → 0/1/2 tangent points, built as the Thales circle over center–external ∩ the given circle (reusing `intersectCircleCircle`). That choice buys branch stability for free: the branch order is left/right of the directed center→point line, which is continuous under any drag of the external point — none of the line∩circle direction-reversal wart. On-circle → the point itself; strictly inside or degenerate radius → empty.
- `expression.dart` *(Phase 58)*: the text tool's expression engine (full user-facing function/operator reference: `docs/EXPRESSIONS.md`) — tokenizer + recursive-descent parser + evaluator, pure numeric, zero construction imports. Sealed `Expr` AST (number / name / unary minus / binary `+ − * / ^` / call); precedence `+ −` < `* /` < unary minus < `^` (right-assoc, so `-2^2 = −4`); parsing throws only `ExpressionFormatException` (a `FormatException` with an offset). Evaluation **never throws**: unknown names, kind/arity mismatches, division by zero, NaN/±∞ all yield null, which renders as `?`. Numeric functions are a table-driven registry (sqrt, sin, cos, tan, asin, acos, atan, abs, round, floor, ceil, min, max — one-line additions later; integrals/CAS explicitly deferred). Trig works in **degrees**, composing with `angle()` which also reports degrees. Constants `pi`/`e` resolve before object names — the lowercase auto-pool contains `e`, so bare `e` is Euler's number while accessor arguments are always object names (`len(e)` is the object). Geometry binding stays out of `math/`: `construction/text_template.dart` (brace splitting into literal/expression segments, `referenceNames`) and `construction/text_evaluator.dart` (`GeoObjectEnv` — accessors `dist`/`len`/`angle`/`area`/`radius`/`perimeter`/`x`/`y` plus bare-name sugar: segment → length, measurement → value, angle → degrees).
- `polygon_math.dart` *(Phase 38)*: `polygonSignedArea(List<Vec2>)` — shoelace, positive CCW. Consumers take the absolute value; a self-intersecting loop gets the shoelace absolute value (documented, GeoGebra-compatible enough).
- `harmonic.dart` *(Phase 65)*: `harmonicConjugate(a, b, c) → Vec2?` — the fourth harmonic point D with cross-ratio (A,B;C,D) = −1; null while the inputs are non-collinear or C is the midpoint of AB (D at infinity).
- All functions are pure, take `Vec2`s, and have epsilon-tolerant predicates (`isParallel`, `isCollinear`).

### Tool system (`domain/tools/`)

- `abstract class Tool { ToolState onTap(...); ToolState onHover(...); Command? complete(...); }`
- One subclass per tool: `PointTool`, `LineThroughTwoPointsTool`, `MidpointTool`, `IntersectionTool`, `ThreePointCircleTool`, `AngleBisectorTool`, `CompassTool`, `SegmentRatioTool`, `SquareMacroTool`, `ParallelogramMacroTool`, `TrapeziumMacroTool`, `VisibilityTool` *(Phase 30)*, etc.
- A tool collects N hit-tested inputs (existing objects or new points), then emits a `Command`. Snap-to-object during input collection.
- **In-progress input display (Phase 29):** a tool input that resolved to an *existing* object is shown by drawing the selection-style halo on that object, not by dropping a temporary point marker on it. `ToolInputPreview` gains `previewObjectIds: List<String>` (default empty) beside `previewPositions`; `TwoLineTool` (which used to preview its first tap projected onto the line), `PointAndLineTool`, `TransformObjectTool`, `IntersectionTool` and `MultiPointTool`-when-the-ladder-reused-an-existing-point report ids, while position-only taps and not-yet-committed `IntersectionPoint`/`PointOnObject` snaps keep the dot+ring marker (those objects don't exist yet). The painter draws the ids with the existing halo pass (union with the selection).
- **Angle tools without by-product points (Phase 29b, user feedback on 29):** Phase 29 haloed *reused* inputs, but a tap on a curve still ran the Phase 20 ladder and permanently glued a `PointOnObject` — for the angle-shaped tools users read those as fake points that shouldn't outlive the gesture. Two changes, deliberately scoped to the angle tools only (for segments/circles/macros the gluing is a feature). **(1) Angle bisector** becomes a dedicated two-mode `AngleBisectorTool` (`domain/tools/angle_bisector_tool.dart`): the first tap decides — a line hit enters **two-line mode** (second line commits one `AddObjectCommand` of a `TwoLineBisectorLine.near(...)`, both lines haloed, zero points created; the GeoGebra two-line bisector, except we create only the tapped wedge's bisector — tap the other wedge for the other one); a point hit or empty canvas enters **point mode**, the old three-point flow except curve taps are *ignored* instead of gluing (existing points reuse + halo, empty canvas still drops free points). Modes don't mix: point taps in line mode and line taps in point mode are ignored. **(2) Angle at vertex** keeps its `ThreePointTool` but with a new `allowCurveTaps: false` flag on `MultiPointTool`: a tap whose hit set contains an in-threshold curve (and no point) is refused — no gluing, no crossing snap, no free point half-on-a-line; the two-line case is what Angle-between-lines is for. `TwoLineBisectorLine` is excluded from Phase 24 whole-object transforms like the other non-point-parent lines. *(Phase 46 finishes the thought: the vertex-angle and line-angle tools merge into one two-mode `AngleTool` on `A` — the bisector's first-tap-decides machine, extracted into a shared `TwoLineOrThreePointTool` base — retiring `TwoLineTool` and the `allowCurveTaps: false` wiring; point mode ignores curve taps like the bisector.)* one `VisibilityTool` (`domain/tools/visibility_tool.dart`) with two named-constructor variants (the `TransformObjectTool` precedent), replacing the old `H` hide-selection / `Shift+H` reveal-all actions. **Hide** (`H`): each tap on a visible object emits one `ChangeAttributesCommand` setting `visible: false` — the object disappears immediately; empty-canvas taps do nothing. **Show/Hide** (`Shift+H`): while active, hidden objects render *dimmed* (~35 % opacity, labels included) and are hit-testable, and each tap *toggles* the hit object's `visible` flag — a dimmed object reappears, tap again re-hides. Every tap = one command = one undo step. `Esc`/`V` deactivate like any tool; no toolbar flyout entry v1 (mobile keeps the object-tree per-row eyes); the inspector's Visible checkbox and the tree eyes remain the selection-based paths. Phase 41 extends the pattern two ways. **(1) `DeleteTool`** (`domain/tools/delete_tool.dart`, stateless like `VisibilityTool`): while active, each tap on an object deletes it — one `DeleteObjectsCommand` = one undo step — with the same cascade rule as the `Del` key: the "Delete dependent objects too?" dialog appears only when the cascade reaches beyond the tapped object, as a *canvas pre-gate* (the tool itself just emits the command; the canvas awaits the shared `confirmCascadeDelete` before dispatching to `handleInput`, so the dialog stays presentation-layer and the Del-key path shares it). Empty taps are ignored (the active tool still owns them); hidden objects stay non-hit-testable (delete them via tree-select + `Del`, or via activation-on-selection). Activation is button-only — the app-bar delete button, no shortcut, no toolbar entry (`VisibilityTool` precedent) — and `Esc`/`V`/pressing the button again deactivate. **(2) Act-on-selection at activation:** activating `DeleteTool` with a non-empty selection deletes the whole selection immediately (same `deleteSelectionWithConfirmation` path, one undo step), and activating **Hide** (`H`) with a selection hides all *visible* selected objects at once (one `ChangeAttributesCommand` built by the pure `VisibilityTool.hideAll` helper; no command when none are visible; the selection stays selected per the Phase 7 precedent) — then either tool stays active for per-tap work. Show/Hide (`Shift+H`) deliberately gets no on-activation action (toggling a mixed selection is ambiguous). The activation-then-act order is deliberate: `activate()` first commits any in-progress drag (Phase 30b), so the drag command precedes the hide/delete command on the undo stack.
- **Unified point resolution (Phase 20):** every tap that a tool turns into a point goes through one shared ladder (`domain/tools/point_resolution.dart`): existing point within threshold → reuse it; two curves whose intersection branch is within threshold → new `IntersectionPoint` at the nearest branch; one curve within threshold → new `PointOnObject` glued to it; otherwise → new `FreePoint`. Used by `PointTool` and `MultiPointTool.collectVertex`, so the point tool, line/segment/circle, midpoint, angle bisector, transforms and macros all snap identically. The standalone Point-on-object tool is retired (subsumed by the smart Point tool). Deliberate consequence: a free point can no longer be dropped *exactly on* a curve — the tap glues instead; place off-curve and drag if a coincident-but-free point is really wanted. `ToolInput` carries the ranked in-threshold candidates (`extraHits`) plus the world-space `snapThreshold`; tools built to consume curves directly (perpendicular/parallel, angle-between-lines, intersection) are unaffected.
- Planned tool additions (Phases 13–16): `IntersectionTool` *(landed, Phase 13)* — pick two curves; creates the `IntersectionPoint` branch nearest the *second* tap, resolved by probing both branch objects so the choice rides the documented deterministic branch order; non-intersecting curves still commit branch 0 (undefined until dragged together). Transformation tools *(landed, Phase 15)* — reflect-about-line reuses `PointAndLineTool` (point + line in either order), reflect-about-point reuses `TwoPointTool` and translate reuses `ThreePointTool` (tap the point first, then the center / the vector's tail and tip), rotation is a small `RotatedPointTool` over `MultiPointTool` capturing its angle from a degrees dialog like the segment-ratio tool (a `TwoPointTool` closure would defeat the toolbar's builder-tear-off highlight), `AngleBySizeTool` *(landed, Phase 16)* — arm point, vertex, size dialog → a `RotatedPoint` plus a `VertexAngle` (GeoGebra convention; a negative size swaps the marker's arms so it measures |size| clockwise), and macro tools for equilateral / isosceles / right / random triangles and random / regular polygons (regular-polygon side count via dialog; "random" macros stamp randomized *free* points, fully editable afterwards).
- Macro tools (square, parallelogram, trapezium) are scripted compositions of primitive commands wrapped in a single undoable `MacroCommand`. Derived corners come from *hidden* scaffolding objects over the visible sides (perpendiculars + compass circles for the square, parallels for the parallelogram and trapezium), so macros introduce no new object kind — codec, painter and hit tester are untouched. Input schemes: **square** = 2 taps, adjacent corners A, B; the shape lies to the *left* of A→B (branch 1 of line∩circle along the perpendicular's direction — the AB carrier's CCW normal — which follows the points continuously, so the side never flips mid-drag). **Parallelogram** = 3 taps, consecutive corners A, B, C; D = A + (C − B) as the single-branch intersection of two hidden parallels. **Trapezium** = 3 taps for consecutive corners A, B, C plus a 4th *position-only* tap that places D as a `PointOnObject` projected onto the hidden parallel-to-AB through C — direct manipulation instead of a ratio dialog; AB ∥ CD by construction, and D inherits `PointOnObject`'s analytic-parameter caveat (translating the parallel along itself leaves D in place). The 4th tap never consumes an existing point — D must stay constrained to the parallel.
- **Whole-object transforms (Phase 24).** The four Phase 15 transforms extend from points to whole curves by *macro composition*: the image of a curve is the **same kind rebuilt over transform-point images of its defining points**, all in one `MacroCommand` — no new `GeoObject` kinds, so codec, painter and hit tester are untouched, and since all four transforms are isometries the image is automatically congruent (a rebuilt `CircleCenterPoint(image(center), image(rim))` has the right radius). *(Phase 68 sharpens the claim: the machinery only needs the defining relations to survive the map — true of any similarity, not just isometries — which is what lets dilation join; see its bullet below.)* Supported sources v1: every curve whose parents are all `GeoPoint`s — `Segment`, `Ray`, `LineThroughTwoPoints`, `CircleCenterPoint`, `CompassCircle`, `ThreePointCircle`, `Arc`, `VertexAngle`, and `Sector` except under reflect-about-line. The parents may themselves be derived points (transform kinds accept any `GeoPoint`), so the image tracks the source's full ancestry live with no recursion. `PerpendicularLine`/`ParallelLine`/`AngleBisectorLine`/`LineAngle`/`PointOnObject` (non-point parents) are excluded v1 — the tap is ignored; the future extension is object-level recursion (isometries preserve perpendicularity/parallelism/bisection, so `image(PerpendicularLine(P, l)) = PerpendicularLine(image(P), image(l))`), deferred because it materializes images of parent curves the user didn't ask for. Orientation, the one subtle point: line reflection reverses orientation — `Arc` is safe (the via-point image picks the branch), a reflected `VertexAngle` **swaps its arm points** so the marker measures the same wedge (no swap under the three orientation-preserving transforms; central reflection is a rotation by π, det +1), and `Sector` is excluded from reflect-about-line only (rebuilding gives the complementary wedge; swapping rim/end would break the radius — documented limitation). Tool UX: one `TransformObjectTool` (`domain/tools/transform_object_tool.dart`) parameterized per transform replaces the four flyout wirings; the **transformee is the first input**, and a slot-1 curve hit is consulted from `ToolInput.hit`/`extraHits` *before* the point-resolution ladder — otherwise Phase 20's smart resolution would glue a `PointOnObject` to the very curve being transformed (the reason this is a dedicated class rather than a patched `PointAndLineTool`). Point-mode behavior is preserved exactly, including reflect's point + line in either order; the `G` chords are unchanged and now accept curves. Image defining points are committed *visible* (usable geometry, auto-named once Phase 23 lands).
- **Transform images reused across gestures (Phase 40, user feedback on 24).** `_commitSource` dedupes shared defining points only *within* one gesture (the identity-keyed image map), so transforming a polygon segment by segment creates a fresh image of each shared vertex per gesture — coincident derived points, each auto-named (the reported "same points get multiple names"). Fix at the tool: `ToolInput` gains an additive `objects` field (the construction's objects in insertion order, default empty — the `snapThreshold`/`viewExtent` precedent), and before creating an image the tool looks for an **equivalent existing object**: same concrete kind, identical parent instances slot-by-slot, equal params (`RotatedPoint.angle` compared exactly — it comes from the same dialog value, no epsilon). Equivalent image points are reused as parents of the rebuilt curve (attributes untouched — a hidden equivalent is reused, not revealed); an already-existing rebuilt curve is not re-added; a commit where nothing new would be added returns `ToolIgnored`. Point mode dedupes the same way. Reuse is keyed on parent *instances*, so rotating about a different center or by a different angle never false-matches. follow the same rules. A shared helper `mirrorPointAcross` (in `domain/tools/`) reflects a point across a line using only existing kinds: hidden perpendicular through the point → hidden branch-0 line∩line foot → `SegmentRatioPoint(point, foot, ratio: 2)` = the exact mirror image. Circle-branch mirroring is deliberately *not* used — fixed branch indices swap sides when the point drags across the axis; the foot + ratio-2 form is single-valued and continuous. Input schemes: **rectangle** = 2 taps for side A, B + a position-only height tap (C = `PointOnObject.near` on the hidden perpendicular through B, D = branch-0 intersection of the hidden perpendicular through A with the hidden parallel-to-AB through C; inherits `PointOnObject`'s analytic-parameter caveat like the trapezium). **Right trapezium** = 3 taps A, B (base, right angle at A), C (far top corner); D = branch-0 intersection of the perpendicular through A with the parallel-to-AB through C. **Rhombus** = 2 taps for side A, B + a position-only direction tap; C = `PointOnObject.near` on a hidden `CompassCircle(A, B, center: B)` (polar parameter — drift-free), D via the parallelogram trick. **Isosceles trapezium** (a.k.a. equilateral trapezium) = 3 taps A, B (base), C (top corner); D = C mirrored across the perpendicular bisector of AB (hidden `Midpoint` + perpendicular axis + mirror scaffolding). **Kite** = 3 taps A (apex), B (side vertex), C (opposite apex); D = B mirrored across the hidden diagonal segment AC.
- **Dilation joins the Transform group (Phase 68, user request).** `ObjectTransform.dilate` + `TransformObjectTool.dilate({newId, ratio})` — the fifth named constructor on the rotate model: the ratio comes from a pre-activation dialog and is baked into the tool; finite **and non-zero** (ratio 0 collapses every image onto the center — rejected like `_parseLength`'s non-positives). Sound because Phase 24's macro composition needs only a *similarity*: a rebuilt `CircleCenterPoint`/`CompassCircle` gets the |ratio|-scaled radius from its scaled defining points, angles are preserved, so all nine curve kinds rebuild correctly. Orientation: plane homothety is `k·I` with det `k² > 0` — orientation-preserving even at negative ratios — so neither Phase 24 caveat applies: no `VertexAngle` arm swap, and `Sector` is supported (its exclusion stays reflect-about-line-only). `HomotheticPoint` (Phase 65) is unchanged and becomes the transform's image-point kind, the role `ReflectedPoint`/`RotatedPoint` play for theirs — codec, labels, tests untouched; `equivalentExisting` learns its `ratio` param (compared exactly, the `RotatedPoint.angle` precedent). UX: the Points-flyout homothetic row and its `TwoPointTool` dialog closure retire; the Transform flyout gains "Dilate from point (object, then center)…" and `G H` rewires to the dilation dialog → `TransformObjectTool.dilate`, whose point mode is tap-for-tap the old tool. Same phase, Points-flyout reorder (user request): intersection moves to row 2 (below point, above midpoint). **Completeness note:** isometries + dilations generate every plane similarity (a spiral similarity is rotate ∘ dilate about the same center), so the Transform group is now closed over similarities by composition; no further similarity tool is *needed*, only conveniences. Inversion — the one broadly valuable non-similarity — cannot ride this machinery (it maps segments to arcs, so rebuild-the-same-kind is wrong by construction) and would be its own phase with dedicated kinds (`InversePoint`, per-kind curve images).
- **Expression-powered numeric dialogs + shortcut in the title (Phase 69, user request).** The numeric tool dialogs (segment ratio, dilation ratio, rotation angle, angle by size, circle radius, segment length) parse their input with the Phase 58 expression language instead of the ad-hoc decimal-or-one-fraction `_parseRatio`: `parseExpression` + `evaluateExpression(expr, EmptyExpressionEnv())` — the numeric-only environment, **no geometry accessors** (a `dist(A,B)`-derived ratio would bake a stale value at creation; live measures are the text tool's job). `sqrt(2)`, `pi/6`, `2^0.5`, pasted `×·÷` all work; `a/b` fractions keep working via the grammar's division; the angle dialogs inherit the language's degrees-mode trig; unparseable, non-finite (and, where a dialog already restricted the range: zero ratio, non-positive length) still read as cancel. The side-count dialog stays integer-only. Separately, every dialog-tool's title row gains the tool's shortcut as dimmed trailing text (`shortcutDisplayFor`, the `ToolMenuRow` convention carried into the dialog) — numeric, naming and text dialogs alike — so the chord is learnable at the point of use.
- Triangle & polygon macros (Phase 16), same rules — visible corners + side segments, derived corners from existing kinds, one `MacroCommand`. Input schemes: **equilateral triangle** = 2 taps, corners A, B; apex C = `RotatedPoint` (B about A by +60°) — no scaffolding, no branch to pick; the triangle lies to the *left* of A→B and follows drags continuously. **Isosceles triangle** = 2 base taps A, B + a position-only apex tap; apex C = `PointOnObject.near` on the hidden perpendicular bisector of AB (hidden `Midpoint` + hidden `PerpendicularLine` referencing the visible base) — |CA| ≡ |CB| by construction; a degenerate base (A≈B) falls back to parameter 0, and C inherits `PointOnObject`'s analytic-parameter caveat. **Right triangle** = 2 base taps A, B (right angle at B) + a position-only tap for C on the hidden perpendicular through B referencing the base — the rectangle's height-tap mechanics; legs AB and BC, hypotenuse CA. **Regular polygon** = 2 taps, adjacent vertices A, B + side count from a dialog (integer 3–100, anything else reads as cancel, like the other dialog tools); the remaining n−2 vertices chain as `RotatedPoint`s — v₍ₖ₊₁₎ = v₍ₖ₋₁₎ rotated about vₖ by 2π/n − π — so the polygon lies left of A→B and every derived vertex is single-valued and continuous; a dedicated `RegularPolygonMacroTool` class (a captured count would defeat the tear-off highlight, like rotation). **Random triangle / random quadrilateral** = one-tap stamps: vertices are randomized *free* points around the tap, joined by segments (stamp radius ≈ 10× the tap's world-space snap threshold ≈ 80 screen px at any zoom, falling back to 80 world units when the threshold is 0). The triangle stamps 3 vertices at sorted random angles and jittered radii (sorted angles keep the outline non-self-intersecting; any triangle is trivially convex). The quadrilateral *(Phase 21, replacing the Phase 16 4–7-vertex random polygon)* is **always strictly convex**: exactly 4 vertices on one circle — no radial jitter, since sorted distinct angles on a circle are always in convex position — with angles from the gap method (n uniform draws normalized onto 2π minus n·minGap, minGap 0.25 rad, prefix-summed from a random start; deterministic, no rejection loop), then one random anisotropic affine stretch about the tap (rotate by φ, scale axes by factors in [0.7, 1.3], rotate back) for variety — affine maps preserve convexity, so the invariant survives. Randomness is injected (a seedable `math.Random` constructor parameter) so tests are deterministic. The Phase 16 "menu-only, no chord" decision is reversed in Phase 21: `X` `3` = random triangle, `X` `4` = random quadrilateral (digit second strokes proven by `G` `3`).
- **Planned tool additions (Phases 33–39):** perpendicular bisector reuses `TwoPointTool` (a `buildPerpendicularBisector` tear-off in the Lines flyout). `TangentTool` collects point + circle **in either order** (the `PointAndLineTool` pattern with a circle slot; a circle hit is consulted from `hit`/`extraHits` before the point ladder) and one tap-pair emits **both** tangent lines in a single `MacroCommand` — the GeoGebra convention; the pair is the natural undo unit, and deleting one afterwards is trivial. `FixedRadiusCircleTool` is dialog-first (`askCircleRadius`, the rotation-dialog pattern; garbage/non-positive reads as cancel), then one tap resolves the center via the ladder — a dedicated class so the tear-off highlight survives, per the rotation precedent. `FixedLengthSegmentTool` (dialog length L): tap endpoint A via the ladder, then a **position-only** direction tap (the trapezium 4th-tap precedent) → one `MacroCommand` of hidden `FixedRadiusCircle(A, L)` + visible `PointOnObject.near` B + visible `Segment(A, B)` — length pinned by construction, direction draggable for free through the Phase 14 slide-drag (B inherits the analytic-parameter caveat; degenerate tap falls back to parameter 0). Chosen over a dedicated `PointAtDistance` kind, which would need a new mutable direction, mutation primitive and drag command. `PolygonTool` is variable-arity over `MultiPointTool`: taps resolve via the ladder and the polygon **closes by tapping the first vertex again** once ≥ 3 are collected (taps on other already-collected vertices are ignored — no self-touching rings; no dialog, no fixed count). `DistanceTool` = `MultiPointTool` with 2 fully-laddered taps → `DistanceMeasurement`. `AreaTool` = one tap consulting `hit`/`extraHits` for the topmost `GeoPolygon`/`GeoCircle`, never falling through to the point ladder; other taps ignored. `LocusTool`: tap 1 must hit a `PointOnObject` (slot-consult), tap 2 a `GeoPoint` whose parent walk reaches the driver (else ignored) → one `AddObjectCommand`. `ToolInput` gains an additive `viewExtent` (visible world width, default 0 — the `snapThreshold` precedent) so the locus tool can bake a line-host sampling window.

### Commands (`domain/commands/`)

- `abstract class Command { void apply(Construction c); void undo(Construction c); }`
- Concrete commands: `AddObjectCommand`, `DeleteObjectsCommand` (cascades to dependents — captures their full state for restore), `MoveFreePointCommand` (one command per drag gesture, not per frame), `TranslateObjectsCommand` (rigidly translates a *set* of free points by one delta in a single undo step — this is how dragging a derived object works, see canvas section), `ChangeAttributesCommand`, `MacroCommand` (groups N commands).
- Drag preview: during a gesture the construction is mutated directly per frame (no command per frame). The gesture must terminate by emitting exactly one command capturing start → end, or by rolling the preview back on cancel (Esc mid-drag). This is the one sanctioned mutation outside a command; CLAUDE.md states the invariant with this carve-out.
- **Tool activation mid-drag commits, deactivation cancels (Phase 30b, user feedback on 30):** a tool-activating shortcut pressed while a move/select drag is still down **ends the drag as its one start → end command** before the tool takes over — never a silent rollback. Rationale: a committed half-drag is one undo away, a cancelled one is unrecoverable, and Phase 30 put tool activations on `H`/`Shift+H`, exactly the keys pressed right after arranging objects (macOS three-finger drag even keeps the drag live for a grace period after the fingers lift, so "after my change" is often physically still mid-drag). Before Phase 30 those keys ran plain commands and never touched the drag. `Esc`/`V` (deactivation, `activate(null)`) keep the rollback — Esc mid-drag stays the deliberate abort gesture — as do the pointer paths (second-finger interrupt, pointer cancel), where "cancelled, never committed" remains right.
- `class CommandStack` (in `application/`) holds undo + redo stacks, exposed as a Riverpod `Notifier`.

### Canvas & interaction (`presentation/canvas/`)

- `GeometryCanvas` widget hosts a `CustomPaint` with a `GeometryPainter` and a gesture stack:
  - `Listener` for pointer events (mouse + touch).
  - `GestureDetector` for tap, pan, scale.
- `Viewport` value type: `Vec2 pan` + `double scale`. World↔screen transforms live here, including zoom-about-a-focal-point (the world point under the cursor stays fixed) and scale clamping.
- Viewport changes (pan, zoom, fit, reset) are *view* state, not construction state — they never go through `Command`s and are not undoable, for the same reason selection changes aren't: undo should replay edits to the document, not replay where the user was looking. The viewport is still snapshotted into the save format (Phase 9), just outside the undo history.
- `HitTester`: iterates visible objects, returns the closest under a screen-px threshold, with priority order points > arcs/circles > segments/rays/lines (loci join this tier in Phase 39, distance = min clamped distance over consecutive sample segments) > angles > measurements *(Phase 38 — world distance to the text anchor; the canvas tap handler additionally checks the text's `labelScreenRect` first, exactly as the label-drag path already does, so text dragged far from its anchor stays tappable)* > polygons *(Phase 37 — the interior hits at distance 0 via an even-odd ray cast but at lowest priority, so anything drawn inside still wins while an empty interior tap selects the region; outside, min clamped edge distance; band-select requires all vertices contained)*. Used by both tools (input picking) and the selection drag. The threshold is **pointer-kind-based** *(Phase 25)*: 16 px for `PointerDeviceKind.touch`, 8 px otherwise — kind-gated rather than platform-gated, so touch-screen laptops and an iPad with a mouse both do the right thing. The canvas records the device kind from the `Listener` events it already handles; the larger touch threshold flows automatically into hit testing, `ToolInput.snapThreshold`, the Phase 20 point-resolution ladder, and the random-stamp radius (a touch stamp is 2× — acceptable, arguably correct on a phone).
- Dragging (in the no-tool move/select mode): a free point moves directly (`MoveFreePointCommand`). Any *other* object drags as a rigid translation of its free-point ancestors — grab a circle's rim and the whole circle moves because its defining points do — emitting one `TranslateObjectsCommand` per gesture. Two planned exceptions (Phase 14): a `PointOnObject` slides along its host curve (new `SetPointOnObjectParameterCommand`, one per gesture, same preview/rollback contract as the other drags), and a `CompassCircle` drags by moving only its *center's* free ancestors — the radius-defining points stay put, because the radius is a measurement, not part of the rigid body. Fully-derived objects with no free ancestors (e.g. an intersection point) don't drag. (A dedicated Drag tool with a select-only no-tool default was considered and shelved — dragging stays in the no-tool mode.)
- `GeometryPainter` walks the construction in insertion order, applies the viewport transform, draws each object using its attributes. Labels rendered via `TextPainter` at the object's per-kind anchor plus the stored `labelDx`/`labelDy` offset, at the per-object `labelFontSize` *(Phase 28)*. Labels are plain text — LaTeX/rich-math label rendering was considered and **deferred** (revisit on demand). Phase 30's Show/Hide tool adds a `showHidden` painter flag: while that tool variant is active, hidden objects (and their labels) draw at reduced opacity and `CanvasHitTester` includes them (`includeHidden`); this is tool-scoped view state — nothing persisted, nothing in the save format, and PNG export never renders hidden objects regardless (same no-UI-chrome rule as halos and markers). Objects with `dashPeriod > 0` draw their stroke as a dashed `Path` (hand-rolled `dashPath` via `PathMetrics`, no dependency); angle markers and the selection halo stay solid — the halo is UI, not object style. Line clipping (Phase 44): a line/ray with `lineClip > 0` draws through the existing segment/ray extent clamps at a clip span computed by a pure domain helper (`lineClipSpan(construction, line)` — parameter min/max over the incident points, see `ObjectAttributes.lineClip`), and `CanvasHitTester` clamps distance to the same span so the invisible region isn't tappable; the helper scans the construction's objects, which the painter and hit tester both already hold (O(objects) per clipped line — fine at realistic sizes, revisit if profiling disagrees). Angle markers *(Phase 22)*: the wedge radius comes from `attributes.angleMarkerRadius` (screen px, per object) instead of a painter constant; an angle whose sweep is exactly π/2 (shared math epsilon — right angles from perpendicular constructions are fp-exact) **automatically draws the right-angle square** — the polyline `v + s·d1 → v + s·(d1 + d2) → v + s·d2`, s = 0.7 × radius — instead of the arc, for both `VertexAngle` and `LineAngle`. When `fillAlpha` is set, the wedge (or square) gets a fill pass at the object color under the stroke pass; the same pass finally implements `Sector` fill, which the attributes documented but the painter never read. Defaults (radius 20, unfilled) render existing constructions identically. Phase 37 extends the `_drawFill` pass to two more fillables: `GeoPolygon` (the closed vertex path) and `GeoCircle` (a filled disc); polygons and loci draw dash-capable outlines like the other strokes (a locus paints one polyline `Path` per non-null sample run — gaps where the traced point was undefined — closed for circle hosts when gapless).
- **Label text & show-value (Phase 35):** label composition moves into a shared `labelText(GeoObject)` helper beside `labelScreenRect`, consumed by *both* the painter and the hit rect so they can't drift (the Phase 28 rule). A label paints iff it has a value part or (`labelVisible` && named); the text is `name = value` when both parts show, the bare value when the name part is hidden, the bare name when `showValue` is off. `showValue` is deliberately **independent of `labelVisible`** — segments are auto-named with `labelVisible: false` (Phase 23), so gating the value behind it would make the inspector's checkbox look dead; a fresh measured segment shows `3.42`, revealing the name upgrades it to `AB = 3.42`. Formatting lives in `presentation/canvas/measure_format.dart` (display-only, so presentation — the `label_anchor` precedent): lengths at 2 decimals, angles in degrees at 1 decimal + `°`, areas reuse the length format (Phase 38); fixed decimals keep goldens deterministic *(Phase 72: the count becomes per-object — the formatters take a `decimals` param fed from `valueDecimals`; null keeps the kind default, so the fixed-width property holds per object)*. Values read straight off domain geometry (`Segment` endpoints' distance, `GeoAngle.angle.measure`) — no new domain API. Measurement objects (Phase 38) and texts (Phase 58) draw *no* geometry in `_drawObject`; their text rides this same label pass — measurements always with a value part, `name = value` when named and label-visible; texts as bare content, never name-composed — so text dragging, `labelFontSize` presets and color styling need zero new code. Values render in PNG export (object style, not UI chrome).
- **Axes & grid (Phase 36):** a background layer drawn first in `paint()`, behind every object: grid hairlines at each multiple of an adaptive step — the smallest `{1, 2, 5} × 10^k` spanning ≥ 48 screen px, via a pure `gridStep(scale, {minPx: 48})` helper in `presentation/canvas/grid_layout.dart` — and 1.5-px axes through the world origin, with tick labels (trailing zeros trimmed, a single `0` at the origin) drawn only while axes are on. The toggles are **document state, not object state**: a `DocumentSettings` value (`showAxes`/`showGrid`, both default false) in its own provider — like the viewport, *not undoable*, but persisted per document (see Persistence). Theme supplies grid/axis colors via a `CanvasColors` `ThemeExtension` (`ColorScheme.outline`/`outlineVariant` were considered and rejected — Material widgets read them for their own chrome). Defaults render existing documents, goldens and smoke byte-identically. Grid and axes are not objects: hit testing, selection and fit ignore them. The export dialog gains an "Include axes & grid (as shown)" checkbox (`ExportOptions.includeAxesGrid`, default true, shown only while either toggle is on): the export renders the document's own toggles gated by it, and an unticked export is byte-identical to a toggles-off one.
- **Snap to grid (Phase 45, follows 36):** a per-document `DocumentSettings.snapToGrid` toggle (default false — like `showAxes`/`showGrid`: not undoable, persisted, File > New resets). While on, **free-point placement and free-point drags quantize to the nearest grid crossing** of the same adaptive `gridStep(scale)` the Phase 36 grid draws at — hard round-to-nearest (the deterministic "fixed to grid" behaviour), not a proximity gate, via a pure componentwise `snapToGrid(Vec2, step)` helper in `domain/math/`. The toggle is deliberately independent of `showGrid` (snapping with the grid hidden is the user's explicit choice), but because both read the same step, snapped points always land on drawn crossings when the grid is visible. Scope is deliberately narrow: **only genuinely free positions snap** — position-only taps in the Phase 20 resolution ladder (grid rounding becomes the ladder's *last* rung, so snapping to an existing point / curve / crossing always wins) and single free-point drags (preview quantizes per frame; still exactly one `MoveFreePointCommand` per gesture). Rigid `TranslateObjectsCommand` drags and `PointOnObject` slides do *not* snap — quantizing every free ancestor independently would distort shapes, and hosted points are constrained to their curve. Layering: `gridStep` lives in presentation, so the canvas computes the step and passes it into the tools as an additive `ToolInput.gridSnapStep` (world units, 0 = off — the `snapThreshold`/`viewExtent` precedent); `domain/` never imports presentation. Snapping happens in world coordinates, so Phase 43's viewport rotation composes for free. UI: a third `CheckedPopupMenuItem` — Snap to grid — in the Phase 36 grid popup; menu-only v1, no shortcut (the `⇧G`/`⇧X` leaders stay a pair; add a key on demand). Export is untouched — snapping is input behaviour, not rendering. Off by default, existing documents and goldens are byte-identical.
- Label dragging (Phase 17, move/select mode only): the label's screen rect (shared `labelScreenRect` helper so painter and canvas can't drift) is hit-tested *before* object geometry on pan-start; the drag updates a painter preview override held as canvas widget state (no construction mutation), clamps the offset magnitude to 40 px radially, and commits exactly one `ChangeAttributesCommand` on release. Labels are screen-sized, so this lives in the canvas widget, not `CanvasHitTester` (which is deliberately viewport-free).
- Multi-touch on mobile: pinch = zoom, two-finger drag = pan. On web/desktop, pointer signals follow the Figma-style mapping (decided in Phase 14): **plain scroll = pan** (both axes, so a trackpad two-finger swipe pans naturally and a mouse wheel scrolls the canvas), **pinch = zoom about the cursor** (browsers deliver a trackpad pinch as a ctrl-flagged wheel event; the Flutter web engine detects that Ctrl isn't physically down and synthesizes a `PointerScaleEvent`, which the canvas handles separately), and **physical `Ctrl`/`Cmd` + scroll = zoom** too, so mouse users keep a wheel zoom. The pre-14 mapping (scroll = zoom) read as "panning also resizes" under trackpad swipes because zoom-about-cursor both scales and shifts when the cursor is off-center. A macOS three-finger drag (accessibility) is a synthetic mouse drag and still rubber-bands — out of scope. Native desktop builds (not a shipping target) deliver trackpad gestures as PointerPanZoom into the scale recognizer's navigation branch, which already pans/zooms correctly.
- **Viewport rotation (Phase 43).** `ViewportState` gains `rotation` (radians CCW, default 0) and `CanvasViewport`'s transforms generalize — rotation composes into world↔screen, `pinning` gains the rotation term, and the length helpers are untouched (rotation preserves lengths, so hit thresholds and snap radii flow through unchanged). Driven by the two-finger twist: the scale recognizer's navigation branch feeds `details.rotation` into the same per-gesture baseline solve as pinch zoom, so twist, pinch and pan compose in one gesture about the focal. Rotation *arms* only past a small threshold (~0.1 rad) so a plain pinch can't drift the canvas, and snaps back to 0 when released within ~2° of level; touch-only v1 (no desktop binding), Reset clears it, Fit resets it to 0. **Rotation is pure view state** — the decided answer to "keep coordinates and grid orientation intact": object coordinates are never touched (rotating the world would rewrite saved geometry per gesture), and the Phase 36 grid/axes are drawn in world space so they rotate *with* the content on screen, staying glued to the world axes — coordinates and grid remain mutually consistent at any view angle. Not undoable (viewport precedent), but persisted: an additive `rotation` key beside `pan`/`scale` (absent → 0, no version bump). Consequences: band-select containment must become a screen-space predicate (`Rect.contains ∘ worldToScreen`) instead of an axis-aligned world rect — under rotation the band's screen rect maps to a rotated world quad; labels stay screen-upright (`TextPainter` never rotates, only anchors transform); PNG export's current-viewport framing carries the rotation, fit framing exports unrotated.
- **Desktop rotation bindings (Phase 43b, follows 43 — user feedback: "make trackpad work, ideally also for web").** A real twist can't work on the web: browsers reduce trackpad gestures to wheel events (swipe) and ctrl-flagged wheel (pinch) — the rotate gesture is never exposed (only desktop Safari's non-standard `GestureEvent`, ruled out as a single-browser JS-interop hack). So desktop rotation is a *synthetic* binding: **`Alt`/`Option` + scroll rotates about the cursor** — linear, `rotation += −dy · 0.003 rad/px` (≈17° per wheel notch), through the same pointer-signal plumbing as `Ctrl`+scroll zoom, so it drives from a mouse wheel and a trackpad two-finger swipe alike. `Shift` is unusable as the modifier: browsers convert `Shift`+wheel into *horizontal* scroll deltas. Wheel streams have no end event, so the touch snap-back's trigger is mirrored as a **quiet-period settle**: 250 ms after the last rotate event, `TwistGate.settled` runs about the last cursor position (normalize to (−π, π], snap within 2° of level). **Compass chip**: an app-bar button mounted only while the view is rotated (its own `Consumer` on a rotation select, so twist frames rebuild one button, not the screen; being conditional also keeps the web smoke's icon indexing intact at level view), needle rotated by −rotation so it points where world-up points on screen, tooltip shows signed degrees; clicking levels the view about the canvas center keeping pan/zoom — the previously-missing way back to level without Reset/Fit. Native desktop (not a shipping target) gets the *true* trackpad twist almost free: macOS delivers rotation via `PointerPanZoom`, which the scale recognizer already folds into `details.rotation` (a pan-zoom counts as two pointers, so the navigation branch engages); the `TwistGate` now also mounts while a pan-zoom pointer is active, tracked via the `Listener`'s pan-zoom callbacks — the web engine never synthesizes those, so the web mapping is untouched. Cheat sheet gains an `Alt + scroll` gesture row.
- **Compass relocation (Phase 60, user feedback on 43b: the app-bar button is too easy to miss).** The compass leaves the app bar for a **floating chip on the canvas's top-right corner** — the map-app convention (map UIs surface their compass on the map itself while rotated), so it sits on the content it levels and can be larger than an app-bar icon: an elevated Material chip with the needle over a live signed-degrees readout. Mounted as a `Positioned` in the canvas `Stack`, *before* the region-pick overlay so an export pick still owns the whole surface. Every 43b behavior carries over: mounted only while the view is rotated (it doubles as the "you are rotated" indicator), needle at −rotation pointing where world-up points on screen, click levels about the canvas center keeping pan/zoom, its own `Consumer` on a rotation select so twist frames rebuild one chip, not the screen. Leaving the app bar entirely also retires the conditional icon-row mount — the web smoke's icon indexing is now rotation-independent by construction.
- **Rotation-preserving Fit (Phase 61, user feedback on 43/60).** Fit's job is framing, not orientation — with the compass as the dedicated way back to level, "Fit construction to view" now keeps the current view angle (supersedes Phase 43's "Fit emits 0"). Mechanism: `visibleWorldBounds` and `fittedViewport` gain an optional `rotation` — bounds are taken in the *view frame* (each contribution rotated by +θ in the y-up frame; a circle's disc rotates as its center ± radius, so the box stays tight), the scale solve is unchanged over the rotated extents, and the resulting state comes from `CanvasViewport.pinning` (bounds center → canvas center), which at θ = 0 reduces exactly to the old pan solve. The view triad is now orthogonal: **compass** levels without moving, **Fit** frames without leveling, **Reset** stays the full home — origin, 100 %, level (decided against a rotation-keeping Reset; the zoom-to-100 % action already keeps the angle for that need). PNG export's fit framing still exports unrotated (callers default `rotation` to 0). Rides along: the compass chip slims slightly on user feedback (30 px needle, tighter padding).

### Persistence (`application/persistence/`)

- JSON schema:
  ```json
  {
    "version": 1,
    "viewport": {"pan": [0,0], "scale": 1},
    "objects": [
      {"id": "p1", "type": "FreePoint", "parents": [], "params": {"x": 1.0, "y": 2.0}, "attributes": {...}},
      {"id": "m1", "type": "Midpoint", "parents": ["p1","p2"], "params": {}, "attributes": {...}}
    ]
  }
  ```
- Save: serialize each object in topological order (= the construction's insertion order).
- Load: parse, then construct in order — each constructor receives already-deserialized parents by id. Use `freezed`'s json support for attributes.
- Encode/decode both live in one hand-written codec (`application/persistence/construction_codec.dart`) that switches on concrete object type, rather than `toJson` methods spread across the domain classes: the type↔constructor registry must exist centrally for *decoding* anyway, keeping the encoder beside it means one file to update per new object kind, and the domain layer stays free of persistence concerns. The cost — a forgotten kind fails at runtime, not compile time — is covered by the round-trip test that instantiates every concrete kind.
- Decode failures (malformed file, unknown type, unknown version, ill-typed parents) throw `FormatException` with the offending object's id, so File > Open can show one dialog for any bad file.
- Schema version field from day one to allow future migrations. A file with a *newer* version than the app understands is rejected, not best-effort parsed.
- Phase 36 adds two additive top-level keys beside `viewport`: `"showAxes"` / `"showGrid"` (absent → false) — **no version bump**: the decoder reads only the keys it knows, so old files decode with defaults and old apps ignore the new keys. `DecodedDocument` gains a settings field; File > New resets to defaults. Like the viewport, the settings are persisted but never undoable. Phase 45 adds a third sibling key `"snapToGrid"` (absent → false) riding the same machinery — additive, no version bump.
- Phase 43 adds an additive `"rotation"` key inside `viewport` beside `pan`/`scale` (absent → 0, radians CCW) — same no-version-bump reasoning; `lineClip` (Phase 44) rides the attributes object like every additive attribute before it.
- Phase 37's `Polygon` is the first object whose parents array has variable length. The codec's parents list already carries an id array, so encoding is untouched; decoding loops the typed `point(i)` helper over `parents.length` instead of fixed slots, with the constructor's ≥ 3 guard normalizing short lists to `FormatException`.

### Export (`application/export/`) — planned, Phase 19

Export the construction as an image, separate from the JSON save format.

- **PNG (committed).** Render off-screen via `ui.PictureRecorder` + the existing `GeometryPainter` — *not* a widget screenshot — so exports work at any resolution and never include UI chrome (selection halos, in-progress tool markers, band rectangle). Framing has three options: "fit construction" (default, via the existing `fittedViewport`), "current viewport", and a **drag-selected region** of the window. An options dialog picks framing, scale factor (1×/2×/4×) and background (theme canvas color vs **transparent**), and always shows the **exact output rectangle in pixels** ("Output: 1920 × 1080 px"), live-updated as framing and scale change. Encode with `ui.Image.toByteData(format: png)`; deliver bytes through a `savePngBytes` sibling of the existing save path in `application/persistence/file_io.dart` (already handles web download + native picker).
- **Region picking.** Choosing "Select region…" in the dialog closes it and arms a one-shot overlay stacked *on top of* `GeometryCanvas` (the canvas widget is untouched and receives no events while the overlay is up): drag draws a marquee rectangle, release captures it in canvas screen coordinates and reopens the export dialog with the region framing selected; Esc cancels back to the dialog. The region maps to a viewport by `pan = screenToWorld(rect.topLeft)` at the unchanged scale, output logical size = the rect's size — so what you see inside the marquee is exactly what exports.
- **Placement.** Orchestration in a new `lib/application/export/` beside `persistence/`, plus a small options dialog in presentation. The painter lives in `presentation/`, so the export code that calls it also stays outside `domain/` — no layer-rule impact.
- **Not a command.** Export is a read-only view operation: not undoable, nothing added to the save format (same reasoning as viewport changes not being undoable).
- **UI.** File menu → "Export as PNG…"; shortcut `Ctrl/Cmd + E` in the shortcut table + cheat sheet.
- **Axes & grid (Phase 36).** The options dialog gains one checkbox — "Include axes & grid (as shown)", default on when either toggle is on — passing the current document settings into the off-screen render. One flag, not two: the export either mirrors the canvas or strips decoration; per-flag control is dialog noise.
- **SVG (stretch, same phase, may slip).** Hand-written SVG writer walking the construction in insertion order, mirroring the painter's per-kind drawing (incl. `dashPeriod` → `stroke-dasharray`, labels as `<text>`). No dependency. Explicitly optional.
- **Out of scope.** PDF and clipboard-copy — revisit on demand.

## Test strategy

Tests mirror the source layout under `test/`. Coverage targets:

- **`test/domain/math/`** — exhaustive numeric tests on intersections (parallel, tangent, coincident, near-tangent), triangle centers (verify against known coords for canonical triangles), and edge cases (degenerate triangles, points coinciding). Property-based via `glados`:
  - midpoint of (A, B) is equidistant from A and B
  - circumcenter is equidistant from all three vertices
  - centroid = (A + B + C) / 3
  - line through (A, B) contains both A and B within epsilon
  - reflection across a perpendicular bisector swaps A and B
- **`test/domain/construction/`** — recompute correctness: build a chain (e.g., midpoint → perpendicular → intersection), drag a root, assert all dependents are consistent. Cascade delete: deleting a parent removes all dependents and is reversible.
- **`test/domain/commands/`** — every command's `undo(apply(c)) == c` for representative inputs.
- **`test/domain/tools/`** — tool state machines: feed a sequence of `onTap` calls, assert the resulting command.
- **`test/application/persistence/`** — JSON round-trip on a complex construction (several derived layers, all object kinds), incl. attributes and viewport.
- **`test/presentation/`** — widget tests for tool flows (tap-tap to make a segment, drag a free point and see the dependent update), and golden tests for rendering each object kind in light + dark theme.

CI-friendly: keep golden tests in their own tagged group so they can be skipped on platforms where rendering differs.

## Keyboard shortcuts

Tools are bound to single letters where possible; less-common variants use Shift+letter or a two-key chord. The one source of truth is a declarative `ShortcutTable` (`lib/presentation/shortcuts/shortcut_table.dart`): a list of bindings, each a one- or two-stroke key sequence plus a semantic `AppAction`, a human-readable label, and a cheat-sheet section. A pure `ShortcutResolver` consumes key strokes one at a time and handles the two-stroke leader chords (a pending leader is cancelled by Esc or any non-matching second stroke, which is swallowed rather than fired standalone); an `AppShortcuts` `Focus` widget at the editor root feeds it hardware key events, marks matches handled, and ignores everything while an `EditableText` has focus so typing a name can never trigger a tool. Flutter's stock `Shortcuts`/`Actions` tables are deliberately *not* used: chords and the focused-text-field guard don't fit `ShortcutActivator`'s single-stroke, always-on model. Mobile users obviously skip these, but on web/desktop they're essential.

## Multi-session workflow

This app spans many sessions. A fresh session has zero memory of prior ones, so we lean on four durable artifacts in the repo. Any new session should be productive within a minute of warm-up.

| File | Role | Cadence |
|---|---|---|
| `docs/PLAN.md` | Architecture, build order, decisions. The "what and why." | Read-mostly; edited only when scope or approach changes. |
| `docs/STATUS.md` | Append-only log of what happened each session. The "where are we." | One entry per session, written at session end. |
| `docs/TODO.md` | Live checklist mirroring the build-order phases. | Tick boxes during the session as items land. |
| `CLAUDE.md` (repo root) | Architectural invariants, common commands, conventions. Auto-loaded by Claude Code every session. | Edit only when invariants change. |

**Session-start ritual.** Open the project and say:

> *Read CLAUDE.md, docs/PLAN.md, docs/STATUS.md, docs/TODO.md. Tell me what's next and propose the first concrete change.*

This can be wrapped as `/continue-build` via `.claude/commands/continue-build.md` so it's one keystroke.

**Session-end ritual.**

1. Commit work-in-progress on a phase branch.
2. Tick completed boxes in `docs/TODO.md`.
3. Append a new entry to `docs/STATUS.md` (date, what was done, what's next, gotchas).

**Branching.** One feature branch per build-order phase (e.g., `phase-1-math`, `phase-2-construction-core`). Merge to `main` once the phase's tests are green and `flutter analyze` is clean.

**Anti-patterns to avoid.**
- Letting a session run too long — context quality degrades. End at a clean checkpoint and start fresh.
- Skipping the STATUS entry. The 30 seconds saved cost 10 minutes next session.
- Treating in-session memory as durable. Anything important must land in one of the four files above.

- `flutter pub get && dart run build_runner build` succeeds.
- `flutter analyze` clean.
- `flutter test` green, including goldens.
- `flutter run -d chrome` — build a non-trivial construction (triangle + circumcircle + orthocenter + perpendicular from one vertex), drag a vertex, confirm everything updates smoothly.
- `flutter build apk` and `flutter build ios` succeed (build only — actual device run optional unless requested).
- Save the construction to JSON, clear, load it, confirm identical render.
- Toggle theme, confirm colors swap and persist across restarts.
- Undo a chain of operations including a drag, then redo — final state matches.
