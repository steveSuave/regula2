# regula2 — V2 Plan: Complex Projective Kernel

## Context

regula2 is the V2 of regula, seeded from the full V1 repo (history preserved; the branch point is tagged `v1-final`, regula commit `7ef44db`). V1's architecture — construction DAG, command-pattern undo, tool state machines, the whole presentation shell — is documented in `docs/archive/PLAN-v1.md` and survives largely intact; **this document describes only what changes and why.**

The driver is the assessment in `docs/V2-assessment.md`: Cinderella-class behaviour — no jumping intersection points under drags, complete loci — is not a set of features but the consequence of one representational choice. **The kernel computes in homogeneous coordinates over ℂ, and drags are resolved by analytic continuation along a path that detours through complex space around degeneracies.** No orientation heuristic patched onto an affine kernel can deliver this (there's a proof); V1's `locus.dart` (704 lines of hand-rolled boundary bisection, branch flipping, and infinity tails) and its `branchIndex` clamping are what approximating it numerically costs. Under a projective complex kernel:

- line ∩ line is **always** exactly one point (possibly at infinity) — a cross product,
- line ∩ conic is **always** exactly two points (possibly complex, possibly coincident),
- conic ∩ conic is **always** four — via the pencil `λA + μB`,
- `isDefined` stops being a graph property and becomes a *rendering* question: "is this point real and finite?",
- circles become conics through the circular points I=(1,i,0), J=(1,−i,0), which also unlocks Cayley–Klein non-Euclidean geometries nearly free.

Beyond the kernel, the V2 scope (in payoff-per-risk order) is: tracing/continuation engine, port of the ~39 object kinds and ~42 tools, a JGEX-style deductive-database prover with visually replayed proofs, and — last — 3D. The kernel track is planned phase-by-phase in `docs/TODO.md` (Phases 100–122); prover and 3D are milestone outlines below, opened as numbered phases when their time comes.

Mathematics sources: Richter-Gebert & Kortenkamp's published papers and *Perspectives on Projective Geometry* (Cinderella itself is proprietary — take the math, never code); Chou–Gao–Zhang for the deductive database and area methods; JGEX (open Java), AlphaGeometry DDAR / Newclid (open Python) for rule sets.

## Architecture: projective-canonical, affine-as-view

*This section described the migration contract until Phase 121 completed it; it now describes the architecture that contract arrived at. The migration's own rules — lift-from-affine bridge defaults, migrated-vs-unmigrated kinds, the batch order — are gone from the code and live in the git history and `docs/archive/`.*

1. **The kernel is `lib/domain/projective/`**: `Complex`, `ProjPoint`, `ProjLine`, `ConicMatrix`, the total intersection functions, and the tracing engine. V1's affine kernel left `lib/` in Phase 121 and sits in `test/v1_oracle/`, where nothing shippable can import it — see point 4.
2. **Every kind stores homogeneous state.** `GeoPoint.projPoint` / `GeoLine.projLine` / `GeoCircle.conic` are abstract (Phase 121; through the migration they carried lift-from-affine defaults, which afterwards would only let a new kind forget its homogeneous state silently). The affine `position` / `line` / `circle` getters are *projections* of that state, and `isDefined` means "real and finite after projection" — a rendering question, not a graph property. **Domain code reads the projective accessors**; the affine ones exist for the painter, hit-tester, codec, and the chart reads §Parameterization sanctions.
3. **`Vec2`, `LineEq` and `CircleEq` are view structs, permanently** — what projective state projects *to*, reached through `toVec2` / `toLineEq` / `toCircleEq`, which answer null where there is no real finite value. Nothing computes geometry in them; nothing outside `lib/domain/` constructs one. `lib/domain/math/` keeps them plus the metric helpers the consumer kinds read (`angle_geometry`, `triangle_centers`, `polygon_math`), and the expression engine.
4. **The canonical order is defined by agreement with V1, and that is permanent.** The intersection functions return roots in an order that agrees with the old affine kernel's on real transverse cases (line∩conic by parameter along the line; circle∩circle real roots by sign against the directed centre line; I and J filtered out of `branchIndex` addressing). That order is what `branchIndex` addresses and what every saved document carries, v1 and v2 alike — so the *oracle* is permanent too, which is why V1's kernel was moved to `test/v1_oracle/` rather than deleted. Branch identity *during* a drag is held by continuation, not by re-sorting (Phase 116); the pass re-derives the canonical index at its end, so commits, saves and undo stay in one address space. Two points may never share `(curve1, curve2, branchIndex)` — see that section below.
5. **One degeneracy convention: the projective value is total, the projection is nullable.** A projective accessor answers null only when a parent's is null, or when the computed homogeneous value is the zero triple; everything else is the projection's question. Degeneracies are values — the line at infinity, a line pair, a doubled line — and V1's epsilon bands that nulled things out are gone, so near-degenerate input yields genuine faraway geometry and only exact degeneracy degenerates. Stated with its three sanctioned exceptions on `GeoObject`, and gated by collapsing the kitchen-sink corpora onto one point. **A violation of this rule is invisible statically and fatal to tracing** (Phase 136b): `Segment` and `Ray` gated their carrier on the parents' *affine* positions, which no static test could tell from correct behaviour — the realness gate refuses complex carriers anyway — but it meant that the moment a complex detour drove a parent off the real axis the carrier vanished, every intersection riding it coasted the whole arc on a stale root, and the detour resolved nothing. So the rule is not bookkeeping: a chart-gated projective accessor is an object that cannot be continued through, and the symptom surfaces only in a walk.

Rejected on the way here, and worth not re-litigating: an affine-canonical bridge (projective computed lazily from affine) cannot hold continuation state or complex values; a parallel `objects2/` fork would have doubled the shell's dispatch surface and abandoned the tests-as-spec property; a big-bang rewrite would have meant weeks of red across 33k lines of tests encoding the affine conventions.

### Two decisions pinned early (see docs/V2-assessment.md "Flutter/Dart-specific difficulty")

- **Numeric throughput / compile target (Phase 101).** Dart has no complex type; every boxed complex op allocates, and tracing runs thousands of steps × dozens of objects per drag frame. The tracing inner loop is planned on `Float64List` struct-of-arrays from the start, and dart2js vs dart2wasm is benchmarked before any kernel code depends on the answer.
- **Web threading (before any prover code, M-P0).** No isolates on web. The prover engine is written as a resumable state machine with an explicit work queue from day one — cooperatively chunked on web, `Isolate.run`-wrapped on native, Worker-portable later. A straight-line fixpoint loop cannot be retrofitted.

### Parameterization (pinned in Phase 111)

**Carrier parameters stay real, read in the affine chart.** A constrained point's parameter (`PointOnObject.parameter`, arc/sector angular extents, segment/ray parameter extents, locus sweep variables) remains a real number against the carrier's *projected* affine view: signed arc-length along the oriented direction for lines (the `orientedAlong` anchor keeps direction V1-compatible), polar angle for circles. The parameter is a UI and persistence quantity — it is what a drag gesture sets, what the codec stores, and what extent clamping compares — so it must be real, invariant under rescaling of the carrier's homogeneous state, and meaningful to the user. Complexification happens on the *value* path only: tracing (Phase 113+) continues the constrained point's homogeneous coordinates along the drag path; it never continues a carrier parameter. When the carrier's projection is undefined (complex or fully at infinity), the constrained point has no chart to evaluate in and goes undefined with it.

- **Lines**: signed arc-length from `pointOnLine` along `direction` — unchanged. Bounded hosts (segments, rays, arcs, sectors) clamp into their extents on every recompute; gluing a point to the drawn extent is a UI concept on the rendered curve, not projective structure.
- **Circles**: polar angle — unchanged.
- **General real conics** (needed by Phase 119 rendering and Phase 120 five-point conics): stereographic parameterization — project from a chosen real point on the conic; rational in t, so evaluation is polynomial in homogeneous coordinates. Ellipses close up (t ∈ ℝ ∪ {∞}, one glue point), parabolas touch infinity once, hyperbolas twice.
- **Hyperbola at infinity**: no gluing through the asymptotic parameter values — each branch is a clamped real extent, like a segment. The UI never walks a parameter across infinity.

Rejected: projective parameters (RP¹ homogeneous pairs) or complex parameters. They make extent clamping, drag-to-parameter mapping, and persistence ambiguous for no payoff — analytic continuation operates on object values along the drag path, not on carrier parameters. (Clarified in Phase 116b: a traced *parameter drag* interpolates the real stored parameter, and a detour evaluates the dragged point's chart form at a complex path parameter strictly inside one pass — the value-path continuation above, never a complex parameter type: the stored parameter, clamping and persistence stay real throughout.)

### Locus on tracing (pinned in Phase 117)

`Locus.recompute` stays a sweep-and-restore over the fixed [chain], but the per-sample machinery of Phases 39b–f (uniform grid walked statically, defined↔undefined boundary bisection, `branchIndex` flipping, infinity tails) is replaced by the tracing engine. The design:

- **Sweep domain.** One real sweep parameter `u` per host: circle hosts sweep the angle (full turn cyclic, or the `angularExtent` bounded); segment hosts sweep the `parameterExtent`; a ray sweeps `φ ∈ [0, π/2]` with `t = origin + halfSpan·tan φ`; a full line sweeps `φ ∈ [−π/2, π/2]` with `t = center + halfSpan·tan φ`, **cyclically** — the domain is RP¹, `tan` is π-periodic, and a run may wrap through the driver's point at infinity (the Cinderella projective-driver semantics; before 117 the two grid edges were separate open ends). The tan substitution is the density profile the old grids encoded; the grids themselves are gone.
- **Drive.** The sweep drives the driver's homogeneous value directly (the `tracedPosition` mutation, now sanctioned for locus sweeps): interior real `u` lifts the chart evaluation with `w` exactly 1 (bitwise-identical to the static sweep); the bitwise domain edge of a ray/line host evaluates to the carrier's direction point (`w = 0`) — a fully projective chain takes its genuine value at driver-infinity, a chart-reading chain member goes undefined there, both honest ("infinity falls out of projection"; the tails' subpixel ladder is deleted). Complex `u` (detour arcs only) mirrors the chart ops over `Complex`, per the 116b convention. The stored `parameter` is untouched and restored bit-exactly with one chain recompute at the end.
- **Structure discovery.** A `sampleCount`-cell static scan (slots inactive — canonical branches, the old uniform sweep) still finds the defined runs, grouped cyclically on circle and full-line hosts. Each run is then *walked* by the tracing engine: chain `IntersectionPoint`s seeded from the run's start state, the shared acceptance rule (motion < min(sep/2, cap), collision refusal, coast-entry refusal), trial spans capped at one scan cell so polyline density never falls below the scan's.
- **Singularities met by the walk.** On starvation the singular `u*` is estimated (collapse law) and classified by a static probe past it: still defined → a **crossing** — a `DetourArc` in complex `u` continues the branch through it (the old machinery re-sorted canonically here and drew a kink; the traced curve is the fix the corpus goldens get regenerated for); undefined → a **fold** — the real curve turns: the walk Zenos in (its accepted steps are the old boundary ladder, stopped by the acceptance rule exactly at the kernel's epsilon-tangent zone, which fences the Phase 39d phantom), swaps each starving slot to its other candidate (the real-curve continuation through the coalescence — no complex machinery needed, and `branchIndex` is never touched), reverses direction, and continues.
- **Termination keeps the Phase 39c contract verbatim**: a parity set tracks outstanding fold swaps; a walk that returns to the original assignment *and* geometrically rejoins its start closes (figure-eights, tangency-bounded circles); any open termination — a genuine end reached while swapped, budget/segment caps — trims back to the last original-assignment sample. Never wrong ink.
- **What this deletes** from `locus.dart`: `_refineBoundary` (48-step bisection + ladder), `_infinityTail`, the tan sample grids, all `branchIndex` mutation and its restore bookkeeping. What it keeps: chain computation, cyclic run grouping, the trim rule, `coreSamples` (defined recorded positions inside the focus window).

Consequences the corpus tests are updated for (point-set-wise comparisons per the phase contract): interior crossings trace smoothly instead of kinking; full-line loci may connect through the driver's infinity (fewer components, limits touched exactly or asymptotically to ~1e-5 of the domain via coast-entry refinement); sample lists are adaptive, not grid-aligned (they already weren't after 39b).

### Root collisions: seen, measured, walked around (pinned in Phase 117b)

Two user documents (`apatitos-topos.rgl`, `locus-miss-2.json`) exposed three gaps in the 114–117 engine. All three are properties of *how a collision is detected and crossed*, not of the geometry, so they are pinned here rather than left as engine folklore.

- **A collision must never hide inside an accepted step.** The Cinderella bound compares a root's motion against the separation at the step's *start*, so it only ever sees a step's endpoints. Where two roots pass through each other **transversally** — separation vanishing *linearly*, the signature of a line drawn through a point that already lies on the curve being intersected (the "second intersection of `CD` with the circle `D` is on" — the commonest construction in the corpus) — the separation can dip to zero and recover inside one step while both endpoints stay comfortably separated and every root moves only a little. Nothing starves, no fold or crossing is classified, and nearest matching quietly keeps the *canonical index* rather than the analytic branch. The step is therefore capped by the extrapolated distance to the next collision (`collisionStepLimit`), which forces every collision to a step *end*, where refinement localizes it. The cap is self-scaling — a separation that is large, or shrinking slowly, extrapolates far ahead and throttles nothing.
- **The collision's parameter is measured, not extrapolated.** `estimateSingularParameter` fits the `s ∝ √(t*−t)` law of a transverse tangency, where it is exact and its near-miss *undershoot* is load-bearing (an undershot arc stays homotopic to the real path). On the linear law it undershoots by a factor that refinement does not improve, so the planned arc hugs the collision instead of clearing it — the detour then exits *nearer* the singularity than it entered and picks the wrong sheet on the way out. So when a detour is about to be planned, the walk brackets and ternary-searches the separation profile directly (`locateSeparationMinimum`): law-agnostic, a bounded handful of evaluations once per singularity. Its *depth relative to its shoulders* is also the crossing/near-miss discriminator the extrapolation cannot provide — a genuine zero bottoms out at solver noise, a miss keeps a finite fraction — so a miss falls back to the extrapolated estimate and its guarantee unchanged.
- **A detour arc must actually leave the real axis.** An arc's two endpoints are its real entry and exit, so a walk that accepts the whole semicircle in one trial has continued from one real parameter straight to the other — exactly the step across the collision the detour exists to prevent, and the acceptance rule cannot tell the difference (near a collision, both roots move little). Arc steps are capped at `π/4`, four minimum.

Two further rules follow from the same documents, about work the engine should not be doing:

- **Structural double roots never seed.** A point built as `TangentLine ∩ the circle it touches` has its two candidates coincident *by construction*, at every position of every parent. There is no second branch to hold identity against and no step size could separate the matches, so seeding it made the Cinderella bound refuse every trial: the controller halved to nothing and the whole pass starved and bailed — on every frame of every drag in the document. Slots whose candidates coincide within `doubleRootEpsilon` at seed time are left to resolve canonically (exact, when the candidates coincide) and the pass's other slots keep tracing.
- **Loci are held back during a tracing pass.** A locus is a DAG leaf — nothing may take one as a parent — so no acceptance decision can read one, while recomputing one is a whole traced sweep of its own. The walk recomputes the rest of the graph per trial and settles the loci once, at whatever state the pass ends on. This is what made the starving frames above *freeze* rather than merely stutter: a bailing frame paid `stepBudget` (~130) full locus sweeps before giving up. The Phase 116 performance gate never covered a construction carrying a locus; it should.

### The engine says what it costs (pinned in Phase 117c)

Both 117b documents came back still slow, and nothing in the domain layer reproduced it: on the VM every frame of both is well under a millisecond. That is the actual finding — not "it is fixed", but "the cost is not where we can see it", and an engine that cannot be asked what a frame cost cannot answer that question from a user's machine.

- **Frames are recorded, and a slow one reports itself.** `TraceDiagnostics` (pure Dart, armed in debug *and profile* builds) records per drag frame: wall time, the locus sweep's share of it, and counts of accepted/rejected trials, detours, folds, separation probes and — the unit that actually matters — **chain solves**, one recompute of the affected subgraph. Trials are not the currency: on `apatitos-topos.rgl` a frame ran 200 walk trials and **742 chain solves**, because a starving step that measures a collision spends probes nobody was counting.
- **A stall reports from inside itself.** A frame that never returns never ends, so the walks call `TraceDiagnostics.checkpoint` from their inner loops: once a frame overruns, it prints where it is and how far along, every second, until it finishes. This is the only instrumentation that survives the symptom being reported — a wedged tab.
- **Debug web is a different compiler, not a flag — and it is ~25× slower.** `flutter run -d chrome` is DDC; profile and release are optimized dart2js. Measured on the reported documents (`benchmark/run_locus_docs.sh`, which compiles them to every target): one `locus-miss-2.json` sweep is 504 chain solves and costs **5.6 µs/solve on the VM, 8.3 on dart2js -O4, 8.8 on dart2wasm — and ~200 µs/solve under DDC**. A 4 ms sweep becomes 178 ms. At two frames like that per pointer event the app crawls and then wedges, with nothing in the kernel looping and no defect to find. **Never judge kernel performance in a debug web build**, and when a report says "slow in Chrome", establish the build mode before anything else. The recorder is armed in profile precisely so the two can be diffed.
- **Sweep cost is set by the geometry, not by `sampleCount`.** The obvious mitigation — a coarse locus preview during a drag, full resolution at gesture end — is worth almost nothing: `locus-miss-2.json` at 128 samples is 504 chain solves, and at **16** it is still **349**, because the walk's step size is adaptive and the folds it must turn around at are properties of the curve. Measure before trading fidelity for speed here; the scan is only ~15% of a sweep.
- **Refine to the question being asked, not to the floating-point floor.** `locateSeparationMinimum` drove its ternary search to 1e-15 so that a *tight near-miss* could not be misread as a collision. But that precision is only needed to settle the **verdict**; once a probe has been below `doubleRootEpsilon` the verdict is closed for good and all the parameter is still for is centring an arc whose radius is a fraction of the same distance. Relaxing the stopping rule at that moment (`_collisionResolution`, 1e-4 relative) took a crossing from ~205 probes to ~35 and the document's frame from 742 chain solves to 442, with the goldens bit-identical. A near-miss still pays the floor, because that is the case the floor was bought for.

### A locus may lag the pointer (pinned in Phase 117d)

The 117c report resolved to "run a profile build", which fixed the reporter's afternoon and none of the underlying fragility: the app still did 500–900 chain solves per pointer event with no defence against those solves being slow. A slower machine, a heavier document or a phone puts it straight back into the same wedge.

- **A locus is the only leaf with unbounded recompute cost.** Everything else in a preview frame is a handful of solves; a locus is a whole traced sweep, and the count is a property of the curve — its folds, its crossings — not of any tunable (128 → 16 `sampleCount` saves a third). So on any document carrying a locus, the frame budget *is* the sweep's budget.
- **Nothing may depend on a locus being current.** It is a DAG leaf — `IntersectionPoint` and `PointOnObject` both refuse one as a parent — so no recompute and no acceptance decision anywhere can read its samples. A locus is pixels, and pixels may lag.
- **So during a preview it re-sweeps on a duty cycle of its own measured cost** (`LocusRefresh`, default share 0.5: sit out one sweep's duration between sweeps). The rule contains no wall-clock constant and so is self-tuning — a sweep inside the frame budget waits less than one frame and runs every frame, unchanged; a sweep 40× the budget updates 40× less often and the gesture stays live. Measured on `locus-miss-2.json`: at 60 Hz with a healthy sweep, **299 of 300 frames still sweep**; when frames arrive faster than the sweep can serve them, frame cost collapses from 2.09 ms to 0.01 ms and the locus coalesces instead of the app wedging.
- **Staleness lives and dies inside the gesture.** The last frame is not a preview — it arrives through the command, outside the scope — so what is committed, undone, redone, saved or hit-tested is always a fully current sweep. The invariant that matters is not "the locus is always current" but "the gesture's responsiveness does not depend on the sweep's cost".

### The version field is a requirement, not a build number (pinned in Phase 118)

V2's schema is version 2, and every V1 document ever saved is version 1. The obvious reading of "bump on any breaking change" is that the encoder then stamps 2 on everything — but that locks a user's older build out of documents it could read perfectly, which is a cost paid by real people for nothing.

- **The stamp is the *lowest* version that reads the document back correctly** (`requiredFormatVersion`). A document using nothing from v2 is written byte-identically to what a V1 build wrote, and opens in one.
- **What earns a bump is misreading, not novelty.** The codec has added keys three times without a bump — viewport rotation, the display flags, the locus params — because an older reader that skips them lands on exactly the defaults the file meant. A `kernel` block is different in kind: skip it and the document is drawn in the wrong geometry, silently. That is the only thing the version field can protect against, so it is the only thing that sets it.
- **v1 is permanent.** Not "kept for a migration window" — it is the format the entire installed base of documents is written in, and there is no event that makes dropping it acceptable. `test/fixtures/` is the corpus that holds the decode path to it: six real documents, swept data-driven, each of which must load with every object wired and survive decode → encode → decode with identical geometry. The version assertion on the corpus is what stops a v2 file being dropped in and quietly ending the coverage.
- **v1 needs no rewriting**, because v2 only adds. The migration is the defaults the v2 readers fall back to, which is why it is worth naming: `branchIndex` means the same thing in both (a canonical-order *seed*, re-derived at every traced pass end since Phase 116 — a v1 file was written by a build that had nothing else), and an absent kernel block is the Euclidean one every pre-M-CK document is in.
- **Two slots reserved with no user yet**, so that the first kind that needs them inherits a settled schema instead of also having to decide one: the kernel block (M-CK's fundamental conic — `euclidean`/`hyperbolic`/`elliptic` reserved as names, the two unimplemented ones *refused* rather than approximated) and homogeneous params (`{"h": [[re,im], …]}` — a `ProjPoint`, a `ProjLine` or a conic's six entries in one shape, each component a pair even when real; Phase 120).

### A conic is drawn by its own parameterization, and clipped exactly (pinned in Phase 119)

`lib/domain/projective/conic_shape.dart` is where a conic becomes ink: what class it is, where its curve goes, and which stretches of it a viewport can see. The painter and hit-tester arms are thin over it, and Phase 120's `FivePointConic` inherits the whole answer.

- **The class is how the conic meets the line at infinity.** Two real meets is a hyperbola, one doubled real meet a parabola, a conjugate pair an ellipse — real or imaginary, settled by whether a line through the centre meets it really. That is the classical definition and also the projective one, so it needs no world-space tolerance, and the same test hands back the real point the parameterization is seeded from. A hyperbola's two branches and a parabola's arm are then *not* cases in the code: they are the arcs between the parameters where the curve passes through infinity.
- **Classification runs in a balanced frame; everything else runs in the caller's.** The class is a projective invariant but asking for it numerically is not — a circle at (10⁶, 10⁶) is representationally a double line at 1e-9, and one at (300, −120) already read as a line pair before this phase. So the question goes to a copy with the centre at the origin and the blocks made commensurate (the Phase 105 recipe, applied to one conic rather than a pencil), and only the answers come back. `ConicMatrix.rank` was fixed on the way: comparing `|det|` against `eps·‖A‖³` asks `σ₃ > eps·σ₁²/σ₂`, far stricter than the conditioning question it meant to ask; against `eps·‖A‖·‖adj‖` it asks `σ₃ > eps·σ₁`. Rank stays a property of *the matrix as written* — the balancing belongs to the caller with the geometric question.
- **The sweep is stereographic, per §Parameterization**, with the rational parameter walked cyclically: `X(Q) = (QᵀAQ)·P₀ − 2·(P₀ᵀAQ)·Q` for `Q(φ) = e_i·cos φ + e_j·sin φ`, so the domain is RP¹ over `φ ∈ [0, π)` and `X` is exactly π-periodic. Polynomial in homogeneous coordinates, total, and free of the blow-up a bare `t = tan φ` would put on one point of the curve — the density profile the Phase 117 locus drive already uses on a full-line host.
- **The viewport clip is exact, not sampled.** A conic can only enter or leave the box across one of the four edge *lines*, and can only escape on ℓ∞, so intersecting with those five cuts the parameter circle into arcs that are wholly visible or wholly not; one interior sample classifies each, adjacent visible ones merge (a curve tangent to an edge from inside is cut where it never leaves and must not draw a seam), and survivors are walked to a flatness tolerance under a shared bisection budget. This is why the painter does *not* use the over-extend-and-let-the-canvas-clip trick that infinite lines use: a hyperbola runs off in two directions and there is no "far enough". Flatness is a screen-space budget converted to world units, so zooming out makes a conic cheaper, never denser.
- **The tap measures to the curve.** Degenerate conics answer exactly from their line components; a curve is answered by a coarse sweep whose *every* local minimum is refined, because the stationarity condition is quartic (≤ 4 stationary points, so a scan an order of magnitude finer cannot miss a basin, but its single best sample can sit in the wrong one where the parameter is stretched). Refinement is golden-section, not Newton: the bracket is already in hand and a tap has no performance pressure. The exact route — intersect with the Apollonius conic of normals through the tap, four feet, no iteration — is **rejected**, because it degenerates precisely where the conic is near-circular and would put the tap path through the pencil solver's hardest input for accuracy no tap can use. An ellipse's interior is not a hit: a conic is a curve, not a region. Band selection can only contain an ellipse, measured by `extremesAlong` (the polar line of a direction's point at infinity), exact in the band's own frame.
- **`isDrawable` is what `isDefined` means for a conic-valued kind** — the migration's "real and finite after projection", put to a conic. An isolated point (two conjugate complex components) is deliberately *not* drawable: it has a real point but no curve, and a conic's ink is its curve. Until Phase 121 renames it, conic-valued kinds live under `GeoCircle`, whose `circle` getter is the circle projection and whose default `isDefined` stays "projects to a circle" — so no existing circle kind changes meaning, and a conic kind overrides.

### The conic constructors, and where the metric enters (pinned in Phase 120b)

Five points determine a conic *projectively* — no distances, no angles, nothing a change of geometry could touch. The classical alternatives do not: a focus, a directrix, an eccentricity and a pair of foci are all **metric** data. That difference is not a footnote, it is the design, because it says exactly which constructors M-CK will have to re-found and which it will not. The user-facing shape is the DGS-standard set (five points, parabola, ellipse, hyperbola) plus the eccentricity generalization; the Conics toolbar group holds conic-*valued* kinds only, so tangent, polar and radical-axis lines stay in Lines — they are lines.

- **Focus–directrix is metric but still polynomial**, so `focalConicOf(F, ℓ, e)` needs no chart read at all:

  ```
  (a²+b²)·[(x·f_w − f_x·w)² + (y·f_w − f_y·w)²] − e²·f_w²·(a·x + b·y + c·w)² = 0
  ```

  holomorphic in every input, covariant under rescaling of `F` (by `μ²`) and of `ℓ` (by `λ²`) independently, and total. The Euclidean structure enters through exactly one coefficient, `a² + b²` — which is `ℓ` evaluated against the degenerate *dual* conic `diag(1,1,0)`, the dual of `{I, J}`. **That one factor is the whole of the geometry in this constructor**, so M-CK switches it by substituting the fundamental conic's dual and nothing else moves. One kind, `FocalConic`, carries the eccentricity as a param; the parabola tool is that kind at `e = 1`, which is why there is no separate parabola kind.
- **The bifocal conic is the one that genuinely needs the chart.** `|PF₁| ± |PF₂|` is a sum of square roots of real distances and is not polynomial in the homogeneous data, so `bifocalConicOf` reads the parents' *projections* — the sanctioned metric-boundary route of Phase 112, and the same place M-CK re-founds measurement. With the centre `O`, the focal vector `D = F₂ − F₁`, `c² = |D|²/4` and `a` from the branch, the conic is

  ```
  (a² − c²)·[(X−O)·D]² + a²·[(X−O)·D^⊥]² − 4c²a²(a² − c²) = 0
  ```

  — **one formula for both branches**: the sum branch has `a ≥ c` and gives an ellipse, the difference branch `a ≤ c` and gives a hyperbola, each by the triangle inequality, so the branch flag selects a definition rather than a case in the algebra.
- **The projective bifocal route is recorded and not built.** A point `F` is a focus of `C` exactly when the isotropic lines `F∨I` and `F∨J` are tangent to it, so the confocal family of `F₁, F₂` is a *pencil in the dual plane* through four fixed points, and "`P` on `C`" is quadratic in the pencil parameter — its two roots are precisely the ellipse and the hyperbola the branch flag names. Elegant, and rejected for now: it points the Phase 102 pencil machinery at a case the chart answers exactly and cheaply, and buys nothing until M-CK, which is when to revisit it.
- **Degeneracies stay total and unbanded**, per the standing Phase 110 rule. Ellipse branch with `P` on the segment `F₁F₂` → `a = c` → the axis doubled; hyperbola branch with `P` on the perpendicular bisector → `a = 0` → that bisector doubled (which is the honest limit: `|XF₁| = |XF₂|` *is* the bisector); focus on the directrix, or a focus at infinity, flattens the focal conic onto its own degenerate limit. The one guard is **coincident foci**, refused at `projectiveEpsilon` like `carrierThrough`: the branch has no meaning there and the circle through `P` is `CircleCenterPoint`'s job, not a limit for this kind to invent.

### A round trip is honest: the detour half-plane is constant (pinned in Phase 120c)

A drag detours around a singularity through one half-plane of the path parameter, and the choice of half-plane decides what a **round trip** does. A return pass parameterizes the reverse path, so its `Im s > 0` is the outward pass's `Im t < 0`. Hence:

- A **constant** half-plane sends the outward leg over the branch point and the return leg under it. The round trip closes a loop, and a loop around a branch point is not the identity: the two roots trade places. Going round again trades them back, the root split being an involution. This is the **honest monodromy** of the configuration, and it is Cinderella's behaviour.
- A half-plane **odd in the drag direction** makes the return leg retrace the same physical side, winding zero net turns, so every round trip restores every branch — *reversal-identity*.

Phases 115–120b shipped reversal-identity. **Phase 120c switched to the constant, on the user's call**, and the reasoning is worth keeping because both options work:

- Reversal-identity's observable — "dragging away and back changes nothing" — *hides a real feature of the geometry*. The two intersection points of two circles genuinely are the two sheets of a square root over the configuration space, and a loop enclosing the branch point genuinely exchanges them. A kernel bought specifically to be honest about complex structure should not spend that honesty on making the honest answer invisible.
- Reversal-identity is also the harder one to get right, because it *needs the drag direction*. Any ±1 rule on directions has a **seam** — two antipodal directions where it flips — which is a topological fact about odd maps to `{±1}`, not a defect of a particular rule. The shipped rule's seam sat on the horizontal axis (it read the sign of `dy` and consulted `dx` only when `dy` was exactly zero), which is precisely where "drag two equal circles onto each other" lives: `dy` was pointer noise, and a twentieth of a pixel of it flipped the outcome about a third of the time. A constant reads nothing about the gesture and so has no seam at all.

So the constant is both the honest convention and the robust one. Measured through the drag session, the way the app runs it: away-and-back swaps the crossing, twice restores it, and every one of 30 (jitter × seed) combinations per trip count agrees.

**The non-uniformity it recorded is closed (Phase 121), and closing it says when the half-plane matters at all.** Locus sweeps kept their own rule (`detourOrientation1D`, odd in the drive direction, so a run and its reverse detoured through the same *physical* half-plane) on the grounds that a scan has no round trip to be honest about and the 117b fixtures pin its sheet choices. Unified onto the one constant `detourHalfPlane`, the fixtures do not move — bitwise — and the reason generalizes: an arc is planned to enclose **one** estimated singularity and encircles it by a half-turn whichever side it passes, and for a simple branch point a half-turn in either sense exchanges the same two sheets. The orientation can therefore only be load-bearing when an arc encloses more than one collision, or one of higher order, and there the arc is mis-planned and neither rule has a claim to the right answer. What a locus needed was a well-planned arc, not a half-plane of its own. Measured: `apatitos-topos.rgl` is the only corpus document that detours (twice, both on forward legs — exactly where the two rules disagreed), and its samples are identical under the odd rule, under `+1` and under `−1`; the reduced rig in `locus_test.dart` is the only other detour coverage, and it now pins that it *does* detour, so the sheet assertions over it are known to be testing something.

### Two intersection points may never share a branch (pinned in Phase 120c)

`IntersectionPoint` is addressed by `(curve1, curve2, branchIndex)`. Two points carrying the same triple are **the same intersection by construction**: they resolve to the same candidate on every recompute, for ever, and no drag, trace or adoption can separate them. What the user sees is two points stacked on one crossing while another crossing sits empty — and tapping the empty one builds *another* point, so they accumulate. The failure is silent and permanent, and it can be baked into a saved file, so it is worth defending at every route that can produce it rather than at the one that happened to:

**One address space per pair, first.** Everything below compares `branchIndex` values, and that is only meaningful if they mean the same thing. `branchIndex` addresses the canonical order of `intersectionCandidates(curve1, curve2)`, whose ordering key is the directed centre line `curve1 → curve2` — so the reversed pair is a *different* order. Worse, it is not a fixed permutation of it: reversing flips the real-finite tier and leaves the points at infinity and the non-real ones alone, so how the two orders correspond depends on how many candidates are currently real, which changes as the parents move. Two points on one curve pair but opposite orderings therefore live in two incompatible address spaces; they drift onto one crossing under a drag, and no guard that compares indices can see it happening. `IntersectionPoint` accordingly **stores its pair in canonical order** (object id ascending) whichever way round the caller names it, renumbering the requested branch onto that order at construction. Which order is canonical carries no meaning; that every point on a pair shares one does. This is what makes the three guards below total — it was the last root cause of the reported conic defect, found by reproducing a screen recording of the failing session.

- **Creation.** `IntersectionTool` refuses a tap on an occupied branch — building the candidate *before* the check, so the address compared is the canonical one, and a point built by tapping the two curves the other way round compares equal.
- **Adoption.** A traced pass writes `branchIndex` back per point, under per-point guards (a coasting slot adopts nothing, a double root adopts nothing). Partial adoption is therefore possible, and a *stale* index can collide with a freshly adopted one. Adoption is **atomic per pair**: either the whole group takes its new indices or the group keeps every old one. Collision refusal already makes a collision unreachable within a pass, so this is belt to that braces — cheap, and the failure it guards against is unrecoverable.
- **Loading.** A document written by an older build can carry the duplicate — and canonicalizing an old file's reversed pair can itself land two points on one crossing. The reader separates them onto unclaimed crossings of the same pair (two passes, so a duplicate is never moved onto a crossing a later point legitimately holds), and reports the ids it moved. This is a *repair*, not a migration: no format change, no version implication — a v1 and a v2 reader disagree about nothing here, they simply both read a document that should never have been written. Re-saving makes the fix permanent. Canonical order needs no version stamp of its own either: no build writes a non-canonical pair, so finding one in a file *is* the marker that it predates this.

The one case that cannot be repaired is a document holding **more intersection points than the curves have crossings** — four crossings cannot host six points however they are re-pointed, and the surplus has to be deleted. That is a user decision, not the decoder's.

**Every bound on `branchIndex` derives from `maxBranchCount`.** Recorded here because three separate hand-written `0..1` literals survived into the conic era and each failed differently: the constructor threw on the third crossing of two conics (120b); the pass-end adoption step silently collapsed branches, because capping adoption makes it *asymmetric* — indices inside the cap write back while indices outside do not, so two branches converge onto one stored index; and `setIntersectionBranch`, the primitive a *committed* re-pointing goes through, threw out of the drag's own command, which is why the crossings kept merging in the app after the engine had stopped merging them (both 120c). The bound is on the addressing space, never on the current candidate count — that varies as parents move, and `recompute` clamps to it.

### A crossing the construction already knows is named, not navigated (pinned in Phase 135)

`branchIndex` addresses a **geometric** order — for line ∩ circle, position along the line's direction. A geometric order exchanges two roots wherever they coincide, so a point holding "the second crossing" quietly becomes a point holding the first one as soon as the figure moves through that coincidence. Tracing was built to carry identity across exactly this, and it cannot be the whole answer, because the flip also happens with no drag at all: *loading* a document at the wrong side of a coincidence resolves it wrongly, and so does every static recompute.

The decisive observation is that these crossings are not generic. For a real quadratic the two roots can coincide **and stay real** only where the discriminant touches zero without changing sign — which is to say, only where one root is pinned by the construction. A real transversal root exchange and a structurally shared point are the same phenomenon. (Where no root is pinned, the roots coincide and go complex: that is a fold, and folds are what the detour machinery is actually for.)

So the fix is to stop navigating and start naming. When `sharedIncidentPoints(curve1, curve2)` is non-empty — the two curves have a point on both **by construction**, `incidence.dart`'s zero-epsilon relation — an `IntersectionPoint` on that pair holds a **structural role** instead of a geometric address: it is one of the shared points, or it is the root left over when they are divided out. Deflation is exact, total and continuous; there is no crossing to carry, no budget to spend and nothing for a static recompute to get wrong.

**The role is derived, never stored.** It settles once, from the first state that can answer unambiguously, by asking which candidate the point's geometric address currently names. A document therefore loads with the role it was saved with, because it is read back off the same geometry — **no format change, no version bump, no migration, and no fixture rewrite**. Making the structural order the stored address would need all four, and buys nothing a derived role does not already give. Ambiguous states settle nothing: coincident candidates, or a shared point that is undefined, leave the point on geometric addressing until a state that can answer.

Two boundaries are deliberate. Deflation names the *left-over* root only when exactly one is left over, so a conic pair with four candidates and one shared point still addresses geometrically — it has three left over and no way to tell them apart. And `sharedIncidentPoints` reads only *defining* points, so a crossing shared by a theorem `incidence.dart` does not model is not found. That is a missed deflation, never a wrong answer, and the detour path still covers it — which is now the only thing that reaches it, so its test rig hides an incidence on purpose (`locus_test.dart`, `drag_crossing_test.dart`).

This was found from a user report — "the locus is full of straight lines and it disappears when the points go past a certain limit" — whose second half had been mis-attributed to the drag step budget across two phases. It is not the budget: the document's `G` is the intersection of a circle *through* `F` with a line *through* `F`, so past either coincidence `G` was bit-identical to `F` and the locus of `G` was the x-axis. Phases 133–134 chased a crossing the engine never needed to cross.

### The hot loop was not where the phase said it was (pinned in Phase 122)

Phase 122 was written as "tracing inner loop fully on SoA `Float64List` (no boxed `Complex` in the hot loop)", on the Phase 101 finding that boxed complex arithmetic allocates. Measured before rewriting anything, that item targets **1.4%** of the cost, and the real hot loop is one function.

- **Measure the split before optimizing it.** On a traced `IntersectionPoint.recompute` (VM), `TracedBranch.follow` — the whole nearest-root match, motion and separation bookkeeping — is 43 ns against the recompute's 3044; `checkpoint` is 11 ns and `restore` 6. Everything else is `intersectionCandidates`. SoA-ing the tracing slot is therefore worth at most a percent and a half, whatever it does to allocation counts, and the phase's remaining items are re-pointed at the function that holds the time.
- **Two circles need no cubic.** `intersectionCandidates` on two circles cost 2875 ns against line∩conic's 363 — 8× — because it went through the general four-root pencil route: balance, cubic, root clustering, member scoring, adjugate split, and then discard I and J, which it had just recovered numerically and which are *known*. But a conic is a circle exactly when it passes through I and J, which is exactly the coefficient shape `xy = 0`, `xx = yy`; and for two of those the combination `b.xx·A − a.xx·B` kills the quadratic block outright, leaving `w·(2Dx + 2Ey + Fw)` — **the pencil's degenerate member in closed form, the line at infinity together with the radical axis.** Steps 2–4 of the recipe collapse into two subtractions, and `ℓ∞ ∩ circle` returns I and J exactly instead of at `|w| ~ 1e-33`.
- **The dispatch test is exact, deliberately.** Every constructor in `circles.dart` emits `xx` and `yy` as the same expression, so the shape holds bitwise; a general conic that merely *happens* to be round — a `FivePointConic` through five concyclic points — misses it by rounding and takes the general route, which is correct and only slower. An exact test needs no tolerance and can never misroute a conic that is not a circle.
- **What does not change is the whole point.** The closed form replaces *finding the degenerate member*, and nothing downstream: the same `_canonicalOrder` runs over its output, so the branch orderings `branchIndex` addresses are the same ones — checked by the existing V1-agreement and complex-rescaling properties, which now run over the short route, and by asking the general route the same question through a conic nudged 1e-30 off the circle shape (400 pairs, both regimes, index for index). The Newton polish goes with the cubic: it cleans up a member found at an inexact root, and there is no such root here.
- **The translation balancing stays, because it is load-bearing** — and is free here, a circle's centre being `(−xw/xx, −yw/xx)` with no adjugate to form. Unbalanced, the closed form loses digits quadratically in the offset exactly as the general recipe's step 1 warns: two unit-scale circles at 1e6 come out 2e-5 off, against the balanced form's 1.3e-10. (Both routes give up near 1e9, where `ww ≈ 2e18` has swallowed the radius in the conic's own entries — the representation, not the algorithm.)
- **Then canonical ordering was half of what remained, and most of that was a tie-break nobody reached.** With the cubic gone, `_canonicalOrder` was 505 ns of the surviving 1080. Not, as expected, in recovering the two centres — handing those in costs 56 ns, worth having since a circle's pole of ℓ∞ is `(−xw : −yw : xx)` off the coefficients, but no more than that. It was in building four `_OrderKey`s eagerly: the lexicographic tie-break coordinates, and a `ProjPoint.normalized` behind each non-affine one. A circle pair gives two real points and then I and J, where tier and primary always decide, so those four lists were built and thrown away every solve. Built lazily instead — same rule, same comparisons, decided at the same place.
- **Measured end to end** on `locus-miss-2.json`, whose chain is circle∩circle: **5.85 → 3.02 µs/solve** on the VM, 8.53 → 3.47 AOT, 8.28 → 3.92 dart2js, 8.65 → 3.69 dart2wasm; the sweep drops from 4.30 to 1.75 ms on AOT. `intersectConicConic` on two circles goes 2676 → 947 ns. Solve *counts* are identical (504), so the walk made the same decisions, and `apatitos-topos.rgl` — line∩circle throughout — is unchanged at 2.04 µs, which is the control that says the win is where it was claimed. 32 goldens byte-identical, the tracing gate's checksums identical.
- **The compile target is dart2wasm, and the choice was not close on the thing it decides.** dart2wasm beats dart2js on raw complex arithmetic by 1.4–1.7× (boxed quadratic 31.4 ns vs 52.0, boxed cubic 114.8 vs 160.0) and is a wash on the whole engine, where allocation and dispatch dominate (`locus-miss-2` 3.69 µs/solve vs 3.92, the drag gate 0.128 ms/frame vs 0.140, but `intersectionCandidates` on two circles 2345 ns vs 2060 — dart2js wins that one). What settles it is that `flutter build web --wasm` emits **both**: a WasmGC browser fetches the 2.4 MB `main.dart.wasm`, anything older falls back to the 2.8 MB `main.dart.js` it would have received anyway. Modern browsers therefore download *less* and run the kernel faster, and no browser is dropped; the only cost is ~2.4 MB more in the Pages artifact. The deploy workflow is switched, and the browser smoke is **green as of 2026-08-18**: the build boots and draws from the Pages deploy, WasmGC path included.
- **The drag budget is a gate, not a printed opinion.** `benchmark/tracing_bench.dart` now throws when a frame exceeds `dragFrameBudgetMs`, so a job can enforce it without parsing text (thrown rather than `exit`ed, because `dart:io` would cost the file its js and wasm targets). Standing measurement, all four targets: 1–2% of the 8 ms budget on the plain stress construction, 7–11% with the 128-sample locus. `.github/workflows/benchmarks.yml` runs the suite on every push to main and is **informational** — a shared runner's absolute timings are not what this budget is about, and the numbers that decide anything are taken locally with the per-target scripts.
- **The tracing slot is 3–6% of a traced recompute on every target** (VM 4.1%, AOT 5.7%, dart2js 6.1%, dart2wasm 3.0%) — measured again after the above, since removing 60% of the solve raises the slot's share without changing its cost. `benchmark/chain_solve_bench.dart` is that breakdown, kept so the SoA question is decided on a current number rather than on the Phase 101 prior.
- **So the SoA rewrite is closed as not worth doing, and that is a measurement, not a reversal.** Phase 101's benchmark stands and its numbers are real: unboxed struct-of-arrays beats boxed `Complex` by 1.30–1.78× *on the arithmetic itself*. Applied to a slot that is 3–6% of a recompute, that is a ceiling of 1–2.5% of a drag frame — below the run-to-run noise of the gate it would be measured on. The prior was sound when it was formed (before there was an engine, the arithmetic was all there was to look at); what it could not know is how little of a frame the arithmetic-heavy *slot* would end up being, next to the graph recompute around it. Phase 101's real dividend was the shape it pinned for `TracedBranch`'s storage, which is already there.
- **Unboxing the kernel is the different question, and it is not this phase's.** The 85–97% lives in `intersectionCandidates`, and 1.3–1.8× is available there in principle. It would mean unboxing `Complex`, `ProjPoint` and `ConicMatrix` through the pencil, the line∩conic solve and the ordering — the most correctness-critical code in the project, all of it specified against `test/v1_oracle/` and none of it currently a bottleneck: the gate sits at 1–2% of budget plain and 7–11% with a locus. **The algorithmic route already beat what representation was promising** — 2.8× on the dominant op, from deleting a cubic that never needed solving — at a fraction of the risk, and it is worth noting that it was invisible until something measured *which function* the time was in rather than which representation it used. If throughput ever becomes the binding constraint again, look for the next such algorithm before reaching for the representation; open a phase for the rewrite only if that search comes up empty.

## M-CK — Cayley–Klein non-Euclidean geometries (opened at Phase 123)

The fundamental conic — *the absolute* — becomes a per-construction setting: Euclidean = the degenerate conic {I, J}; hyperbolic = the unit circle (Beltrami–Klein); elliptic = the imaginary unit conic. Incidence is projective and does not move: joins, meets, intersections, poles, polars, tangents and the five-point conic need **zero changes**, which is the dividend Phases 103–110 were bought for. *Measurement* is where geometry lives — distance and angle become cross-ratio logarithms against the absolute — and perpendicularity is conjugacy with respect to it, which is Phase 107's I,J formulation with the absolute substituted. UI is a construction-level mode with disc-boundary rendering for hyperbolic; the setting persists through the Phase 118 codec hook, which has reserved the three names and *refused* the two unimplemented ones since that phase. Scope guard: **no Poincaré model-switching in v1 of this milestone.**

### The absolute is carried as its dual (pinned in Phase 123)

The obvious carrier is the conic itself, and for two of the three geometries that works — a proper absolute is its own dual up to the adjugate. It does not work for the one every existing document is in, and the reason is sharper than "degenerate": the Euclidean absolute **as a point conic is the doubled line at infinity `w² = 0`, which is rank 1**, and the adjugate of a rank-1 matrix vanishes identically. So the dual is not ill-conditioned to recover, it is *unrecoverable* — the point conic has forgotten it. The dual is the point pair {I, J}, rank 2, `diag(1, 1, 0)`, and it has to be written down. (The two are easy to conflate because {I, J} is the name usually given to "the Euclidean absolute"; that name is the dual's.)

- **The code already reads the dual, everywhere it reads the metric at all.** Perpendicularity of two lines is conjugacy in the dual, `ℓ₁ᵀC*ℓ₂ = 0`, which for `diag(1,1,0)` is `a₁a₂ + b₁b₂ = 0` — the familiar test, and exactly what `euclidean.dart`'s `normalDirectionOf` encodes. Phase 120b found the same thing from the other end: the whole of the Euclidean structure in `focalConicOf` is the single coefficient `a² + b²`, which is `ℓ` evaluated against `diag(1,1,0)`. Two independent arrivals at the dual is the argument for making it the primary field.
- So an `Absolute` value carries **both matrices, with the dual primary**, and the three named instances supply both explicitly rather than deriving one from the other. Deriving is what fails on the Euclidean case, and the Euclidean case is the default.
- Points and lines therefore switch geometry by *substitution*, not by branching: the metric kernels take an `Absolute` and the Euclidean instance reproduces today's arithmetic bit-for-bit. **That bitwise property is the phase's gate** — the entire suite must stay green with the absolute threaded through, before any second geometry exists to compare against.

### Four tiers of kind, not two, and the affine one is the finding (pinned in Phase 123)

The outline said measurement switches and incidence does not. Between them sit the *affine* kinds, and they are the milestone's real cost. The tiers, and the audit that filled them in, are below; the counts are the audit's, not the import census's, which undercounted badly (§"The audit").

1. **Incidence** — joins, meets, `IntersectionPoint`, `PolarLine`, `TangentLine`, `FivePointConic`, `HarmonicConjugatePoint`. Projective, untouched, and the reason the kernel track was worth doing.
2. **Affine (ℓ∞-founded)** — `Midpoint`, `Centroid`, `ParallelLine`, `TranslatedPoint`, `SegmentRatioPoint`, `HomotheticPoint`, `CentralReflectionPoint`. These read the *line* at infinity rather than the two points on it, and ℓ∞ is distinguished **only because the Euclidean absolute is degenerate and ℓ∞ is the line carrying it**. With a proper absolute conic there is no distinguished line, so nothing here is automatic. They split by whether the construction is secretly harmonic:
   - `Midpoint` generalizes **verbatim in form**. The affine midpoint of `A`, `B` is the harmonic conjugate of `AB ∩ ℓ∞` with respect to `A` and `B`; the CK midpoint is the harmonic conjugate with respect to the absolute's two points on that line, and Euclidean is the degenerate limit where those two coincide. Same construction, absolute substituted — the same shape as perpendicularity. (With a proper absolute there are *two* such points, internal and external, so it acquires a branch, like the bisector pair.)
   - `ParallelLine` does **not** generalize. "The parallel through `P`" is a uniqueness that hyperbolic geometry exists to deny. It is **refused** in non-Euclidean modes, not approximated — the same rule the codec already applies to an unimplemented metric, for the same reason: drawing the wrong geometry silently is the one outcome worth refusing a document over.
   Which side each of the seven falls on is audit work, not prose work.
3. **Metric (I,J-founded)** — the perpendiculars and bisectors, every circle kind, `ReflectedPoint`, `RotatedPoint`, `ProjectionPoint`, the triangle centres, `FocalConic`, `BifocalConic`. These substitute the absolute and are the bulk of the milestone. A circle is a conic through I and J; under a proper absolute it is a conic **bitangent to the absolute**, which is a different shape, so the notion generalizes but its coefficient test does not.
4. **Chart-metric (the measurements)** — `DistanceMeasurement`, `LengthMeasurement`, `AreaMeasurement`, `VertexAngle`, `LineAngle`, `SlopeMeasurement`. Phase 112 already named this boundary and said M-CK re-founds measurement exactly here; that is now literal. These become cross-ratio logarithms against the absolute. `SlopeMeasurement` is Euclidean by definition and is refused.

**Phase 122's circle fast path is Euclidean-specific and is safe anyway** — worth recording, because it looks like a correctness dependency hiding inside a performance optimization and is not one. `intersectionCandidates` short-circuits two circles on the exact test `xy = 0, xx = yy`, which is the *Euclidean* circle shape. Under another absolute a "circle" is bitangent to it and does not have that shape, so the test simply does not fire and the general pencil route runs — correct, only slower. The dispatch being exact rather than tolerant is what makes this automatic; a tolerance would have had to be re-derived per geometry.

**The metric is one operation, not a scattering — pole/polar against the absolute, plus harmonic conjugation.** This is the audit's structural result and it is what makes the milestone tractable. Read as projective constructions rather than as formulas, most of tier 2 and tier 3 are already the CK construction with the Euclidean absolute substituted in:

- `perpendicularThrough(P, ℓ) = P ∨ normalDirectionOf(ℓ)`, and `normalDirectionOf(ℓ)` **is** the pole of `ℓ` w.r.t. the absolute. Generalizes verbatim.
- `ReflectedPoint` is the harmonic homology with axis `ℓ` and centre the pole of `ℓ`; `CentralReflectionPoint` is the harmonic homology with centre `C` and axis the polar of `C`, which under the Euclidean absolute is ℓ∞ — which is why it currently reads as an affine homothety of ratio −1. Both generalize verbatim.
- `Midpoint` is the harmonic conjugate of `AB ∩ ℓ∞`, i.e. of the absolute's points on `AB`, as above.

So the tier-3 work is largely *rewriting formulas as the pole/polar constructions they already are* and then substituting — not inventing per-kind CK geometry. The exceptions are real and are where Phases 124–125 will actually spend: `Incenter` and `InscribedCircle` route through `triangle_centers.dart`, which computes in `Vec2` and lifts back, so they need re-founding rather than substitution; `RadicalAxisLine` relies on the exact Euclidean circle coefficient shape; `CircleCenter` is `poleOf(ℓ∞)` and the CK centre is the pole of the chord of contact with the absolute, a different line; `FixedRadiusCircle` carries a **radius as a stored param**, which is a metric quantity and so changes meaning with the geometry; `BifocalConic` was already recorded in §"The conic constructors" as the one that genuinely needs the chart.

**`branchIndex` addressing is relative to the absolute, and that is the milestone's sharpest constraint.** `intersectionCandidates` filters `isCircularPoint` out of its candidate list on *both* the line∩conic and conic∩conic routes, and `_canonicalOrder` keys on the directed centre line, a centre being `poleOf(ℓ∞)`. Both are Euclidean. So the candidate list a `branchIndex` addresses — the address space every saved document is written in, and the one PLAN calls permanent — **is a function of the document's absolute.** Consequences, all of which land on the milestone rather than on Phase 123:

- Per-document this is consistent: the absolute is fixed at load, so a document's addresses mean what they meant when it was saved. Nothing existing breaks.
- **Switching a live document's geometry is a re-addressing event**, not a display setting. Every `IntersectionPoint` may need re-pointing, by chordal match, exactly as the Phase 120c decoder repair re-points a duplicate. The alternative — refuse to switch a document containing intersection points — is worse UX for the same correctness.
- This is precisely the failure class Phase 120c spent a phase on (two points silently sharing one crossing, permanently, saveable). The mode switch must go through a command that re-points and reports, or it will reproduce it.

### The threading decision, closed on the audit (pinned in Phase 123)

The previous section left this open pending the caller count, on Phase 122's rule. The count came back **38 of 50**, so the ambient setting is not an exceptional dependency to be smuggled in — it is nearly universal, and a nearly universal dependency belongs in the signature.

**`GeoObject.recompute()` gains the absolute as a parameter.** The twelve tier-1 kinds ignore it. This keeps every kind a pure function of (parents, params, ambient), keeps the domain layer free of ambient state, and — the property M-CK actually needs — lets a test ask one kind the same question under two geometries with no global to set and unset.

Rejected, with reasons, so they are not revisited: a **back-reference** from `GeoObject` to its `Construction` puts a cycle in the model and forces a whole `Construction` into every stub test, of which this suite has many; a **scoped ambient value** keeps the signature but reintroduces exactly the hidden global state the pure-domain rule exists to prevent, and would be read from inside a traced pass, where it would be invisible. The reuse contract's protection of `construction.dart` is of its *algorithm* — insertion-order-is-topological-order, the dependents map, one notification — not of the arity of the call it makes seven times.

### Angle unifies, distance does not (pinned in Phase 124)

The phase was written as "the tier-4 kinds re-founded on cross-ratio, with Euclidean as the degenerate case that reproduces today's numbers". Measured before building anything: **that is true of angle and false of distance**, and the split is not an implementation detail — it is the Cayley–Klein classification arriving as a constraint on the code. Distance and angle are each independently *elliptic*, *parabolic* or *hyperbolic* according to how the absolute meets the line (or pencil) being measured along, and the three geometries sit like this:

| geometry | distance | angle |
|---|---|---|
| Euclidean | parabolic | elliptic |
| hyperbolic | hyperbolic | elliptic |
| elliptic | elliptic | elliptic |

- **Angle substitutes, and at the bilinear-form level rather than through logarithms.** `cos θ = |⟨ℓ,m⟩*| / √(⟨ℓ,ℓ⟩*·⟨m,m⟩*)` against the *dual* absolute is Laguerre's cross-ratio formula with the logs cleared — no root-finding, no branch choice, no complex log. Under `diag(1,1,0)` the pairing is `a₁a₂ + b₁b₂`, so the formula **is** the textbook Euclidean angle between two lines, not a limit of it. Measured agreement with the chart route: **7.4e-13** over 20k random line pairs. That one number is what makes M-CK a substitution rather than a rewrite.
- **Distance dispatches, because Euclidean distance is not a cross-ratio at all.** A line meets the Euclidean absolute — the *doubled* line at infinity — in one point twice, and a cross-ratio with a repeated point is identically 1, so its logarithm is identically 0 for every pair of points at every constant. Recovering Euclidean distance needs the constant to diverge exactly as the absolute degenerates, which is not a formula anything can evaluate. The algebraic form of the same fact is that `⟨P,Q⟩ = w₁w₂`: the Euclidean point pairing has *forgotten where the points are*. This is the same statement as "Euclidean geometry has similar triangles" — there is no absolute unit of length, so length cannot be projective.
- **So `DistanceMeasurement` keeps the chart under Euclidean, and that is not a shortcut** — the chart is the only place the quantity exists. `VertexAngle` and `LineAngle` also keep their exact chart answer under Euclidean, but for the opposite reason: there the chart formula already *is* the CK one, so the specialization is exact, cheaper, and keeps a right angle reading exactly π/2 instead of π/2 plus rounding. Both are the Phase 122 circle-fast-path rule — the general formula is the definition, the specialization is what runs where it is exact, and the agreement is proven by test rather than by routing everything through the slow path.
- **A marker is not a measure.** `GeoAngle` grew `measure` beside `angle` because the two part company under a proper absolute: the marker arc is still drawn between the same two chords at the same screen vertex, while the number is the CK angle. Same rule as a measurement's anchor — an anchor is where a label is drawn, not something measured.
- **Three kinds do not generalize, and say so rather than reporting a Euclidean number.** `LengthMeasurement` and `AreaMeasurement` are *integrals*, not substitutions: a hyperbolic circle's circumference is `2π·sinh r` and a hyperbolic triangle's area is its angular *defect*, neither of which shares any algebra with the formula it would replace. `SlopeMeasurement` is a ratio of chart coordinates against a distinguished pair of axes, and neither survives a change of absolute. Undefined is the honest answer; a chart number would silently be the Euclidean answer to a question the document is not asking.
- **Which lines are isotropic is itself a fact about the geometry**, and it is easy to trip over: `3x − 4y + 5 = 0` is an entirely ordinary Euclidean line and is *tangent to the hyperbolic absolute* (its distance from the origin is exactly 5/5 = 1), so it has no hyperbolic angle to anything. Found by a test that picked it for having integer coefficients, and kept as a case.

### Two constructions, one algebra (pinned in Phase 125)

The audit predicted that most of tiers 2–3 would generalize by substitution. The sharpest instance is that **the midpoint and the angle bisector are the same construction, dually**, and the derivation is worth keeping because it also explains a familiar asymmetry.

A midpoint of `P`, `Q` is a point of the pair harmonic both to `{P, Q}` and to the two points where the line `PQ` meets the absolute. Parameterize that line as `X(t) = P + t·Q`, so `P` is `t = 0` and `Q` is `t = ∞`. The absolute meets it where `⟨Q,Q⟩t² + 2⟨P,Q⟩t + ⟨P,P⟩ = 0`. Being harmonic to `{0, ∞}` forces the pair to be `{m, −m}`; being harmonic to the two roots then forces `m² = t₁t₂ = ⟨P,P⟩/⟨Q,Q⟩`. Hence

```
M± = √⟨Q,Q⟩·P ± √⟨P,P⟩·Q          B± = √⟨m,m⟩*·ℓ ± √⟨ℓ,ℓ⟩*·m
```

the second being the identical argument run in the dual conic over the pencil through `ℓ ∧ m`.

- **Euclidean falls out of both.** `⟨P,P⟩ = w²`, so the midpoint formula reads `w_Q·P ± w_P·Q`: the plus branch is the affine midpoint and the minus branch is the point at infinity in direction `P − Q`. That second root is the **external midpoint**, and its sitting at infinity is exactly why Euclidean geometry appears to have one midpoint rather than two. Dually `⟨ℓ,ℓ⟩* = a² + b²`, which is precisely the √-unitization `twoLineBisectorOf` already used — so that function was the general one with I and J substituted in, all along.
- **Euclidean keeps its own formula anyway, and here the reason is not speed.** The general form picks a *pair*; the Euclidean representative-based formula picks which member is "the" midpoint. `√(w²)` is `|w|`, so the general form silently takes the other member whenever `w < 0`. Which member is "the" one is a ray concept the projective pair cannot carry — the same caveat `angleBisectorOf` has always documented for internal-vs-external.
- **Conjugacy is perpendicularity, and that needs its own case.** Under a proper absolute a line and its perpendicular can sit on opposite sides of it — one meeting it really, one not — so `⟨ℓ,ℓ⟩*·⟨m,m⟩*` is negative and the arccos argument is imaginary. A vanishing pairing between two *non-isotropic* lines is a right angle regardless, by definition, and has to be tested before the ratio. The isotropic test comes first in turn: a line in the dual form's **kernel** — ℓ∞ under the Euclidean absolute — pairs to zero against everything, which is degeneracy, not universal perpendicularity.
- **Every measure removes a global phase before pairing.** The CK constructions take a square root of a form that is negative on the interior of the absolute, so they routinely return a real element scaled by `i`; an unnormalized pairing against a real element is then imaginary and the realness gate rejects a perfectly good pair. The normalization divides by the pivot's unit **phase**, not by the pivot itself, because it has to be *exact*: a real triple divides by ±1 and an i-scaled one by ±i, both bit-exact, where dividing by the component would rescale and round — and the perpendicularity test above is an exact zero, so a canonicalization that turned it into 2.7e-17 would lose every right angle it touched.

### A circle follows its distance measure (pinned in Phase 125)

Phase 124 found that angle substitutes and distance dispatches. **Circles inherit the split**, because a circle *is* a level set of distance — so the same fault line runs through the constructors, and `ck_circles.dart` is a companion to `circles.dart` rather than a generalization of it.

- Under a **proper** absolute, `d(C,X) = r` squares to `⟨C,X⟩² = k·⟨C,C⟩·⟨X,X⟩`, a conic: `K = ⟨R,R⟩·(ΩC)(ΩC)ᵀ − ⟨C,R⟩²·Ω` for a circle through `R`. That is a member of the pencil spanned by `Ω` and the doubled polar of the centre — a conic **bitangent to the absolute**, the classical Cayley–Klein circle. Its chord of contact is the polar of the centre with respect to *both* conics, which is the test the implementation is checked by.
- Under the **Euclidean** absolute the same pencil collapses: `Ω` is the doubled line at infinity, its polar at any finite centre is ℓ∞ again, and every member is a multiple of ℓ∞. There is no circle in the family. Euclidean circles are the dual statement — the conics through I and J — and `circles.dart` stays exactly as it is.
- **A centre on the absolute is not a degeneracy**, which the Euclidean intuition gets wrong: it is a **horocycle**, the genuine limit circle of infinite radius tangent to the absolute at its ideal centre. `circleThrough`'s "no circle has its centre at infinity" is a fact about the parabolic measure, not about circles.
- **Which lines are isotropic is a fact about the geometry too**, and it trips up test data: `3x − 4y + 5 = 0` is an ordinary Euclidean line and is tangent to the hyperbolic absolute, so it has no hyperbolic angle to anything.

**Three kinds that looked like re-foundings generalize instead, because their definitions are constructions rather than formulas.** The centroid is the medians' common point; the incentre is the internal bisectors' common point; the inscribed circle is centred there through the foot of a perpendicular to a side. Each needed only the CK midpoint or the CK bisector, both of which came from §"Two constructions, one algebra". The lesson generalizes: **before refusing a kind, check whether the Euclidean formula is a shortcut for a construction that does generalize.**

**What is refused, and why it is a refusal rather than a gap.** Homothety and translation, because a similarity that is not an isometry does not exist in a Cayley–Klein geometry at all — similar-but-not-congruent triangles exist exactly when the parallel postulate holds. Apollonius and bifocal conics, the radical axis and the focal conic, because each is a locus of distance ratios, sums or powers, and CK distances are logarithms. The circle centre, because recovering the chord of contact from a conic alone is a generalized eigenproblem for the pencil `{K, Ω}`, not a substitution. `RotatedPoint` is the one honest *gap* rather than a refusal: a rotation about the disc centre is literally the Euclidean matrix, both proper absolutes being rotation-invariant there, and only a general centre needs the frame construction that is missing. **Closed in Phase 127, and the frame was not needed** — see §"A rotation is the exponential of one generator", which also finds that half the deferral's reasoning was right and names which half.

**The gate is behavioural, and it replaces the one the plan had scheduled.** Phase 124 scheduled removing `recompute`'s Euclidean default at the end of this phase, on the Phase 121 precedent that a migration default inverts into a trap. That precedent does not transfer: the trap there was a kind *silently inheriting* a wrong value, and here the parameter is supplied by `Construction` at every production call site, so the default only ever applies in tests that mean Euclidean. The risk that actually remains — a new kind whose `recompute` ignores the parameter — is invisible to a signature and visible to a test. `ck_kind_coverage_test` sweeps the corpus at three layouts and requires every kind to change its value or withdraw it; it caught six kinds mid-phase, including one bug introduced by the phase itself (`GeoAngle.measure` falling back to the chart sweep when the CK angle was null — the trap in person). Two things it flagged are correct and are recorded rather than suppressed: per-*instance* checking is too strict, since the join of the disc centre with a pole drops the pole's `w` and makes several constructions genuinely coincide there; and a `LineAngle` measuring a line against its own perpendicular is exactly π/2 in every geometry, because conjugacy is perpendicularity everywhere.

### A rotation is the exponential of one generator (pinned in Phase 127)

Phase 125 deferred `RotatedPoint` on the grounds that a CK rotation about a general centre needs an orthonormal frame in the pencil through it, and that the sign of the dual form varies across that pencil so the angle parameterization is not uniformly circular. **The second half is true and the first is not**, and separating them is the whole of this phase.

**No frame is needed, because the isometries are a Lie group and the rotation is an exponential.** The maps preserving the absolute have Lie algebra `{Ω⁻¹K : K antisymmetric}`, and every 3×3 antisymmetric matrix is a cross-product `[C]ₓ` whose kernel is `C` — so the one-parameter group fixing a point `C` is `exp(t·Ω*[C]ₓ)`, with no basis chosen anywhere. That generator `N` satisfies `N³ = −λ²N`, which closes the exponential into Rodrigues' formula, `R = I + sin θ·(N/λ) + (1 − cos θ)·(N/λ)²`. Two matrix products and no series.

**And it is one formula for all three geometries**: expanded under the Euclidean dual `diag(1,1,0)` it reproduces the shipped `ProjTransform.rotation` entry for entry, `λ = 1` included — the same relationship `harmonicHomology` has to `reflection` (§"The audit"). The Euclidean route is kept anyway, being exact and cheaper, per the Phase 122/124 rule.

**Where the parameterization stops being circular is the centre, not the pencil, and the sign of `λ²` says so.** `λ²` is the absolute's quadratic form at the centre up to sign and scale, so its sign is *where the centre sits*:

- `λ² > 0` — inside the absolute. The pencil of lines through an interior point misses the dual conic entirely, so its angle measure is elliptic and the rotation is as circular as a Euclidean one. This is the case Phase 125 believed did not exist.
- `λ² = 0` — on the absolute. A parabolic isometry (a horolation), `N³ = 0`, with no angle at all.
- `λ² < 0` — outside. A boost along the polar of the centre — a hyperbolic translation whose parameter is a **rapidity**, so `cos` and `sin` would answer with a different isometry rather than an approximate one.

That is the classical trichotomy of hyperbolic isometries arriving as a sign test, and it is why the last two are refused rather than approximated. In elliptic geometry the absolute has no real points, so every real centre is interior and the refusal never fires.

**Two conventions had to be pinned rather than inherited.** The sign of `λ` is free and the stored dual's own sign is a projective convention — the hyperbolic dual is stored as the adjugate, which is `−Ω⁻¹` — so a generator taken at face value turns clockwise in one geometry and counter-clockwise in another; the handedness is anchored explicitly so positive angles are counter-clockwise in the chart in all three. And the centre's **global phase comes off first** (`ProjPoint.dephased`, promoted from `ck_measure.dart`'s private canonicalization): `λ²` scales as `k²`, so an `i`-scaled representative of an ordinary interior centre would fail the realness test and be refused as a boost — the construction has to be a function of the projective point, not of the triple.

### A shape is not an angle (pinned in Phase 128)

Phase 127 put a CK rotation under the two macro tools that stand on `RotatedPoint` and left them "unmeasured either way". Measured, both are wrong, and the note carried forward from that phase — "an equilateral triangle by three CK rotations is genuinely equilateral" — is false.

**`ckRotation` delivers the angle it is asked for exactly, in every geometry, and that is the defect rather than a symptom of one.** The triangle tool's apex sits at exactly 60° from A under every absolute, so the two legs stay equal and the base does not: long in the hyperbolic plane, short in the elliptic one, by 1.2 % at a chart side of 0.3 and 23 % at 0.9. The polygon tool chains a fixed Euclidean interior angle, so every side but the last is equal and the ring never closes — a hyperbolic octagon at a chart side of 0.6 closes with a segment 3.8× its other sides, which is a visibly broken figure rather than a rounding complaint.

**The general fact is that a constant angle names a *shape* only in Euclidean geometry.** A CK plane has no similar figures: angle determines size, so a specification given in angles alone picks out a different figure at every scale. A regular n-gon of Cayley–Klein side `s` turns by θ where `cos(π/n) = σ(s/2)·sin(θ/2)`, with `σ = cosh` hyperbolic, `cos` elliptic and `σ ≡ 1` Euclidean — which is the whole of why a constant serves there and nowhere else.

**So the fix is not a better constant, and that is a construction-graph fact rather than an arithmetic one.** The correct turn is a function of a parent-dependent quantity, and `RotatedPoint.angle` is fixed for the object's lifetime, so a figure baked correct on the stamp stops being regular at the first drag. Both tools are re-expressed instead, in constructions that use *only* metric-neutral parts:

- **The equilateral triangle becomes Euclid I.1** — the apex is a crossing of the circle centred at A through B with the circle centred at B through A. Exactly equilateral in all three geometries at every side length, because "the circle centred at A through B" is a metric-neutral phrase and `CompassCircle` already realises it as one.
- **The regular polygon becomes an orbit.** Its two taps are the centre O and one vertex V, and the rest are `rot(O, 2πk/n)(V)`. Here `2πk/n` really is a constant in every geometry, because it is an angle at the **centre of a symmetry group** rather than an angle of the figure: the cyclic group of order n fixing O acts transitively on the vertices of a regular n-gon in any CK plane, and every side is then an isometric image of every other by construction.

**That contrast is the rule worth extracting.** When a constant angle appears in a construction, ask whether it is an angle *of the figure* or an angle *at the centre of the symmetry that generates it*. Only the second survives a change of absolute; the first is Euclidean-only however carefully it is computed.

Both tools **dispatch on the absolute** and keep their Euclidean routes unchanged, per the Phase 122/124 rule — the Euclidean triangle keeps its scaffolding-free `RotatedPoint` apex with no intersection branch to address, and the Euclidean polygon keeps its two adjacent vertices. The cost is named rather than hidden: in a proper geometry the polygon tool's two taps mean centre-and-vertex where the same two taps mean two adjacent vertices in a Euclidean document. That is a genuine wart, and it is preferred to refusing the tool outright, which was the other honest option.

**A geometry switch does not rebuild a figure**, so a triangle stamped in a Euclidean document stays a `RotatedPoint` apex and is simply wrong after the switch. That is the same class of limitation as the absolute's fixed unit radius: the switch reinterprets a construction, it does not re-author one.

### The macro triage: the parallel is the divider (pinned in Phase 129)

Phase 128 fixed the two macro tools that specified a figure by a **constant angle**. The other nine specify figures by *metric primitives* — perpendicular, compass circle, midpoint, reflection, parallel — every one of which Phase 125 already substituted. So the question here is not whether the primitives generalize; it is whether the **figure** survives, and the answer splits four ways.

**Already right, because every primitive in them generalizes.** The isosceles triangle (a point on the perpendicular bisector of the base) and the right triangle (a point on the perpendicular at a corner). The right angle really is π/2 under every absolute; what changes is the angle *sum*, which is the point of the milestone rather than a defect in the tool. Both are now pinned rather than assumed.

**Right once one affine step is substituted.** The kite and the isosceles trapezium both reflect a point across an axis, and `mirrorPointAcross` did it affinely: the perpendicular foot plus a `SegmentRatioPoint` at ratio 2, which is `2·foot − point`. A ratio along a segment is affine and Phase 125 refused it, so both figures collapsed to two defined sides and two undefined ones. The metric reflection is a harmonic homology and already ships as `ReflectedPoint`, single-valued and branch-free — so under a proper absolute the route has *less* machinery than the Euclidean one, not more. The isosceles trapezium keeps its equal legs in every geometry; what it loses is the word "trapezium", since its two base sides are perpendicular to a common axis and so ultraparallel rather than parallel — a Saccheri quadrilateral, said at the site rather than silently claimed.

**A defined figure that is not the one it is named after.** The square: perpendicular and compass circle at each end of AB give three equal sides and two right base angles, which is a **Saccheri quadrilateral** — its summit measures longer than the base in the hyperbolic plane and shorter in the elliptic one. A square is the regular 4-gon, so under a proper absolute it takes the Phase 128 orbit, and its CK route is `RegularPolygonMacroTool`'s with n = 4.

**Refused, because the figure does not exist.** The parallelogram, the rectangle, the trapezium and the right trapezium all stand on `ParallelLine`, and `parallelThrough` has answered the zero triple under a proper absolute since Phase 125: "*the* parallel through P" is a uniqueness, and it is precisely the uniqueness hyperbolic geometry exists to deny — elliptic denies it from the other side, having no parallels at all. A rectangle needs four right angles besides, and no Cayley–Klein plane has a quadrilateral with four.

**Refused for a weaker reason, and the reason is worth keeping separate.** The rhombus stands on parallels too and its figure is *not* impossible: an equilateral quadrilateral exists in every geometry, and its fourth corner is the crossing of the compass circles about C and A other than B — Euclid I.1 once more, the third time in two phases that the metric-neutral construction turns out to be the classical one. What stops it is the *third* corner, which is a `PointOnObject` glued to a compass circle: `PointOnObject` parameterizes a circle by its polar angle in the chart (PLAN §Parameterization), and a conic bitangent to the absolute has no centre and no polar angle. **Gluing a point to a general conic is the missing capability**, it is wanted well beyond this tool, and it gets its own phase rather than half a construction here.

**A refusal has to be visible, and this is what these tools did instead.** They committed the tapped free points and then a chain of permanently undefined derived objects, with nothing said: four taps, two dots and half a figure, in a document where no amount of dragging can complete it. That is worse than a wrong figure, because a wrong figure at least tells the user something happened. All five refuse their input outright now — `MultiPointTool.availableUnder`, checked in `collectVertex` rather than `onInput`, because the tools whose last tap is position-only override `onInput` and every one of them still routes its *first* tap through the collector. The toolbar disables their rows and puts the reason where the row's explanation goes, keeping the tool's name; the rhombus's reason says "not yet" and the others' say why not at all. The two statements are checked against each other by a test that asks every macro tool directly — a disabled row and a refusing tool are one fact written twice, and the fact lives with the tool.

### A conic frames itself, and the absolute has a size (pinned in Phases 130–131)

Two things the milestone had written down rather than built, and they turn out to be the same complaint from two directions: **the plane and the figure were measured in different units**.

**A conic's box is its support function** (Phase 130). `visibleWorldBounds` read centre and radius, which a conic bitangent to the absolute has not got, so every Cayley–Klein circle contributed nothing to a fit — and neither did any other non-circular conic, which nobody had noticed. `ConicShape.extentAlong(u, v)` gives the least and greatest of `u·x + v·y` over the curve, built on the existing exact `extremesAlong` rather than beside it. It is gated on `ConicClass.ellipse`, and the gate is the point rather than a limitation: `extremesAlong` answers a hyperbola perfectly well — the tangents normal to a direction are real there too — but the curve runs out between them, so a box built on them frames a curve that leaves it. A caller framing a view wants a box or nothing, exactly as it wants nothing from a line. Taking a *direction* rather than an axis is what keeps a rotated view frame exact: one call per view axis with the axis as the normal, no conic transformed and nothing sampled.

**The absolute's radius is a chart scale, not a geometry** (Phase 131). That is the whole of why it can be a per-document setting. Substituting `x = R·x′` carries `⟨P,Q⟩` to `R²` times the unit-disc form, and every measure in `ck_measure.dart` is a *ratio* of such forms, so the `R²` cancels — the plane of radius R is the unit plane drawn R times larger, with identical distances and angles between corresponding points. Nothing about the geometry is parameterized; only the chart it is drawn in.

What that buys is the thing the deferral was about: a construction already drawn at world coordinates of tens or hundreds is *inside* the plane rather than outside it, **with no point moved**. The alternative — rescaling the construction into the unit disc on switching — produces the identical geometry, and rewrites the user's data to get there. Sizing the absolute is the same answer at the cost of one document field.

**The Euclidean absolute refuses a radius, and the refusal is the same fact as similar triangles.** It lies on one line and so has no scale; that is precisely why Euclidean geometry has no absolute unit of length. `DocumentKernel` is what guarantees the refusal is never reached — a Euclidean kernel carrying a stray radius is still the default kernel and answers the unit instance.

**Entering a proper geometry sizes the plane to the figure**; moving between the two proper ones does not. Twice the furthest point puts the construction in the inner half of the disc — far enough from the boundary to be comfortably in the plane, near enough that the geometry is visibly not flat. But once a document *is* hyperbolic, its radius is the plane it is drawn in, and re-fitting on a second switch would move the boundary under a construction the user is working in.

**Schema: `radius ≠ 1` is version 3**, and it is on the version list for the same reason the kernel block itself is (§"The version field is a requirement"). A v2 reader skips the key and lands in the right *geometry*, the radius being a chart scale — and then reads a figure drawn at radius 240 against the unit disc, where every point is outside the plane and the whole document computes undefined. A file that draws as nothing is a misread, not a graceful degradation. A hyperbolic document at the canonical radius is exactly the v2 file it always was, which is what keeps the encoder's "lowest version that reads back correctly" rule honest at three versions rather than two.

### The switch is an operation, not a setting

**A geometry switch re-addresses every intersection point.** `branchIndex` names a position in the candidate list *as filtered and ordered against the absolute*, so the same stored number can name a different crossing after the switch. Phase 123 found this while auditing and assigned it here; Phase 126 built it, and the demonstration is sharper than the argument was. Two `FivePointConic`s through Euclidean-concyclic points that *miss*: a five-point conic is tier 1, so both conics are bit-identical in every geometry and the two complex crossings do not move by an ulp — but Euclidean filters I and J out and hyperbolic keeps them, and they sort *around* the complex pair rather than after it. Address 0 is a crossing in one geometry and a circular point in the other.

**So `Construction.kernel` stopped being `final` without becoming a setter.** Through Phase 125 the field was final on the reasoning that a settable one is exactly how the re-addressing would get skipped. That reasoning was right and is kept by changing the *shape* of the mutation rather than by trusting the caller: the only way to change the kernel is `switchKernel`, which switches, recomputes, re-points by chordal match and returns the report — there is no call that switches without re-addressing. The general principle is worth keeping: when a mutation has an obligation attached, make the obligation the only route rather than a rule the caller must remember.

**Undo restores addresses; it does not re-derive them.** Nearest-match is not invertible — running it backwards can land a point where it never was, and a point with no position at the switch was never matched in either direction — so `SetGeometryCommand` records what the switch decided and `replayKernel` takes the addresses instead of computing them. What could not be matched at all is *reported* rather than repaired, because there is no evidence of what the user meant; that is the same obligation the decoder's `repairedIntersections` carries.

**Lifting the codec's refusal was gated on the tool layer, not on the kernels.** The refusal was the honest answer while nothing could draw such a document, and deleting it required the thing that actually prevents the failure it was standing in for: `ToolInput.absolute`, filled from `Construction.kernel`. While the tools were on the Euclidean default, loading a hyperbolic document meant every crossing the user tapped wrote an address into the file naming a different crossing on reload. The threading also turned up a defect of a different character — `coincidentExistingPoint` perturbs every mutable root and recomputes the *whole construction*, so its absolute is not merely the one it answers in, it is the one the document is left in.

### What is drawn, and what is deliberately not

**Only the hyperbolic absolute is drawable, and the other two are silent for different reasons.** `x² + y² − w² = 0` is the unit circle, the Beltrami–Klein disc's boundary, and the region outside it is not part of the plane — the wash makes that legible before a drag discovers it. The elliptic absolute has no real points, and that is a fact about the geometry rather than a gap in the renderer: elliptic space has no boundary and no unreachable region, so drawing anything would invent an edge that is not there. The Euclidean absolute is the line at infinity, real but with no points in any chart. Centre and radius come from the viewport rather than from a projection of the conic, which is exact at any view state including rotation, because a circle stays a circle.

**Gauss–Bonnet is now a test, which is the first payment on the coverage gate's debt.** Phase 125's gate showed each kind *responds* to the absolute and said explicitly that it did not show the response was right. A triangle's angle sum — π exactly under Euclidean, less under hyperbolic, more under elliptic, with the defect growing with the triangle and vanishing in the small limit — is a global fact about three independent `VertexAngle`s, so an angle measure wrong by a scale, a sign, a supplement or a chart artefact cannot survive it. It is also exactly what the in-app guide tells a user to go and build, which is the right thing to verify first.

### The phase decomposition

- **Phase 123 — the absolute, and the audit that scopes the milestone.** The `Absolute` type (dual primary) with the three instances; `DocumentKernel` carried from the codec into `Construction` and the providers so the setting exists end to end and round-trips; hyperbolic and elliptic still refused at load. The audit above, across all 53 files. **Zero Euclidean behaviour change** is the safety property that makes everything after it incremental — the suite, the goldens and the tracing checksums must all be untouched.
- **Phase 124 — measurement on cross-ratio.** Done, and half its premise was wrong — see §"Angle unifies, distance does not". Angle substitutes; distance dispatches, Euclidean distance not being a cross-ratio at all. Anchors and angle markers stay chart quantities.
- **Phase 125 — the tier-2/3 substitutions**, taken in the order the audit gives them: the verbatim pole/polar generalizations first, then the five genuine re-foundings (`Incenter`/`InscribedCircle`, `RadicalAxisLine`, `CircleCenter`, `FixedRadiusCircle`'s radius param, `BifocalConic`), then the refusals made real in the tools and the inspector.
- **Phase 126 — the mode as a UI.** Done — see §"The switch is an operation, not a setting" and §"What is drawn, and what is deliberately not". The kernel carried into the tool layer *first*, then the switch as a re-addressing operation with its command, then the codec's refusal lifted, then the disc, the menu and the guide.
- **Phase 126b–e — what the kernel phases could not see.** Four user-reported defects in the presentation boundary, a web-renderer defect behind them (`test/web/` exists because of it), and then the two silent re-addressing reports wired to the user — see `docs/STATUS.md`, since these are corrections rather than architecture.
- **Phase 127 — `RotatedPoint`, and the deferral re-examined.** Done — see §"A rotation is the exponential of one generator". The last of Phase 125's per-kind debt that was a *gap* rather than a refusal, and it closed by finding that the frame the deferral asked for was never needed.
- **Phase 128 — the macro tools, measured and re-expressed.** Done — see §"A shape is not an angle". Phase 127's last open box, and it turned out to be a defect rather than a gap: both tools specified a figure by a constant angle, which names a shape in no geometry but the Euclidean one.
- **Phase 129 — the macro triage.** Done — see §"The macro triage". The other nine macro tools, sorted into already-right, right-after-one-substitution, wrong-figure and does-not-exist. The divider is `ParallelLine`, whose refusal Phase 125 already wrote and which nothing downstream had noticed.
- **Phases 130–131 — a conic frames itself, and the absolute has a size.** Done — see §"A conic frames itself". Two items the milestone had written down rather than built. The second was a deferred decision and its resolution is that the radius is a chart scale rather than a geometry, which is what makes it safe to put in a document.


## Milestone outlines

Opened as numbered phases when started; each then gets its own PLAN section. Key decisions are recorded now so they don't get re-litigated.

### M-CK — Cayley–Klein non-Euclidean geometries

**Opened at Phase 123 — see §"M-CK — Cayley–Klein" below for the milestone's own section.** The outline that stood here is folded into it.

### M-P — Deductive-database prover

Independent of the kernel track; can start any time after Phase 112 (it consumes projected positions only).

- **M-P0 — threading decision.** Benchmark cooperative chunking (yield between fixpoint rounds) vs a Web Worker on dart2js/dart2wasm, reusing the Phase 101 harness; `Isolate.run` on native either way. The engine is a resumable state machine regardless (see pinned decisions above).
- **M-P1 — predicates + numeric filter.** Predicates `coll / para / perp / cong / cyclic / eqangle / eqratio / midp / simtri / contri` with numeric evaluators over the diagram's projected positions. Generalize `point_coincidence.dart`'s perturbation probe (V1 already built Cinderella's randomized theorem test) from "same position" to "predicate survives perturbation" — the model filter that keeps forward chaining tractable: never attempt a deduction that isn't numerically true.
- **M-P2 — forward chaining.** Fact database keyed by canonical predicate forms (eqangle/eqratio canonicalization is the fiddly part — take Newclid's canonical forms); ~20-rule DD core from the open DDAR/Newclid sources (rules, not code); fixpoint to quiescence; every derived fact records (rule, premises) so the proof DAG is free. **Wu's method and Gröbner bases are skipped permanently** — unreadable proofs, exact rational arithmetic over `BigInt`, bad effort/reward.
- **M-P3 — full-angle engine.** Second engine for angle-chase problems, a peer behind one `Prover` facade, same fact DB and numeric filter.
- **M-P4 — proof replay UI.** The product: a proof panel (step list) with on-figure animated highlighting per step, reusing painter selection styling and the label system. Point-merge UX says "these coincide by Varignon's theorem" with a *Show why* replay instead of silently merging. The numeric probe stays the always-on cheap path; DD certifies and explains on demand.
- **M-P5 — area method (optional).** Third engine, readable proofs; only if M-P2/3 leave explanatory gaps.

### M-3D (last)

- **M-3D0 — decision record, written before any code.** Taxonomy bounded hard: point / line / plane / sphere / circle-as-plane∩sphere / conic-in-a-plane / polyhedra; **general quadric∩quadric excluded permanently** (a quartic space curve — a phase of effort for almost no user value). 2D remains the default *mode*: locked camera, plane-constrained construction, zero tax on the existing one-tap tool UX. Rendering is wireframe `CustomPainter` with painter's-algorithm depth sorting and depth cueing — no `flutter_gpu`/`flutter_scene`. Tracing is *not* generalized to 3D initially; the bounded taxonomy keeps static intersections simple.
- **M-3D1 — camera.** 4×4 camera; alt-scroll orbit, ctrl-alt-scroll z-dolly — an extension of the existing viewport rotation (V1 Phase 43). Camera lives in presentation; domain stays frame-free.
- **M-3D2 — 3D kernel types + workplane model.** `ProjPoint3`/`Plane`/`Sphere` (real-first; complexify only where a total-intersection payoff exists), reusing `Complex` and the SoA patterns; `Workplane` as a construction-level current-plane object. 3D objects are new `Geo*3` kinds beside the 2D ones, dispatched by the same painter/hit-tester switches.
- **M-3D3 — placement UX.** A 2D click doesn't determine a 3D point: click = ray cast → snap to existing object → else land on the current workplane; a modifier lifts off-plane (maps onto ctrl-alt-scroll raise/lower). Extends the `point_resolution.dart` ladder — ray-snap slots in where snap-to-intersection sits today.
- **M-3D4 — taxonomy objects + tools + codec v3.** Conic-in-plane reuses `ConicMatrix` in plane coordinates — the 2D kernel is the 3D kernel's chart.
- **M-3D5 — depth-aware presentation.** Depth-sorted painting; hit-testing gains depth as the tiebreaker after (priority, distance); goldens per camera preset.

## Risks & de-risking

Three spikes are scheduled first in their tracks, each killing the biggest unknown before architecture hardens on it:

1. **Phase 101** — complex-arithmetic throughput and compile target. Risk: allocation kills drag frames on dart2js. Killed by benchmarking boxed vs SoA on VM/js/wasm up front.
2. **Phase 102** — conic∩conic numerical stability in doubles. Risk: the pencil/cubic/degenerate-split route is numerically treacherous. Killed by prototyping against ground truth (V1 `intersectCircleCircle`, conics through constructed points) and recording the normalization / root-choice / polishing recipe before Phase 105 productionizes it.
3. **Phase 113** — continuation robustness. Risk: the tracing long tail (root-matching failures, step starvation) — the assessment's "hardest per line, budget generously". Contained by proving the skeleton on toys behind a feature flag with a graceful static-solve bail that ships in every phase, so tracing hardens incrementally (114–116) without the app ever depending on an unfinished engine.

Standing risks: test-suite coupling to old branch orderings (mitigated by the canonical-order compatibility rule; dynamic-behaviour breaks quarantined to Phases 116–117 with STATUS notes); parameterization at infinity (pinned — see §Parameterization: parameters stay real in the affine chart; stereographic parameterization for general conics; hyperbola branches as clamped extents); scope creep from CK/prover/3D (milestone-gated; never started mid-kernel-track).

- **Docs & process** — PLAN/STATUS/TODO/archive rotation, CLAUDE.md session protocol, branch-per-phase, analyze-clean + tests-green definition of done, goldens tag-excluded in CI.

## Deferred decisions

- **Toolchain upgrade — Flutter 3.47 / Dart 3.13, booked for after M-P lands.** Development is pinned at Flutter 3.41.9 / Dart 3.11.5 (2026-04-29). `riverpod` 3.4.2, `riverpod_generator` 4.0.6 and `analyzer` >= 10 all sit behind that pin — they want Dart >= 3.12 and `meta ^1.18`, where `flutter from sdk` pins `meta 1.17.0` — so no `pubspec.yaml` edit reaches them; only the SDK moves them. Deferred because the kernel track and M-P are worth more than a toolchain sweep, but the cost grows with the wait: a tree-wide lint sweep under `analyzer` 9 -> 14 against the strict-inference/strict-raw-types block, and a probable whole-tree reformat under `dart_style` 3.1.3 -> 3.1.12 that needs its own commit up front or every real diff becomes unreadable (the Phase 120c lesson). The structural mitigation is already in place: only ~31 files in `lib/presentation/` import Flutter at all, so `lib/domain/` cannot break on a *Flutter* upgrade — only on a Dart language change.
  - **The evidence is already free, and it is green.** `ci.yml` pulls `channel: stable`, so every push has analyzed and tested against **3.47.0** since it shipped, resolving the committed `pubspec.lock`. The upgrade is therefore mostly a question of moving the *local* SDK to what CI already proves. A red CI on an otherwise untouched tree is the signal the deferral has run out.
  - **What CI does not cover** is exactly where the work will land: goldens (`--exclude-tags golden`, regenerated on macOS), the local `dart format` version, and the renderer — a green suite says nothing about the rasterizer (Phase 126d), and web is the compile target.
- **Dependency drift has no test and no gate.** Nothing fails because a package is a year old, so it accumulates silently: twelve packages sat locked below their own constraints for 36 V2 sessions until a routine `flutter pub outdated` turned into a `file_picker` 11 -> 12 API migration (session 135). Worth running at the start of any session that is not mid-phase — minutes to check, and the alternative compounds.
- **Package / app rename.** `pubspec.yaml` name stays `regula` (174 files import `package:regula/…`); renaming to `regula2` plus Android/iOS bundle-id changes is a mechanical later change, to be done in one dedicated commit if/when the app ships under a new identity.
